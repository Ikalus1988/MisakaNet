### 93.1 接手时先纠正了一件事：checkout 停在一个陈旧分支上

工作区起初在 `rebase/pr2494`，`git status` 干净，`git log` 看起来也正常——但
`git merge-base --is-ancestor HEAD origin/main` 为假，**它落后 `origin/main` 15 个提交**。
后果是具体的：`grep` 在树里找不到 `#3288` 刚加的 `/api/leaderboard/state` 路由，我一度以为

量一次。"干净"和"最新"是两件事，而陈旧分支上的 `grep` 会给出**看起来像结论的空结果**。

### 93.6 两条投稿转成课程：#3170 是 E2，#3091 是 E1

`#3170` / `#3091` 都是 `pending-review` 的 lesson 投稿。转课之前各自确认了是**真盲区**，
不是召回缺陷。写成 PR #3289（合入 `07c64caf`），两条分级的差别就是"我有没有真的复现"：

- **#3170 → E2（失败和修复都在本机复现）**：封顶函数 `f(r)=1−(1+r)^(−k)` 的 `f′(0)=k`，
  低区把衰减变成放大，`ρ·k=1.854>1` 必然上升。实测 `f′(0)=1.999997`、空闲不动点
  `0.573965`（投稿测的是 0.574）、四个起点全部收敛到它；修后 `f′(0)=1.000000`、
  `max(f(r)−r)=8.3e−17`（修前 `+0.1101`）、`r0` 处 C¹ 差 `9.3e−8`、空闲 30 轮真的衰减。
  **投稿里有一个数复现不出来，课程里明写了**：`r0` 取 0.2 时 `0.60 → 0.04072`，不是它写的
  `0.061737`——那一行依赖它没给出的 `r0 = 2σ`；与 `r0` 无关的行（含 `0.01 → 0.001029`）精确吻合。
- **#3091 → E1（诚实的 E1）**：非 ASCII 安装路径让 initdb 收到 GBK 字节而它要 UTF-8，
  `0xb7` 就是那个字符 GBK 编码的首字节。复现需要一台中文用户名的 Windows，本机不是，
  所以**没有实测就不写 E2**。字节链我自己验了：U+98CE 的 GBK 是 `B7 E7`，
  `'\u98ce'.encode('gbk') == b'\xb7\xe7'`，课程里留了这一行可复跑。

**两个坑是本地跑测试/门禁抓到的，都不是生成器抓到的：**

1. **`docs/trust-semantics.md` 的证据分布表会因为加课而陈旧**。加一条 E1、一条 E2 之后，
   E1 49→50、E2 76→77、总数 481→483，而 `scripts/evidence_distribution.py --check` 会红。
   **六个生成器一个都不管这张表**——它是手工粘贴的，由 `tests/test_evidence_distribution.py`
   兜底。**"跑一遍生成器"不等于"派生面都同步了。"**
2. **`FR3-home-path` 拒收课程里的 Windows home 路径**（`check_field_reports.py`）。已改成
   `<non-ASCII-user>`，字节解释保留码点——**隐私规则要的是不发布 home 路径，而课程要的是
   那个字符的码点，两者不冲突**。这条是跑门禁跑出来的，不是猜出来的。

   > **它随后咬了本节自己一次**：本节的初稿为了记录这件事，把那串字面路径抄了进来，
   > 于是 PR #3290 的 `field reports` 变红——判据是同一个（`docs/**` 属"published surfaces"，
   > FR3 对**改动到的** docs 文件生效）。**"记录一次泄漏"和"再泄漏一次"用的是同一条规则，
   > 而记录者的豁免不存在。** 修法照旧：写形状，不写字面值。

**排名 diff（看了，没有照单全收）**：31 条 pinned 查询里 6 条换了顺序。2 条是本次引入的
（`encoding bug Python` 新课进第 3，0.6351；`中文乱码怎么解决` 进第 7，0.6965）；4 条是
**相邻名次对调、分差 ≤0.002**（其中 `feishu block API false success` 是精确平局），
属加课后 IDF 漂移，不是语义变化。另一面也要记：**饱和封顶那条课没有进任何一条查询的 top-10**
——31 条里没有监控/饱和类查询，这是**fixture 的缺口**，不是课程的缺口。

### 93.8 §92.5 的 Ruby 矛盾：文档级定论，实测仍未闭环

子代理做了只读调查（本机无 Ruby、`docker` 二进制在但 daemon 不可达、apt 装 Ruby 需 root，
都超出只读权限）。结论：

- **官方语义站在课程根因那一行（`:26`）**：`require_relative` 相对**调用者文件**所在目录，
  不是 cwd。官方手册原句是 "relative to the directory containing the requiring file"
  （[Kernel#require_relative](https://docs.ruby-lang.org/en/3.3/Kernel.html#method-i-require_relative)），
  同页 C 实现 `rb_current_realfilepath()` 自证 base 取自调用者文件路径。只有 `load` 才吃 cwd。
- **所以错的是 Solution 一段**（`cd` 步骤，`:35–46`；`File.expand_path(File.dirname(__FILE__), …)`
  那条与 `require_relative` 等价、对"树不存在"是空转；`:84` 的验证同理）。
- **§92.5 的标题措辞偏了一点**：矛盾在 **Solution 对 Root Cause**，不在 Root Cause 句内部。
- **生产检索**：`require_relative LoadError` 的 top-1 = **11.68** 精确复现（`worker-bm25`）。
  但"第二名 2.5"**复现不出来**：该查询只返回 2 条，第 2 条是 FAQ，而 **FAQ 分与 lesson 分不是
  同一把尺子**（FAQ 0–100，lesson 走 BM25+IDF）。所以"首命中就是那门课"成立，"11.68 vs 2.5"
  在同口径下拿不到——**记数字前先确认两边的尺子**。
- **建议**：不要去编辑那门课（课程合入后不可变，修正走新 PR）。新增一篇纠正课
  （`require_relative` 相对文件、明确否定 `cd`、正确诊断 = 检查安装树）并把旧课降级为
  `superseded`；Docker 那一半另有覆盖。**唯一还没闭合的是"一次运行时实测"**——文档、C 源码、
  维护者自己在 #2465 的答复三方一致，但§90.4.1 那条规则仍然成立：**没测到 ≠ 测过**。
