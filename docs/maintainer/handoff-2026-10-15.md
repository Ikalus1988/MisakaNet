### 91.3 `test_me_inbox.py` 那个 import：第一遍测法是错的，结论差点跟着错

那个文件末尾有

```python
if __name__ == "__main__":
    pytest.main([__file__, "-v"])
```

但模块里没有 `import pytest`。直接跑文件，第一次实测得到的是：

```
ModuleNotFoundError: No module named 'misakanet'
```

**根本没走到 `pytest.main`。** 如果就此收工，commit 里就会写「跑起来是 `NameError`」——
一句我并没有测到的话。加上 CI 的 `PYTHONPATH=.` 再跑，才是真相对照：

| 树 | 结果 |
|---|---|
| 带 import，`PYTHONPATH=.` | **15 passed in 1.28s** |
| 不带 import，`PYTHONPATH=.` | `NameError: name 'pytest' is not defined` |

> **规则（承 §90.4.1）：验证一个修复之前，先确认你真的走到了那条路径。**
> 第一次的失败被更早的一层挡住了，而那一层恰好是本机环境与 CI 的差异。
> 这与「反例必须让退回旧写法真的变红」是同一条：**没测到 ≠ 测过。**

### 92.3 pr-agent 会把 `Closes #N` 抹掉，于是赏金 issue 静默地不关

#3258 合并后 **#2838 仍然 OPEN**。原因不是 GitHub 的行为，是我们的：

```
$ gh pr view 3258 --json closingIssuesReferences --jq '.closingIssuesReferences'
[]
$ gh pr view 3258 --json body --jq '.body | test("closes #2838")'
false
```

原 PR #2921 的正文第一行是 `Closes #2838.`，但 **pr-agent 用 `<!-- pr-agent-generated -->`

而且没有任何门禁会喊——PR 照样绿灯、合并照样成功，只有 issue 留在队列里没人知道。

**待定**：这要么修 pr-agent 的正文改写（保留原始 closing 关键字），要么在 lesson PR 上加一道
形状检查断言 `closingIssuesReferences` 非空。前者更根本。

### 92.5 已入库但内容存疑：Ruby 那门课的根因段自相矛盾

#3258 合入 `44d4cc01`。它的 Ruby 一节同时说了三件不能同时成立的事：

1. 根因段：`require_relative` 相对**文件**而非 cwd；
2. Step 2：`cd` 到脚本所在目录；
3. Step 3：`require File.expand_path(File.join(File.dirname(__FILE__), 'lib', 'tui'))`。

第 3 条**正是 `require_relative` 本身的语义**。若第 2 条能解决，第 3 条对这个同一问题就是多余的。

**本机没有 Ruby，所以只标记、不改。** §90.4.1 那条规则在这里成立：没测到 ≠ 测过。PR 上留了
一条能一次定论的复现命令（把 `require_relative` 的脚本放在 `$d/app/`，从 `/tmp` 运行）。
`evidence_level: E1` 本来就诚实地标了深度不足，所以这不是隐瞒，是欠账。

### 92.7 同一个 PR 被两个机制夹住：引用 `Closes #N` 会被当成认领

§92 自己的 PR（#3278）被形状门禁拦了：

> **This claims a question bounty (#2838) but changes no file under `lessons/core`,
> `lessons/contrib` or `lessons/en`.**

那个 PR 只改了 `docs/maintainer/handoff-2026-10-15.md`，确实没加 lesson。但它**根本没有认领**
#2838——§92.3 是在**记录** pr-agent 抹掉 `Closes #N` 这件事。判据是：

```python
CLAIMS_ISSUE = re.compile(r"(?i)\b(?:close[sd]?|fix(?:e[sd])?|resolve[sd]?|solve[sd]?|address(?:es|ed)?)\b"
                          r"(?:\s+\w+){0,3}?\s+#(\d{1,6})")
```

**它不认 Markdown 的代码跨度。** 正文里这句是在解释机制：

> the body rewrite replaced `` `Closes #2838.` `` with a `<!-- pr-agent-generated -->` section

`Closes` + 空格 + `#2838` —— 正则命中，于是 #2838 的正文带着 `misakanet-question-bounty` 锚点，
"认领赏金但没写 lesson" 这条就成立了。

**两个机制在这里互相掩护，证据还被自己毁了**：pr-agent 随后重写了本 PR 的正文，把同一句话截断成

> §92.3: pr-agent rewrites PR body and strips `` `Closes # ``

—— 数字没了。所以**现在去读 PR 正文已经看不出当初命中的是什么**，只能靠 `CLAIMS_ISSUE` 复现。

`pr-shape-guard.yml` 的注释已经防过同一类的一半（"a PR's own body can quote the marker while
explaining it"），但只防了**引用锚点**，没防**引用动词**。

> **待定（与 §92.3 同属"让文档能描述自己踩的坑"这件事）**：要么给 `CLAIMS_ISSUE` 加代码跨度
> 的负向断言，要么在 pr-agent 的摘要里保留原始正文。后者更根本——它同时解释了 §92.3。
>
> 顺带一条操作事实：**形状门禁只对 `opened / synchronize / reopened` 触发，改 PR 正文不会重跑**
> （`pr-shape-guard.yml:4`）。所以本节是靠追加一个提交重跑 CI 的，不是靠改正文。
