# `needs-human-review` 50 样本实测（2026-11-09）

> 目的：回答「review band 的 145 条到底卡在哪」。样本＝当时最新的 50 条开放 `needs-human-review`，
> 逐条看结构（Problem / Root Cause / Fix / Verification）、泛化性（§2.1.1 的「去掉专有名词」测试）
> 与转换器能不能吃下。

## 1. 结构：一半内容完整，另一半是「旧表单没有 Root Cause」

| 形态 | 条数 | 说明 |
|---|---|---|
| Problem + Root Cause + Fix（±Verification） | **22** | 11-04 之后的新表单：六段齐 |
| Problem + Fix + Verification，**无 Root Cause** | **19** | 10 月旧表单：`Problem/Error/What was tried/Fix (if known)/Verification`，从未要求写根因 |
| Problem + Verification，**无 Fix** | 8 | 内容太薄，需要回信补 |
| 只有 Root Cause + Fix（无 Problem 标题） | 1 | 标题写进了正文 |

结论：结构缺口 **不是内容质量**，而是**表单版本**——10 月的 intake 表单根本没有 Root Cause 这一节。

## 2. 泛化性：22 条完整样本里 20 条通过

用 §2.1.1 的测试（去掉专有名词后根因仍成立、且能改写成一条可回答的判断）：

- **20 条通过**（例：「旧二进制整文件读改写会把新字段抹掉」→ 与新字段名无关；「golden 由被测同一管线生成 → 对拍恒绿」；「curl 走 Schannel / Node 用自带 CA」）。
- **1 条是标注过的假设**（#4418：MCP SSE 并发/限流，原文写「大概率」，没有观测）——按「假设必须标注」可以收，但应留在 E0/待复现。
- **1 条边界**（#4426：工作目录名可预测 + 并行自动化把目录搬走）——改成「按名字寻址的目录不是身份」成立，但证据只在那个环境里。

## 3. 真正的瓶颈：转换器只吃下 1/50，不是因为内容

`convert_intake_batch.py --limit 200` 当时报：**scanned 151, convertible 1**（#4606），
skip 直方图 `missing Problem/Root Cause/Fix: 146`。而人工核对同一批里 **22 条四段齐全**。

根因在 `intake_lesson_to_file.section()`：它取**第一次**出现的 `## <name>`。而 MCP intake 表单的
正文是「表单的空 `## Problem` + 提交者自己的 `## Problem`/`## 症状`」，于是拿到的是**空串**。

在 50 条上做离线模拟（把同名标题的**所有**出现拼起来）：

| 解析方式 | 通过 P/R/C/F 的样本 |
|---|---|
| 现状（第一次出现） | 1（走完整转换流程的只有 #4606） |
| 所有出现拼接 | **17** |
| 拼接 + `症状`/`Symptom` 视为 Problem 别名 | **21** |

也就是说：**21/50 的内容是够的，卡在解析和别名上**，不是卡在人审。

## 4. 建议（按收益排序）

1. **改 `section()`：同名标题取「所有出现拼接」而非第一次**（空的首段自然被跳过）。离线模拟 +16/50。
2. **`症状` / `Symptom` 作为 Problem 的别名**（4/50 只差这一条）。
3. 改完后重跑 `convert_intake_batch.py`，把新通过的一批按 #4602 的流程转换（gate → 生成物 → PR → 回执）；
   预计一次能把 review band 从 145 压到 ~90。
4. **10 月旧表单的 19 条**不要硬转：它们没有根因段。要么在 `Fix (if known)` 里能读出根因时人工转，
   要么回信请提交者补根因——这正是那 121 条「缺 Problem/Root Cause/Fix」的主体。

## 5. 没做的事

- 没有改解析器（本文是测量，不是补丁）。
- 没有复核 22 条里每条的技术正确性——只做了「结构 + 泛化性」两道门。
- 样本是**最新** 50 条，不是随机抽样；老样本（10 月旧表单）在样本里被高估/低估都可能，量级以 §1 的形态分布为准。
