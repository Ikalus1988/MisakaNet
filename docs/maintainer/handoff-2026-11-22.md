## 1. 判断

### 1.1 「满页 = 截断信号」，同一天在两处独立出现

| 位置 | 旧行为 | 实测 |
|---|---|---|
| `convert_intake_batch.open_intakes()` | 默认 `--limit 300`，一页读回就问"够不够" | 469 条 open `mcp-intake`，只看到最新 300：**scanned 74 / convertible 0**；改成 1000 后 **183 / 7** |
| `question_autopilot.existing_bounty()` | `per_page=100` 单页找 anchor 标记 | 114 条 open 赏金里 **6 个 anchor 各被开了两次** |

两处都在同一个文件里有过先例（`ISSUE_PAGE_SIZE` 的注释就是为这个写的），但**判据没有跟着走**。

**判据（下次别重新推导）**：

- 任何"读一页 + 和阈值比"的自动化，把 **`len(结果) == 请求上限` 当失败**，不要当队尾。满页和队尾打印的东西一模一样。
- 修完不要只看 dry run：`workflow_dispatch` 跑一次真的，因为生产路径（`--write`、token 权限、步内过滤）与本地 dry run 可以不一样。这一轮两次都是靠真跑才确认（`scanned 184 / convertible 7 / new lesson file(s): 7`）。

### 1.2 「归属靠标记」：收口规则只能关自己写的东西

`#5565` 给赏金加了收口规则，第一条判据写成"正文里没有 anchor 标记 ⇒ 它没被刷新 ⇒ 关掉"。第一次真实运行关了
**10 条不是它开的** `bounty` issue（#1258、#1550、#1753、#1819、#2593、#4013、#4751、#4874、#4875、#4876），
五分钟后全部重开（`#5569` 修）。

**判据**：一条关闭规则必须从对象的**自身属性**出发（"有没有我的标记"），不能从**我对它做过什么**出发（"我有没有刷新它"）。
后者在只有自己写对象的系统里恒真，一旦存在第三方写的同类对象就变成误伤 —— 而它一出现就是十条。

### 1.3 「grep 到 issue 号」不是修好的证据

横扫 20 条 `scope:repo` 时，最早的想法是"引用次数多 = 早修好了"。**不成立**：引用最多的是 `#2903`(7)、`#2998`(7)、
`#2221`(5)，而它们大多只是"记录在哪"（handoff/ADR/README）。真正修好的两条，判据是别的形状：

- `#2891`：`deploy-worker.yml` 里 `npm ci` 那一步的注释**点名叫了它**，并写了"`npx` 会取 latest，`package.json` 管的不是生产"；
- `#3231`：`detect_placeholder_fixture()` 在 `reject` 分支之前，`auto-placeholder` 这条路径的注释解释**为什么不用 `needs-salvage`**。

**判据**：一条 issue 已修的标志是"改动点引用了它，并且解释了为什么这么改"；不是引用次数。

### 1.4 公共面那条决定，缺的不是判据而是执行者

`intake-flywheel.md` §5 的复测（`#5561`）：被拦的课 20 → 24 → **27**，词 27 → 34 → 34，而**批次可转数一直是 0~1**。
34 个词里 21 个是散文（62%），9 个是真标识符，4 个是公开工具名（已进 allowlist：`ss-server`/`bru`/`bruno`）。

决定依赖的那一环是"人写课时顺手改句子"，而它**没有队列、没有标签、没有归属**。所以每进一条这样的报料，这个桶就长一条。

### 1.5 本地产物与 CI 产物不同源（Windows / Linux）

同一份语料，Windows 跑 `update_lessons_json.py` 得到 `data/lessons.json` 3,922,632 B，Linux 得 3,887,437 B（差 ~35 KB，
~32 B/篇，来自 CRLF 进入了被截取的 summary/preview 字段）；`lessons/index.md` 在 Windows 上是整表 churn。
第一次推 PR 时 `gate` 就红在这里。

**判据**：语料产物在 **WSL 里**按 CI 顺序重跑，然后到 **ext4 的干净 clone** 里跑 `scripts/ci/check_dist_diff.py main-side` 自查。
在 `/mnt/d` 上跑会给假阳性：工作区里被 Windows 写过的文件带 CRLF，而 WSL 的 git 不做归一化。

## 5. 坑（本卷实际踩到的）

1. **`git reset --hard origin/main` 拿到的是旧的 `origin/main`**：浅克隆里 `git fetch origin main` 与
   `refs/remotes/origin/main` 的更新不同步，于是提交的 parent 落在旧的头上，rebase 之后才发现。对时的顺序是
   `fetch → log origin/main → reset`，且要看一眼 `git rev-parse HEAD^`。
2. **同一天里同一个文件连着合两条 PR，第二条必冲突**：squash 改了历史，rebase 会打印
   `skipped previously applied commit`。这不是错，但**产物必须在 rebase 之后重新生成**，否则 diff 里带着旧语料。
3. **`wsl -e bash -lc` 的 `/tmp` 会被清**（本机 `swap.vhdx` 报错会导致实例重启），临时 clone 放 `~`。
4. **测试会写真实数据文件**：`tests/test_intake_receipt.py` 往 `data/intake_receipts.jsonl` 写 297 行（`#5551`）。
   跑完全量测试要 `git checkout -- data/intake_receipts.jsonl` 再提交。
5. **`gh` 的 `GITHUB_TOKEN` 在本机是失效的**：所有命令都要 `GITHUB_TOKEN= gh …` 走 keyring 账号；
   推分支用 `http.extraheader` 带 keyring token，不要写进 remote URL。
