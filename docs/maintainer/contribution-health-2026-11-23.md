# 贡献健康度：三个读数与三个提议（2026-11-23）

这份文件回答一个问题：**这个仓库"活跃"吗？** 答案是：活跃，但活跃的是自动化；而**审核产能**
（唯一不能用 cron 替代的东西）正在被自己的赏金入口换成噪声。

关闭得快，说明分诊不慢；问题在**进来的是什么**。

## 二、三个判断

### 2.1 审核产能是唯一稀缺资源，而赏金入口在把它换成噪声

80 个关闭的 PR 里，23 个是"回答问题"的赏金 PR，45 个连 DCO 都没有。它们是**同一条流水线**的产物：
每个 issue 上都挂着 Opire 页脚邀请 `/claim`，仓库自己又生成 **70 条**
`[Bounty] Answer the N linked question(s)`。于是"回答问题"这件事的最大供给方是**想拿赏金、但不读这个仓库的
agent**。

代价可以量：每一个关闭都需要一次**写清理由**的诊断（这是对的，也是慢的原因）——

- `#4813`：PR 只加了一个 `BOUNTY_RESOLUTION.md`，写着"已解决 + 收款账号"，没有任何答案；
- `#4666`：答案描述了另一个仓库（`misakanet-bootstrap`、`/Library/LaunchAgents/…` 都不存在）；
- `#5223`：Shape Guard 直接判定"claims a question bounty"且补丁形状不安全。

**24 个合并背后是 80 次诊断。** 这是当前最贵的一项支出，而且它不产出语料、不产出代码。

### 2.2 "活跃度"里绝大部分是自动化；外部贡献的集中度是 1 人

396 / 408 次提交来自 owner，其余是 dependabot + 两位贡献者。合并的外部 PR 里 75% 来自一个人。
这不是"社区不活跃"的抱怨——它意味着**如果那个人明天不来了，外部贡献≈0**，而现在所有关于
"社区"的读数（贡献者榜、赏金、邀请）都在为这一个人服务。

### 2.3 机械层杀死的真贡献，比质量层更多

在开的 3 个外部 PR 里，2 个（`#5341`、`#5345`）**因为生成物冲突**卡住：冲突全在
`data/lessons.json`、`docs/data/*`、`docs/.generated-pages.json`、`docs/_redirects` 上。贡献者要自己
rebase、跑七个生成器、再自查——而这恰恰是仓库对维护者说"不要手工解"的那一步。

同一形状的第二例：45 / 80 带 `needs-dco`，而 `fix-dco.yml` **只在有人评论 `/fix-dco` 时**才跑。
一个第一次来的人不知道该评论什么，于是 PR 死在一条 `git commit --amend -s` 上。

**判据**：一个贡献者无法自己修复的失败，要么由机器人修，要么在邀请里写明怎么修。否则它不是在
筛质量，是在筛"读过内部文档的人"。

## 三、三个提议（按"每单位审核产能的收益"排序）

### P1（先做，最便宜）把贡献健康度做成读数

`scripts/heartbeat_report.py` 已经在报检索、语料、E0–E4，但没有一行报**贡献**：外部 PR 开了多少、
合了多少、关了多少、多少不同作者、合并耗时中位数、多少卡在 `needs-dco`。

没有这一行，下面两个提议无法验收——而且"活跃度"会继续由提交数（=自动化）代言。

### P2（收益最大）把"冲突全在生成物上"的 PR 自动重建

把 `auto-sync-prs.yml` 的失败分支接上仓库已有的零件：检出 `main` → 只取贡献者**手写**的文件
（`lessons/**`、`docs/**/*.md` 里非生成物）→ 跑七个生成器 → 推回原分支。这正是维护者今天手做的
那一步（`#5341`、`#5345`、以及 `#5597`→`#5617` 都是同一动作）。

判据：外部 PR 的"因冲突而失败"数量归零；贡献者不需要跑生成器。

### P3（需要产品决定）把噪声的来源收窄

两条路，选一条：

1. **停发/收敛那 70 条生成式赏金**：它们由未答问题生成，而"回答问题"恰好是最容易被廉价批量生产的；
2. **把验收前置到 claim 处**：`/claim` 的模板强制"命令 + 输出"字段，没有就不算认领（`.github/ISSUE_TEMPLATE/ai-bounty-template.md`
   的第 0 条已经这么要求，但它在 PR 阶段才被检查）。

`#5521`（Opire 页脚清理 workflow）是第三条路，但它引入一个新的、会批量改评论的自动化——它是
**事后清理**，P3 是**事前不产生**。清理不解决问题来源。

## 四、验收

| 提议 | 读数怎么变 |
|---|---|
| P1 | heartbeat 出现"外部 PR / 作者 / 中位合并时长 / needs-dco 率"一行，且可回溯 |
| P2 | 外部 PR 里"生成物冲突"导致的重开或放弃数量 = 0；`auto-sync` 失败不再需要维护者介入 |
| P3 | 关闭未合的 PR 里 `Answer the N` 类占比下降；每次合并所需诊断次数下降 |

## 五、不做的事

- **不追 PR 数量**。现在的问题是 107 个外部 PR 只换到 24 次合并，不是提交太少。
- **不为活跃度放宽门禁**。DCO、Shape Guard、公共面这三道门各自都抓到过真问题；该改的是**门禁失败后
  的下一分钟**（谁修、怎么修），不是门槛高度。
- **不把"回答问题"当成内容来源**。语料已经证明它的可转换率极低（173 条 intake 可转 0），
  而它现在是噪声的主要供给方。
