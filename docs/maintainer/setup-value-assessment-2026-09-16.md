# setup 的第一性原理评估：它解决什么、是否独立必要、离"傻瓜式"还有多远

> 评估对象：`packages/misakanet-setup`（npx 安装器，0.4.2）+ `integrations/agent-autostart`（Python 版）。
> 评估基准：仓库主体的既有形态（PRD ①–⑥、MCP 服务、语料、worker）+ **用户口述的原始要求**
> "服务完全不熟悉 Agent 规则但需要使用 agent 提效的打工人，并且已经傻瓜式管理"。
> 日期：2026-09-16。所有数字都来自本次会话可复现的命令，不是估计。

## 0. 结论先行

1. **独立必要：是。** 它把"语料 + 服务"变成"被 agent 用到的记忆"，主体自己不提供这条路径。
2. **是否重复主体：不重复，但内部有必要的重复。** 两套安装器行为镜像（70 项测试保平），
   今天改 Codex 文案、加 codewhale 都不得不改两处 —— 建议收敛为单一行为源。
3. **是否符合那条 PRD 口径：约六成。** "装一次"这半基本达标；"不用管 / 默默预防 / 自动沉淀"
   这半仍是**提醒 + 自律**。真正的瓶颈不在安装，而在**agent 是否遵循**，且目前没有可测量的指标。
4. **PRD 里没有这一条。** `docs/prd/01–06` 分别是 intake / wallet / workflows / D1 服务 / 问答闭环 /
   注册，**没有任何一条要求谈安装或接入**。setup 是 PRD 之外长出来的"采用面" —— 它服务于
   PRD ④ 的服务能否被用上，本身不产生新功能。用户口述的那句要求**在仓库里没有写成文字**，
   本次评估把它当作默认判据。

## 1. 第一性原理：没有 setup 会怎样

主体的价值 = 439 篇课程 + 一个服务（7 个工具、D1）+ intake/问答闭环。
但**服务不会自己走进任何 agent 的工作流**。价值兑现需要两件事同时成立：

| 条件 | 谁提供 | 没有它会怎样 |
|---|---|---|
| **(a) 可达**：把传输与鉴权接进每个 agent 的配置 | 安装器 | 用户要自己知道 `~/.claude.json`、`.codex/config.toml`、`.hermes/config.yaml`、`.openclaw/openclaw.json`、`.codewhale/mcp.json` 各自怎么写 —— 这正是"不熟悉 Agent 规则"的人最不可能做到的部分 |
| **(b) 会查**：告诉 agent **何时**该查 | 规则块 / 钩子 | 端点存在但没人调用；即使接好了，agent 也不会在遇到报错时自发查询 |

两条都有实证：本机 5 个 agent 是**五套不同的配置文件**（本次逐个验证过）；外部用户按插件市场
安装时连"装哪个包"都解析错了（#1677）；而 codex / codewhale 只有在规则块进入 prompt 后才会自发调用
（`codex debug prompt-input` 里能看到 `# AGENTS.md instructions` 就是我们的块）。

**所以 setup 不是"锦上添花"。** 它是主体价值的最后一公里；没有它，这个仓库对外部用户约等于
"一个没人调用的 MCP 端点"。

## 2. 与主体相比：规模、独立性、重复度

| 面 | 规模 | 说明 |
|---|---|---|
| setup 面 | **~3,565 行**（`packages/misakanet-setup` 1,219 + `integrations/agent-autostart` 2,346） | 唯一的分发/接入面；**70 项测试**挂在它上面 |
| 主体 | **~39,000 行**（`scripts/` 26,817 + `workers/` 12,195）+ 439 篇课程 | 服务、索引、intake、D1、站点 |

- **不是主体的子集**：主体里没有任何模块负责"把 MCP 接进别人的 agent 配置"。
- **内部确有重复（应当收敛）**：Python 安装器（面向 clone 用户）与 npx 安装器（面向陌生用户）
  行为镜像 —— 幂等、备份、`--verify`、`--uninstall`、规则块、钩子都要各写一遍。两条分发渠道
  是真实需求，但**行为源应该只有一个**（例如 Python 侧转发到 npx 包，或两边共读一份 spec 文件）。
- **旧的重复面已经退掉了**：`inject_to_claude.py` 已不在仓库（仅 `.pnpm-store` 缓存与
  `docs/domains/{docker,claude}.md` 两处陈旧引用）—— 建议顺手清掉那两处文本。

## 3. 对照"傻瓜式管理"逐条打分（用户口述口径）

| 要求 | 现状 | 证据 / 缺口 |
|---|---|---|
| **一条命令装好**（不需要知道配置在哪） | ✅ 5 个目标：Claude Code / Codex / Hermes / OpenClaw / codewhale；幂等、备份、`--verify`、`--uninstall` | 今天实测：连跑两次第二次为 no-op；对 CLI 写出的 `mcp.json` 也能识别为"无改动" |
| **装完不用管** | △ | 14 天升级提示已存在，但 **0.4.1 之前安装的用户必须先手动重跑一次**（旧安装器从不刷新钩子，#1745），且**没有渠道**通知他们（只有 README 一句话） |
| **默默预防重复犯错** | △ | 钩子默认不联网取课程（`MISAKANET_HOOK_FETCH=1` 才取）；是否查询取决于 agent 是否遵循规则块 —— codewhale 实测 2 次里 1 次没查 |
| **长会话自动沉淀** | △ | 仍是"提醒"（规则里的"约 20 轮"或钩子提示），不是自动流程；**Codex 连钩子都没有**（0.154.0 的 hooks 走管理员层） |
| **可回退、不搞坏环境** | ✅ | 备份 + `--uninstall`；今天两次真实安装/卸载都在真机上验过 |
| **受众能不能上手** | ⚠️ | 需要 Node/npx，且前提是"你已经装好并用着某个 agent CLI"。**真正对不懂规则的人友好的路径是
  「把一句话粘给助手」**（`integrations/agent-autostart/INSTALL_FOR_ME.md`，助手自己读文档、自己装、自己回报）—— 这条目前只是 README 里的补充说明，应该提到主路径 |
| **不泄漏凭据** | ✅ | token 只进配置文件与请求头，不进 argv（OpenClaw 那条正是为规避 argv 泄漏才改成写文件的） |

## 4. 最关键的洞察：瓶颈不是安装，是"遵循"

今天最有价值的两组数据点：

1. **codewhale**：同一份生产规则块，一次跑完 `search → get_lesson`，另一次用 56 次 `bash` 探索而完全没查；
   而把它改写成**三行祈使句**（"你必须先调用…，第一行原样输出 AGENT-MARKER-42"）后，**立刻**同时出现标记与工具调用。
2. **Codex**：配置与 prompt 投递都已确证（`mcp list` / `doctor` / `debug prompt-input`），但它没有用户级
   生命周期钩子 → "20 轮沉淀"只能靠规则块自律。

也就是说：**"傻瓜式"的上限现在由"指令遵循率"决定，而不是由安装器决定**。而我们对遵循率**没有任何测量** ——
安装器只统计"配置写没写对"，没人统计"遇到报错时有没有真的查"。

### 建议（按性价比排序）

1. **规则块改成祈使句前置**（现在是一段温和长句），并用同一批问题对 5 个 agent 做 A/B 复测遵循率；
2. **把"是否真的查了"变成可观测**：钩子在"检测到报错/失败却没有任何 misakanet 调用"时记一次本地计数，
   `--verify` 能报出来 —— 这比"安装成功"更接近用户真正关心的事；
3. **把 INSTALL_FOR_ME.md 那条路提到主路径**：对不懂 agent 规则的打工人，"粘一句话给助手"比"开终端跑 npx"更傻瓜；
4. **收敛两套安装器的行为源**，并在清理 `docs/domains/{docker,claude}.md` 里的 `inject_to_claude.py` 残留。

## 5. 一条操作性教训（今天重复了三次）

`npm publish` 的绿色 workfow ≠ 用户能装到。今天三次发布（`misakanet@2.30.2`、`setup@0.4.1`、
`setup@0.4.2`）都出现 registry 传播滞后，最久约 7 分钟；判据应当是
**"`registry.npmjs.org/<pkg>/<version>` 能解析出版本号"**，而不是 workflow 的勾。
