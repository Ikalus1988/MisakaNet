### 90.2 更正一：占位符**够不到**自动批准线 —— §89.7 那句「会动自动批准线」是错的

§89.7 把 #3231 记成「落在打分路径上、**会动自动批准线** → 属策略，已开 issue 交 owner」。
这句话是**没测就写的**。实跑了 `auto_review_issue()`（阈值 `THRESHOLD_APPROVE=75` / `THRESHOLD_REVIEW=40`，
`make_decision:748`），四种构造：

| 构造 | weighted | conf | final | 判定 |
|---|---|---|---|---|
| #3137 原形态（5 个 AC，全 `test-*`）| 38.50 | 0.85 | 32.73 | **reject** |
| 补 `## Root Cause` / `## Fix` / 代码块 + 版本号 | 45.50 | 0.85 | 38.67 | **review** |
| 6 个小节全齐（Problem/Environment/Root Cause/Fix/Verification/AC）| 60.50 | 1.00 | 60.50 | **review** |
| 再加 frontmatter + 12 行填充把字数堆上去 | **65.75** | 1.00 | 65.75 | **review** |

**堆到 65.75 仍差 approve 线 9 分多，够不着。** 而且拖分的不是「夹具」：

```
✗ Only 1 generic tech keywords
✗ Contains specific project names
```

两条都与「是不是夹具」毫无关系。**结论：占位符永远不会拿到 auto-approve，守卫不碰打分路径，
不碰任何权重或阈值。**

所以两个方向的记录都只有一半对：

| 来源 | 说法 | 实测 |
|---|---|---|
| §89.7 | 「会动自动批准线 → 属策略」| **错**。approve 够不着 |
| #3231 issue 正文 | 「方向单一，与 §86.4 不冲突」| **对**，但当时是断言不是证据 |
| 我自己的子代理报告 | 「探针体 75.5 → approve，守卫会移除自动批准」| **错**。复现不出来，最高 65.75 |

第三条记在这里是因为它本来会改变结论。**子代理报的实测数字必须自己复跑** —— 它的代码引用
（`make_decision:748-759`、阈值 `:77-78`、硬信号上限 `:895-899`）全部核对无误，唯独那条
决定性的分数是错的，两者不能因为"同一份报告"就一起采信。

### 90.3 更正二：`reject` 不是终点 —— 它每天绕回人工队列

即使不动打分，#3231 原文建议的落点（`reject` 分支前加 pre-check）**仍然达不到目的**：

```
reject → auto-rejected + needs-salvage
       → intake-salvage-digest.yml 每天 08:00 UTC 按 --label auto-rejected 捞取（:31-33）
       → 重新打上 needs-human-review（:105、:178）
```

正文里「天然不进人工队列」这句把 `reject` 当成了终点，而下游还有一个**每天主动把东西捞回
人工队列**的作业。守卫的真实效果是：占位符从「立刻进人工队列」变成「次日进人工队列 + 每天
一条 digest 噪音」，并制造一批在被捞和被 30 天自动关闭（`:130`）之间来回的 issue。

**比现状更糟。** 所以 owner 选了独立标签：占位符打 `auto-placeholder`，digest 的
`--label auto-rejected` 查询**天然看不见它**。

> 选标签而不是静默关闭的理由值得留着：静默关闭在真报料被误判时**没有回收路径**，而独立标签
> 只是让 digest 漏掉它 —— **漏掉不等于不可恢复**。

### 90.4 实现（PR #3239）与两次变异复验

`decision` 现在有第五个值 `placeholder`，分数原样保留（测试里断言 `weighted_score > 0` 且
`make_decision(...)` 仍能独立给出自己的判定）。两个锚点，都不是裸前缀匹配：

1. **所有 AC 值为 `test-*` 占位符**，且**要求小节存在且至少有一个值**。「所有值都匹配」在没有值
   时**恒为真**，而正常报料本来就可以没有 AC（`issue-quality-gate.yml:52-59` 明确把无 AC 当作
   「报料而非规格」豁免）。这条写错会拒掉全仓每一条无 AC 的报料。
2. **problem 段是单个 `test-*` token**，不是以 `test-` 开头。否则真报料会被吞掉。

变异复验（退回旧写法看是否变红）：

| 变异 | 结果 |
|---|---|
| 退回裸 `^test-` 前缀 | 1 条红（counterexample）✓ |
| 去掉「AC 非空」要求 | **13 条红**，含空真那一条 ✓ |

**90.4.1 我第一版的 counterexample 测试是装饰性的 —— 留档**

第一次变异跑完是**绿的**。原因：我的反例只有第一行以 `test-` 开头，而实现里是 `all(...)` 要求
**每行**都匹配，于是裸前缀根本不会误判，测试通过的理由和它声称的理由无关。

改成**每行都以 `test-` 开头**（`test-suite hangs on windows-latest` / `test-hang predates my
change`）之后，裸前缀才真的误判，测试才咬得住。

> **规则：反例测试必须让"退回旧写法"真的变红，否则它是装饰。** 而且要先跑变异再写"已验证"——
> 这次是变异跑绿了才发现反例选得不对。

#### 90.5.3 实验①：文件即成因（owner 批准的那一步）

上一轮记的实验阻塞是「要改 main 上的 workflow，推送会触发部署面」。**这个前提不成立** ——
既然每次 push 都跑，而 push 事件用的是**被推送 ref 上的文件副本**，就可以推到一次性分支上观测。

实验①（把 `guarded-repository.yml` 从分支上删掉，推 `probe/guarded-repository-absent`）：

| 分支 | 该文件在分支上 | 结果 |
|---|---|---|
| `probe/guarded-repository-absent`（`9dd1f1a2`）| **否** | **没有 guarded-repository run** |
| `main`（同一窗口）| 是 | 有 run，failure |

**结论：这些 jobs=0 的失败 run 就是这个文件产生的。** 分支已删。

这一下把整条"平台侧无关行为"的可能性排除掉了，**②③（减权限 / 删跨仓调用那一个作业）现在才真正
值得做** —— 但 owner 本轮只批了①，所以停在这里。
