## 67. 发布 PR 的 changelog 不是「等着就好」，它有三个实缺陷

上一阶段我记的是「等 changelog 重新生成再合」。隔夜复查，release-please **确实重跑了**（分支 `4aa56787` → `db65cfd3`），但产出是错的：

1. **本轮的课程合并（#3072）与 handoff（#3063 / #3065 / #3067 / #3075）全部不在 changelog 里。** 只 grep 到 `phase 4` 与 `phase 5`。`release-please-config.json` 的 `changelog-sections` 只配了 `feat` / `fix` / `docs` / `refactor` / `test` / `ci` —— **`lesson:` 和 `lessons:` 这两个 type 根本没配**，那六门课是被静默丢弃的，不是被归错类。
2. **同一个 commit 被写了两遍。** `9adcef7`（counters-d1 flake）出现两次，一次带 `closes #1648`、一次带 `([#3066])`，两条都指向同一 SHA。根因是我的 commit message 结尾 `Refs #1648` 与 PR 号同时存在，release-please 为两种引用各生成一条。
3. **仓库自带的去重修复步骤看不见它。** workflow 里有一步 `Drop the duplicate entries in the pending release section`，日志报 `CHANGELOG.md: no duplicate entries in the newest release section` —— **它检查的是已发布的文件，而重复在待发布的 PR 正文里**。检查对象错了，于是每次都报「无需修复」。

**结论：2.42.3 现在合下去，会发布一份缺了本轮全部课程与交接、且有一条重复项的 changelog。** 需要先补 `changelog-sections` 的 `lesson` type、修掉那条双引用、让去重步骤查 PR 正文而不是 CHANGELOG.md。这三件都超出「收尾」范围，未动。

## 71. §67 有两条根因是错的，这里更正

§67 说 2.42.3 的 changelog「缺 phase 7/8/9」且「去重步骤检查了错误的对象」。读完代码后：**第一条偏，第二条错。**

**偏的那条。** §67 写「`docs(handoff):` 配了 `docs` 却不出现，原因不明」。真实原因与 `docs` 无关：`release-please-config.json` 的 `changelog-sections` 只声明了 `feat` / `fix` / `docs` / `refactor` / `test` / `ci`，而 **`lesson:` 与 `lessons:` 这两个 type 根本没配**。自 v2.42.2 起 main 上有 **9 个**课程提交，changelog 里零条目。

**错的那条。** §67 写去重步骤「检查的是已发布文件，而重复在待发布的 PR 正文里。检查对象错了」。**它没有错。** 该步骤用 worktree 挂在 `origin/$BRANCH` 上，查的**就是**分支里那份待发布的 `CHANGELOG.md`。它报 `no duplicate entries` 的真实原因是 `normalise()` 只剥尾部那组括号（形如 `(#N…) (sha…)`，两段都是 Markdown 链接），剥不掉 `, closes [#1648]…` 这种**在括号组外面**的后缀，于是同一 commit 的两条渲染归一化后不相等。**它被指向了一个它认不出的形状，不是被指向了错误的对象。**

修在 #3118：补两个 type；`normalise()` 先剥 `(,|and) (closes|fixes|resolves|addresses) #N` 一类尾部引用。两条新测试用 2.42.3 的真实行，变异验证（退回旧解析器 → 恰好 2 红 / 共 20）。

**我在这里犯的第二个误判模式**：把「条目数在两次重生成后始终 29 条不变」读成「release-please 还没跑完」。**条目数不增长本身就是「被丢弃」的判据** —— 真的在重算，它必然增长。同 §57：把「我没看到变化」当成了「它还在工作」。

## 73. 第一性原理下的收口判据

这一阶段我用的判据很简单：**一个开放项的阻塞是什么，而不是它看起来像什么。**

- 外部服务抖动（`pr-genius` 的 HTTP 500）→ 重跑。
- 外部权限缺失（`pr-agent` 的 403）→ **重跑无效**，需要改权限或改检查语义，属于所有者的决定。
- 派生产物冲突 → 跑生成器，本地即可判定。
- 真实源码冲突 → 需要意图判断，所以去问提出者。

**这四条里只有第三条能靠我一个人做完。** 其余的要么等外部条件，要么等另一个人回答 —— 把它们混成「未决」记一笔，等于把三种性质完全不同的事塞进同一个抽屉。

### 75.2 为什么 phase 4 是个例外 —— 判据是 **PR** 的文件，不是 commit 的

phase 4 同样是 handoff-only commit，却**在** changelog 里。不一致是真的，解释得通，而且**只能从 release-please 源码确认**：

`src/github.ts:382` 把 `commit.files` 取自**关联 PR 的文件列表**，不是该 commit 自己的文件；`src/manifest.ts:706` 的 `excludeCommits()` 在生成 notes **之前**执行。于是判据是「这个 PR 的所有文件是否都落在排除路径下」。
