## 105. 顺手的发现：`deploy-freshness` 在"一切正常"时也会红

`check_deploy_freshness` 比的是 `commit_sha` 与 HEAD **完全相等**；而 `deploy-worker.yml` 只在
`workers/register-proxy-sw.js`、`workers/wrangler.toml` 变动时触发。两者一乘，结论是：
**任何一次 docs-only 落地都会把它弄红**，直到下一次 worker 改动。

实测（2026-10-18，部署成功之后）：

- 生产 `6699a3b5`，HEAD `fb95ea17`，相差 2 个提交——`a0bb02aa`（Quickstart 复制按钮）、`fb95ea17`（handoff），**都不碰 worker 路径**；
- `git log 6699a3b5..HEAD -- workers/register-proxy-sw.js workers/wrangler.toml` **为空** → 生产跑的正是最新的 worker 代码；
- 可 `python3 scripts/doctor.py --deploy-freshness` 仍然 ❌：`production runs 6699a3b5…, but this checkout is fb95ea17… — 2 commit(s) behind. The worker is stale; the deploy did not land. (#2779)`

`deploy-freshness.yml` 的 run 历史是同一个形状：部署完成那一刻 success，下一条 docs 提交之后 failure。

**候选修法（未做，留给下一轮决定）**：把比较基准从 HEAD 换成"HEAD 上最后一次触及 worker 触发路径的提交"
（`git log -1 --format=%H -- workers/register-proxy-sw.js workers/wrangler.toml`），并在
`tests/test_deploy_freshness.py` 里补一条"docs-only 提交不算落后"的用例。
门禁该抓的是**部署没落地**，不是**文档又写了一段**——#2779 的历史教训不能被换成另一种误报。

### 109.2 自动化的真实边界（逐个 workflow 看过）

- `intake-auto-review`：开单即跑，1–2 分钟/条，打标签 + 打分 + 评论。**只分类，不产出课程**。
- `done_but_open.py`（每日 08:00 UTC）：**只报告**"课程已在 main、issue 还开着"，不关单、不发回执。

**结论：不满足。** 分类能力绰绰有余（9.5 条/天 × 2 分钟远低于 cron 能力），**转化能力是 0**，所以积压线性增长，只能靠人隔几天清扫一次。

### 109.3 为什么"再加分类"不会提速

128 条有分数的 `needs-human-review` 里，**108 条落在 40–60 的"需要人看"区间**（≥75 只有 1 条，60–75 有 13 条）。
分类器的决策边界正好压在绝大多数样本上——它输出的是几乎恒定的"不确定"，人照样得逐条读。**加分类等于加噪音。**

## 110. 降级不能冒充"没有"（今天实测到的两条，已修）

两处"系统知道自己降级、但没告诉看它的人"的地方，都来自同一天的 D1 额度耗尽。

### 110.1 检索：`no_match` 不能再冒充"知识库没有"

`misakanet_search` 现在在降级时返回三个字段：`degraded: true`、`degraded_reasons`（`index_unavailable` / `corpus_snapshot`，可同时为真）、`notice`（一句话，明说"这是降级读取，不是没有这条课程"）。工具描述里也写明了，agent 读得到。

判据写进 `workers/search-degraded-notice.test.mjs`：健康态不带 `degraded`；只缺索引时只报 `index_unavailable` 且**不得**提快照；D1 拒绝读取后如实报 `corpus_snapshot`；两个都坏时两条都报；`resetLessonsReadState()` 后必须回到健康态（**降级态自己不清除，就是另一种谎**）。

### 110.2 安装器：说清是谁的问题

旧文案在注册失败时无条件说"多半是网络"。今天的实测是服务端 `{"code":"storage_unavailable","storage":{"token":true},"hint":"… Retry shortly."}`——网络是好的，用户会被指挥去重启路由器。

现在按服务端返回分流：`storage_unavailable` → "服务端暂时存不了 token（**不是你的网络**）"；其它 `code` → 点名；真的没有响应 → 保留网络判断并附上次的传输错误（`lastRequestError`）。服务端的 `hint` 原文带上。

判据：`workers/misakanet-setup-register-failure.test.mjs` 用真实 CLI + 假端点跑两条路径（服务端答 `storage_unavailable` / 端点不可达），断言各自说对、且不互相冒充。
