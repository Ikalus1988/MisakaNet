## 3. 本轮踩的坑

1. **版本门禁只挡"文档超前"，落后是静默的**（`align_versions.py` 的 R5）。`--source 2.30.0` 不动
   `API.md` / `JOIN.md`（那是 `--registry` 的职责），于是它们安静地落后两个版本，`--check` 仍然全绿。
2. **一条"违反词表"的句子能在词表测试下全绿**：正则少了连字符分支。**门禁的覆盖面比它的名字窄**——
   这是这个仓库第二次栽在同类问题上（第一次是 `{{LESSONS_COUNT}}` 一次性替换）。
3. **没被注册的句子 = 无人看守的漂移面**。README 的 Glama 段、JOIN 的 Version-Info 块都"在公开面上、
   有数字、没进 SSOT"，所以只能靠人偶然看见。
4. 本机 `npm` 必须 `--cache /tmp/...`（`$HOME` 只读，旧缓存里有 root 文件）。
5. **未认证的 GitHub API 很容易被限流**（本轮用它查 workflow 结论时连续返回空）——
   验证发布状态更可靠的办法是**直接查 registry**（`npm view` / `dist.shasum`）。
6. 本仓是 **shallow clone**：`git rev-parse --is-shallow-repository` = true，`git log --all` 看不到
   09-07 边界之前的主线历史（做历史取证时必须声明这一点）。
7. 外部评审这份"实测读代码"的报告里，**四条硬错全部来自"读到的不是 HEAD"**：gitignored 的
   `.pnpm-store` 快照、别人的示例文本、修复前的代码、历史报告。仓库侧的对策见 §4 第 1 条。

## 5. 教训（一句话版）

- **门禁的名字不等于它的覆盖面**：正则少一个分支、SSOT 少注册一句，都会让"绿"失去意义。
  修完要**回灌验证**（把漂移放回去，看它是否真的红）。
- **数字类表面要么进 SSOT，要么标快照日期**，否则它迟早被外部读者当成现状引用——本轮两份评审就是证据。
- **验证发布以 registry 为准**（`npm view … dist.shasum` 对本地 pack 的 shasum），不要只信 CI 的绿色。
- **"实测读代码"必须锚定 HEAD**：`git rev-parse --short HEAD` 写进结论里，才不会把快照当现状。

### 6.2 三个操作性新事实（都踩过）

1. **PR 的 `CodeQL` 检查是绿的，不代表告警关了。** #1688 合并后 #268 仍 open，实例被钉在合并提交上、行号从 167 变成 **177**——流向只是**换了一条**（我把版本改成读 `package.json`，而它进了 `User-Agent` 头）。**要判断告警是否消失，只能看合并提交（`refs/heads/main`）上的告警状态**，PR 检查只比"新增"。
2. **用 API 建的 tag 不会触发 `on: push: tags` 工作流**（`POST /git/refs` 返回 201，但 `misakanet-setup-publish.yml` 没有排队）。发布要么用 **git 推 tag**，要么用该工作流的 **`workflow_dispatch`**（它支持"手动发布当前版本"）。
3. **`scripts/gh_push_via_api.py` 只接受"分支 == base"**：它拒绝把一个已存在的 PR 分支往前推（`refusing to move …: it is at <sha>, not the base`）。要往已有的 PR 分支追加提交，只能用 git；git 不通时，**换一个新分支重开 PR 并注明取代关系**（本轮 #1689 → #1690 就是这么处理的）。

### 6.3 又一个"守护自己变成告警"

#1689 的 CodeQL 检查红在 **1 new alert (high)**：为"防止 #268 回来"写的那条测试用
`declared.replace(/\./g, '\\.')` 构造 RegExp——只转义点、不转义反斜杠，正是
`js/incomplete-sanitization`。改成子串比较（`includes`）后消失。
**守卫类改动的自检标准：它会失败吗？它自己会不会成为新的失败源？**

### 6.4 本地工具链的两个坑

- **不要把 `git fetch` 的结果接进管道再判 exit code**：`git fetch … | tail -1` 的退出码是 `tail` 的，
  于是"重试循环"每次都当成功 break——本轮因此以为本地 main 是新的，实际落后一整天。
- **本机 git 协议今天基本不可用**（`GnuTLS recv error (-110)` / 连接超时）：内容推送走
  `scripts/gh_push_via_api.py`，**状态与告警一律查 GitHub API**（`git fetch` 不可信时，
  `origin/main` 是陈旧引用）。

### 7.2 Hermes 的形状抄自它自己

`hermes_cli/mcp_config.py` 里 `_env_key_for_server()` = `f"MCP_{name.upper().replace('-','_')}_API_KEY"`，token 写 dotenv、配置里只留 `${…}` 模板。所以安装器写的两份文件与 `hermes mcp add --auth header` 完全一致 —— 只是**没有起子进程**（token 不进 argv）。YAML 是文本手术（本包零依赖是发布门禁），用注释标记定界，并会**替换** `hermes mcp add` 早先写过的条目而不是写重复键。

### 7.3 ⚠️ 最关键的一条：注册正确 ≠ 能连上

`hermes mcp list` 显示 `misakanet … ✓ enabled` 之后，`hermes mcp test misakanet` 却是：

```
✗ Connection failed (10447ms): Client error '400 Bad Request' for url 'https://misakanet.org/mcp'
```

用**本地监听器**把客户端真实握手抓下来才看清：Hermes 的 `mcp` SDK 0.1.0 序列是
`HEAD /mcp` → `POST initialize`（**`MCP-Protocol-Version: 2025-11-25`**）→ `notifications/initialized` → `tools/list`。
而 worker 对任何不在 `SUPPORTED_PROTOCOL_VERSIONS` 里的 header 值**直接 400** —— 尽管它本来就在
`initialize` 结果里做版本协商（**两半自相矛盾**）。按 MCP 规范，客户端提出未实现的版本属于**协商**，
答案在 `initialize` 结果里。结果是：**任何用较新 SDK 的客户端都连不上，且只看到一句 400**。

修完线上复验：`2025-11-25` → **200**（协商到 `2025-06-18`），`hermes mcp test misakanet` →
**✓ Connected (2761ms) · ✓ Tools discovered: 7`。

**教训**：验证一个集成时，"配置文件写对了"和"它真的能用"之间隔着一个握手。**抓客户端的真实请求**
（本地监听器 + 把目标指向它）比读双方文档快得多，也才找到那句被 SDK 吞掉的 400。
