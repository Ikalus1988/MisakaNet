## 5. 教训（一句话版）

- **门禁的名字不等于它的覆盖面**：正则少一个分支、SSOT 少注册一句，都会让"绿"失去意义。
  修完要**回灌验证**（把漂移放回去，看它是否真的红）。
- **数字类表面要么进 SSOT，要么标快照日期**，否则它迟早被外部读者当成现状引用——本轮两份评审就是证据。
- **验证发布以 registry 为准**（`npm view … dist.shasum` 对本地 pack 的 shasum），不要只信 CI 的绿色。
- **"实测读代码"必须锚定 HEAD**：`git rev-parse --short HEAD` 写进结论里，才不会把快照当现状。

### 6.2 三个操作性新事实（都踩过）

1. **PR 的 `CodeQL` 检查是绿的，不代表告警关了。** #1688 合并后 #268 仍 open，实例被钉在合并提交上、行号从 167 变成 **177**——流向只是**换了一条**（我把版本改成读 `package.json`，而它进了 `User-Agent` 头）。**要判断告警是否消失，只能看合并提交（`refs/heads/main`）上的告警状态**，PR 检查只比"新增"。
2. **用 API 建的 tag 不会触发 `on: push: tags` 工作流**（`POST /git/refs` 返回 201，但 `misakanet-setup-publish.yml` 没有排队）。发布要么用 **git 推 tag**，要么用该工作流的 **`workflow_dispatch`**（它支持"手动发布当前版本"）。
3. **`scripts/gh_push_via_api.py` 只接受"分支 == base"**：它拒绝把一个已存在的 PR 分支往前推（`refusing to move …: it is at <sha>, not the base`）。要往已有的 PR 分支追加提交，只能用 git；git 不通时，**换一个新分支重开 PR 并注明取代关系**（本轮 #1689 → #1690 就是这么处理的）。

### 6.3 又一个"守护自己变成告警"

#1689 的 CodeQL 检查红在 **1 new alert (high)**：为"防止 #268 回来"写的那条测试用
`declared.replace(/\./g, '\\.')` 构造 RegExp——只转义点、不转义反斜杠，正是
`js/incomplete-sanitization`。改成子串比较（`includes`）后消失。
**守卫类改动的自检标准：它会失败吗？它自己会不会成为新的失败源？**

### 6.4 本地工具链的两个坑

- **不要把 `git fetch` 的结果接进管道再判 exit code**：`git fetch … | tail -1` 的退出码是 `tail` 的，
  于是"重试循环"每次都当成功 break——本轮因此以为本地 main 是新的，实际落后一整天。
- **本机 git 协议今天基本不可用**（`GnuTLS recv error (-110)` / 连接超时）：内容推送走
  `scripts/gh_push_via_api.py`，**状态与告警一律查 GitHub API**（`git fetch` 不可信时，
  `origin/main` 是陈旧引用）。

### 7.2 Hermes 的形状抄自它自己

`hermes_cli/mcp_config.py` 里 `_env_key_for_server()` = `f"MCP_{name.upper().replace('-','_')}_API_KEY"`，token 写 dotenv、配置里只留 `${…}` 模板。所以安装器写的两份文件与 `hermes mcp add --auth header` 完全一致 —— 只是**没有起子进程**（token 不进 argv）。YAML 是文本手术（本包零依赖是发布门禁），用注释标记定界，并会**替换** `hermes mcp add` 早先写过的条目而不是写重复键。

### 7.3 ⚠️ 最关键的一条：注册正确 ≠ 能连上

`hermes mcp list` 显示 `misakanet … ✓ enabled` 之后，`hermes mcp test misakanet` 却是：

```
✗ Connection failed (10447ms): Client error '400 Bad Request' for url 'https://misakanet.org/mcp'
```

用**本地监听器**把客户端真实握手抓下来才看清：Hermes 的 `mcp` SDK 0.1.0 序列是
`HEAD /mcp` → `POST initialize`（**`MCP-Protocol-Version: 2025-11-25`**）→ `notifications/initialized` → `tools/list`。
而 worker 对任何不在 `SUPPORTED_PROTOCOL_VERSIONS` 里的 header 值**直接 400** —— 尽管它本来就在
`initialize` 结果里做版本协商（**两半自相矛盾**）。按 MCP 规范，客户端提出未实现的版本属于**协商**，
答案在 `initialize` 结果里。结果是：**任何用较新 SDK 的客户端都连不上，且只看到一句 400**。

修完线上复验：`2025-11-25` → **200**（协商到 `2025-06-18`），`hermes mcp test misakanet` →
**✓ Connected (2761ms) · ✓ Tools discovered: 7`。

**教训**：验证一个集成时，"配置文件写对了"和"它真的能用"之间隔着一个握手。**抓客户端的真实请求**
（本地监听器 + 把目标指向它）比读双方文档快得多，也才找到那句被 SDK 吞掉的 400。

### 8.2 ⚠️ 险情：本机 `origin/main` 静默落后一整天，差点把已合并的内容推回去

**经过**：本机到 github.com 的 git 协议长期不可用，`git fetch` 一直失败——但我的"重试循环"写成
`git fetch … | tail -1`，**管道退出码是 `tail` 的**，于是每次都当成功 break。结果是本地 `origin/main`
停在一天前。随后我用 `git checkout -B <branch> origin/main` 建分支做新工作，**把这一天里已合并的
12 个文件在本地整体回退**（其中 `scripts/node_status.py` 退回 PR 前的版本、`tests/test_node_status.py`
直接消失）。因为这些文件与我当时在改的东西无关，`git status` 只显示我有意改的那几个——**本地看起来
完全正常**。

**是怎么被抓到的**：跑本地门禁时 `tests/test_node_status.py` 出现 5 个失败（镜像函数不见了）。

**怎么一次查清**：不再逐个猜，改用 **API 树全量对照**——

```python
tree = GET /repos/{owner}/{repo}/git/trees/main?recursive=1      # 1997 个 blob 的 path→sha
# 对每个 path 算 git blob 哈希：sha1(b"blob %d\0" % len(data) + data)，与 tree 里的 sha 比
```

一次跑出：**缺失 0、内容不同 12**（全部是那次回退造成的，与我本轮改动无关），逐个从 main 取回后复验
**偏差 0**。

**结论（写进流程）**：
1. **判 exit code 不要接管道**；`git fetch` 失败要当场看见。
2. **git 协议不可用时，`origin/main` 是陈旧引用，不能当基线**：建分支/推送前用上面那段 API 树对照，
   再动手。
3. 本地测试全绿 ≠ 本地树是新的——**门禁只能发现"被回退到坏状态"的文件，发现不了"被回退到旧但仍自洽"的文件**。
   这次是运气好：旧 `node_status.py` 与恢复后的新测试直接冲突，才炸出来。

### 10.2 唯一异常：hermes 的 `no_match`，而我把原因解释错了

同一个查询，只改 `domain`：不传 → 3 命中；`domain="python"` → **0**；`domain="contrib"` → **3**；
`domain="devops"` → 0。当时的结论是"过滤参数用的是索引里的目录名而非 frontmatter domain"，
据此立了 **#1725**，并在 `AGENTS.md` §3.2 写了"照 frontmatter 填会 no_match，不确定就省略 domain"。

**这个解释只对了一半，而且不是重点。** 继续往下挖（本轮最有价值的一段）：

- 远端检索结果里 **title 是文件名 slug**、`domain` 是目录名（`pt-br` / `contrib`）；
- `/api/lessons` 查 D1：`domain=contrib` ≥50 行、`ops` 22、`core` 10，而 `python` 只有 1、`devops` 2；
- **D1 行本身**就是 slug + 目录名 —— 不是过滤器的词表问题；
- **已提交的 `data/lessons.json`** 同样如此（YAML 课程 title=slug、domain=`contrib`、tags=`[]`）；
- 把样本按 frontmatter 风格切开：**5/5 YAML 课程降级**，JSON 课程正常（2/3，另一篇另见下）；
- 本机（有 PyYAML）跑 `sync_lessons_to_d1.py` 对同样两篇输出的是**正确**标题与 `python`。

**根因**：`parse_frontmatter()` 的 YAML 兜底把 `import yaml` 失败**静默吞掉**并返回 `{}`
（`scripts/update_lessons_json.py`、`scripts/sync_lessons_to_d1.py` 各一份），而跑这两个脚本的
workflow **都没装 Python 依赖**（`update-lessons.yml` 只 setup-python；`sync-d1.yml` 只装 wrangler）。
仓库里 **370/434 篇是 YAML frontmatter** —— 于是 `title=文件名`、`domain=父目录名`、`tags=[]`、
`language` 一律 `en`，写进了公开索引和 D1。立案 **#1726**。

**影响面远大于 #1725**：检索结果标题全是 slug（每次调用都给用户看文件名）、domain 过滤按目录名匹配、
tag 过滤与加权失效、status/language/summary/created/updated 全是兜底值。

**#1725 的归宿**：等数据修好并重新同步后，按文档填 frontmatter domain 就会正常命中 —— 它是这个数据缺陷的
**症状**，不是独立的词表缺陷。`AGENTS.md` §3.2 那段"止血"说明届时必须改写（否则会把已经修好的行为说成坏的）。

### 10.3 顺带查出的两处语料缺陷

1. **3 篇 frontmatter 无法解析**（连 PyYAML 也报 `ScannerError`）：
   `ci-test-coverage-gate.md`、`ci-workflow-fail-fast-matrix.md`、`import-path-verification-after-refactor.md`
   —— 一个 `---` 块里先写了 YAML 键值、又贴了整个 JSON 对象（一次"元数据归一化"留下的坏账）。
   这类文件**任何环境都会降级**。
2. **39 篇课程的 `domain` 就是 `contrib`**（占 393 篇的 10%）—— 目录名被当成主题。它们的实际主题五花八门：
   `sovits`/`ffmpeg`/`cron`/`disk`/`json`/`gateway`/`chroma`… 于是这 39 篇按 domain 根本找不到，
   而且把 `contrib` 当成了一个"领域"计入公开计数。这条正好是 **#1687 词表那一半**的硬证据。

### 10.4 教训

- **静默兜底会把一个环境缺陷变成长期错误数据**：`except Exception: pass` + `or dir_name` 让 CI 的
  缺依赖表现成"语料元数据不好"，没人会去怀疑 CI。修法不是补一行 `pip install` 就完事 ——
  要让**缺依赖时报错**，并加一条"跑需要 pyyaml 的脚本就必须装依赖"的守卫测试。
- **线上现象的第一个解释可能是错的**：`domain` 过滤不命中，看起来像词表/文档问题（我一开始也是这么写的），
  实际是数据列被写坏了。**先查数据本身，再改语义**。
- **抽查样本要按"结构"分层**：JSON/YAML 两种 frontmatter 混在同一语料里，正是它们把缺陷切成了两半 ——
  也正因为有这 63 篇 JSON 课程没坏，线上才看起来"大体正常"。

### 三轮下来的共同教训

三件事（#1675 的第二层、#1731 的缓存、#1687 的校验器）都是**同一个形状**：
"我们以为的输入/来源"，与**线上返回的东西**不一致。共同修法是：从返回对象反推来源
（`problem` 的前缀、索引里记录的 stamp、校验器对同一段 frontmatter 的解析结果），而不是相信调用链的意图。
