## 3. 本轮踩的坑

1. **版本门禁只挡"文档超前"，落后是静默的**（`align_versions.py` 的 R5）。`--source 2.30.0` 不动
   `API.md` / `JOIN.md`（那是 `--registry` 的职责），于是它们安静地落后两个版本，`--check` 仍然全绿。
2. **一条"违反词表"的句子能在词表测试下全绿**：正则少了连字符分支。**门禁的覆盖面比它的名字窄**——
   这是这个仓库第二次栽在同类问题上（第一次是 `{{LESSONS_COUNT}}` 一次性替换）。
3. **没被注册的句子 = 无人看守的漂移面**。README 的 Glama 段、JOIN 的 Version-Info 块都"在公开面上、
   有数字、没进 SSOT"，所以只能靠人偶然看见。
4. 本机 `npm` 必须 `--cache /tmp/...`（`$HOME` 只读，旧缓存里有 root 文件）。
5. **未认证的 GitHub API 很容易被限流**（本轮用它查 workflow 结论时连续返回空）——
   验证发布状态更可靠的办法是**直接查 registry**（`npm view` / `dist.shasum`）。
6. 本仓是 **shallow clone**：`git rev-parse --is-shallow-repository` = true，`git log --all` 看不到
   09-07 边界之前的主线历史（做历史取证时必须声明这一点）。
7. 外部评审这份"实测读代码"的报告里，**四条硬错全部来自"读到的不是 HEAD"**：gitignored 的
   `.pnpm-store` 快照、别人的示例文本、修复前的代码、历史报告。仓库侧的对策见 §4 第 1 条。

## 5. 教训（一句话版）

- **门禁的名字不等于它的覆盖面**：正则少一个分支、SSOT 少注册一句，都会让"绿"失去意义。
  修完要**回灌验证**（把漂移放回去，看它是否真的红）。
- **数字类表面要么进 SSOT，要么标快照日期**，否则它迟早被外部读者当成现状引用——本轮两份评审就是证据。
- **验证发布以 registry 为准**（`npm view … dist.shasum` 对本地 pack 的 shasum），不要只信 CI 的绿色。
- **"实测读代码"必须锚定 HEAD**：`git rev-parse --short HEAD` 写进结论里，才不会把快照当现状。
