## 4. 这轮学到的两个边界

1. **`format` 维度对 issue 是结构性不可得的。** 44/44 的拒绝理由都含 `No frontmatter` 与 `No code blocks`——
   intake 是 GitHub issue，本来就没有 frontmatter。40 分门槛实际由其余五维支撑。**是否给 issue 面单独的
   format 口径，需要先测量**（改成不扣 frontmatter 后，多少条会越过 40），不要凭直觉改。
2. **`me_inbox` 的两条查找路径不等价。** 按 `dedup_key` 查的是**提交时**的哈希；按 `intake_id=issue-N`
   查的是 `issue_number`。当行是由 sync 从**正文重算**哈希写入时（非 question 的 intake 没有 pending 行），
   只有 issue-id 路径可靠——这一条写进这里，免得下次又用错键。

### 8.2 空标题的分数漏洞（#4455）

`score_verification` 把「有 `## Verification` 标题」当成有验证：空标题也能拿 +20 基础分，再叠加全正文的
`expected|output|result` 与列表加分。实测在 44 条开放 auto-rejected 上，**加一个空标题**让 33 条平均 +6.9
（最多 +13.0），10 条越过 40 分线，正文一个字没改。

修法同 #4427 的 `## Problem`：先用 `sections` / `_section_text` 读**内容**，`has_verification = bool(content.strip())`；
空节落入既有的 inline-evidence 分支。修复后实测（当时 21 条开放）：最大 **+2.0**（format 维度仍把标题算结构），
**0 条翻越 40**。PR **#4506**，3 个回归测试。

### 8.3 答案通知邮件（可选、先确认再发）

最小闭环，用 Cloudflare Email Sending（`send_email` 绑定，账户限额 200 封/天）：

| 环节 | 行为 |
|---|---|
| 提交 | `submit_intake(kind="question", notify_email=…)`——**可选**，agent 先问用户；hosted 与 stdio 两个 schema 都加（parity 门禁比较），stdio 转发 |
| 存储 | `notify:<dedup>` = `{email, token, issue_url, state:pending}`，7 天；token 单独索引 |
| 确认 | 发**一封**中性确认信（不含问题正文）→ `GET /api/notify/confirm?t=…` 标记 confirmed 并烧掉 token |
| 通知 | **每 15 分钟** cron 扫最近两天 answered 的 `questions`（一条带索引的查询）→ 每个 confirmed 记录发**一封**（只含 issue 链接）→ **删除地址** |
| 降级 | 绑定缺失/发送失败都不影响 intake；未确认的 7 天过期 |

`Confirmed. We will email you once, when the answer is ready.` → 回答问题并同步 → **00:01 收到通知**
（主题 `Your MisakaNet question was answered`，正文只有 issue 链接）。测试问题 #4514 已关。
