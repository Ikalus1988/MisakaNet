## 1. 现状：三件"没人看所以一直坏"的事

### 1.1 一个每天在跑的 workflow，连续 4 天失败，无人发现（今天修完）

`Intake Salvage Digest`（每日 08:00 UTC）自 **≤2026-09-09** 起每天失败。排查后发现有**三层 bug 叠在一起**，
每一层都只在上一层被修掉后才露出来：

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 1 | `gh` 没有 token | `exit code 4` | 只声明了 `permissions: issues: write`（**不会**把 token 放进环境），仓库里其它用 `gh` 的 workflow 全都显式 `env: GH_TOKEN` |
| 2 | `$(date -u +%Y-%m-%d %H:%M UTC)` 未加引号 | `date: extra operand '%H:%M'`，`exit 1` | 空格让 `%H:%M` 成为第二个操作数；步骤在 `bash -e` 下直接中止 |
| 3 | 双引号里的反引号 | ``/salvage-review: No such file or directory``，`exit 127` | `` `/salvage-review` `` 被当作**命令替换**执行；同一坑还静默吃掉了 `` `## Error` ``/`` `## Verification` `` 两段文案 |

**代价是"载荷性"的**：这个 job 的存在意义就是把 auto-rejected 的 intake 送到人眼前。它 4 天没跑，
于是 salvage 队列（4 条）一直躺着没人处理——而 Actions 列表里只多了一条"每日计划任务失败"，
在几十条绿色里读起来像噪声。

**教训**：仓库里**没有任何测试**覆盖 workflow 的 shell 脚本。YAML lint、pin 检查、diff review 都抓不到这三条。
修完之后补了 `tests/test_salvage_digest_script.py`：把该 step 从 workflow 里抽出来、替换 `${{ … }}`、
用 stub `gh` 在 `bash -e` 下跑一遍（0.2 秒）。三处 bug 任意放回都会红（3/3/1 例失败）。
线上核验：手动 `workflow_dispatch` → 首个绿色 run（`828707962`），并生成摘要 **#1639**。

## 2. 评审策略：按"能抓到什么"分层，而不是按"谁写的"

### Tier 0 — 已在跑，保持（机械门禁）

DCO、pytest、worker 套件、计数/页面/版本门禁、SARIF（现在 0 开放告警）、action pin 检查。
它们的边界是**"能写成断言的"**：能证明"代码符合某条规则"，不能证明"某个东西真的在运行"。

### Tier 1 — 补上"可执行表面"（今天新增的类别，性价比最高）

> 判据：**"绿"不等于"在跑"。**

1. **把 workflow 的 step 变成可在本地跑的测试**：凡是 workflow 里带 `run: |` 的关键脚本，
   抽出来 + stub 掉外部命令 + `bash -e` 跑一遍。今天已落地一例（salvage digest）；
   建议下一步做成通用检查（`scripts/check_workflow_scripts.py`），覆盖 `update-lessons`、`register`、
   `issue-quality-gate` 等每日/每 PR 跑的脚本。
2. **把外部平台状态变成"声明 + 定期核对"**：dsh.so / DSH STORE 的裁决、
   `registry/candidates.json` 的 `latestCommit`/`status`、registry 的 `isLatest`。
   今天就是因为"钉在修复前的 commit"而不自知。
3. **每周一次"看不见的表面"巡检**（产出 3 行结论即可）：
   ① 所有 `schedule` workflow 最近一次结论（今天证明它们会静默失败）；
   ② 开放告警数（code-scanning / Dependabot）；
   ③ 外部平台状态是否与仓库声明一致。

### Tier 2 — 信任语义的**独立**复核（最高价值，必须"不是作者"）

凡改动**"什么被自动接受 / 拒绝 / 展示"**的东西，都要一个没有作者包袱的人过一遍。今天属于这一类的三处：

| 改动 | 决定什么 | 为什么必须独立复核 |
|---|---|---|
| intake 评分（`intake_auto_review.py`） | 什么被 auto-reject（= 什么永远进不了人眼） | 阈值直接决定"真盲区是否被挡在门外"；今天的修复正是一次假阳性事故 |
| 检索相关性下限 + `no_match` | agent 看到什么、看不到什么 | 静默的假阴性不会有人报错，只会让人不再用 |
| release 版本不变量 + `release-please` 接线 | 能不能发版 | 今天的实例：一条不变量让发布 PR 变红了一整天 |

**评审方式建议：对抗式复核（adversarial review）**，要求复核对每个改动给出三样东西：
一个假阴性用例、一个假阳性用例、一条"修了但没生效"的路径（缓存/门条件/触发时机）。
具体做法：给复核者 **diff + 测试 + 线上可观测点**，但不给"我认为它怎么工作"的说明，避免复述我的理解。
（`subagent` 可实现：它没有本次会话的上下文，正好充当"只读代码"的复核者。）

### Tier 3 — 贡献者侧评审：按"卡住别人的程度"排队

1. **一句话解围**：#1634/#1616/#1617 的作者缺 `Signed-off-by` → 留评论给命令；
2. **止住重复劳动**：#1528 的四份实现选一（按质量/完整性），其余明确关闭并致谢；
3. **内容复核**：#1633 按 `intake-triage.md` 的课程清单过一遍（结构、证据分级、验证段可跑）；
4. **批量 triage**：以 #1639 摘要为入口处理 4 条 salvage；#1635 补 AC。

### Tier 4 — 我自己的动作纪律（成本最低，今天已踩两次）

- 改 workflow / 门禁类文件后，**先跑本地对应测试再 push**（今天我 push 了坏 YAML，靠 422 才发现）；
- 新增一条不变量时，**先回答"谁在写这个事实"**（§12 已写进残余风险）——
  发布了不变量却没接上"写入者"，第一个撞上的就是发布 PR。

## 3. 赏金 issue：要发，但只发"可判定"的，并先做防重复

### 3.1 先看现有赏金教了我们什么

bounty #1528 引来了 **4 份实现（3 位作者）**。这不是作者的问题，是**赏金设计**的问题：

- 规格不够"可判定"（"给贡献者回执"有太多合理解释）→ 各人按自己的理解实现，无法比较；
- 没有认领机制 → 三个人并行开工，谁也不知道别人在做。

### 3.2 建议的赏金规则（下次发之前先定）

1. **可判定验收**：issue 里给出"跑什么命令、看什么输出、什么算通过"，像今天的新测试那样可复现；
2. **一人一实现**：用 Opire 的 `/try` 认领，并在 issue 顶部维护"当前认领人"；
   认领后 7 天无 push 视为释放；
3. **先 spec 后实现**（针对中等复杂度）：先用一条"方案评论"征集（不付赏金或小额），
   选定方案后再发实现赏金——避免四份并存；
4. **不发给需要领域判断或涉及信任语义的**：salvage 课程化、检索下限标定、页面 URL 策略、E0→E2 证据升级。

### 3.3 具体候选（按"值不值"排序）

| 候选 | 为什么适合赏金 | 验收方式 |
|---|---|---|
| **`scripts/check_workflow_scripts.py`**：把"workflow 里的关键脚本能在本地跑"变成通用检查 | 规格明确、纯机械、正是今天暴露的缺口 | 新测试对每个含 `run:` 的 workflow 做静态+可执行检查；把三处 bug 放回会红 |

### ⑤ 这一步学到的两条（已写进 §1 与本节）

1. **只看 CI 状态无法识别刷单**：占位 PR 的 CI 只是 `dco` 红，看起来和"忘了签核的正常 PR"一样；**必须打开 diff 看内容**。
