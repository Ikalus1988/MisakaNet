## 3. 可复用的判据

1. **提取器的失败模式永远是"返回空"，而空看起来就是干净。** 面检查（intake 与课程门禁）在一个小门禁上
   暴露了三个缺陷，只有一个响：挂错分支（大声失败）、字段没接上（安静）、正则吃掉后一个词（安静报"干净"）。
   凡是"返回列表"的检查，必须能把 `null`（没查成）和 `[]`（查过没问题）分开。
2. **答案键要读 base ref。** 词表由语料生成，所以加课的 PR 会把**自己的词**写进答案键——`mico` 会因为
   那篇需要检查的课说了它而变成"已知"。读 base 的副本，问的才是"语料**此前**认不认识这个词"。
3. **假阳性率决定了门禁的形状。** 课程门禁第一版扫每个代码块和每个行内 code，651 篇里 **182 篇（28%）**
   被红——绝大多数是因为**写了代码**（`case1`、`normalizerow`、`conftest.py`）。逐层收紧到 **1 篇（0.15%）**：
   只认声明了 shell 方言的代码块、行内 span 必须有参数、词表加上课程正文、文件名过滤。
4. **测试里写死版本号 = 发版永远绿不了。** `cli-contract.js` 断言 `--version` 是 `0.3.0`，
   release-please 一 bump 到 0.3.1，包自己的测试就把自己的 release 挂了（#4014）。而且这是个循环死锁：
   gate 只在被它挡住的事情发生之后才放行（与 #3755 同形）。
5. **算"跳过/缺失"和算"失败"必须分开。** bench 把重试用尽算成 miss，同一个 commit 三次读数
   15/14/12；改成剔除后三次**逐字节相同**。探针历史上也吃过同一亏（64 条里 20 条空 body 曾读成 -31%）。
6. **加包进 release-please 有顺序。** 门禁断言"base 账本覆盖每个已声明的包"，所以**先登记账本、再声明配置**，
   两次 PR。顺序是门禁定的，不是人定的。
