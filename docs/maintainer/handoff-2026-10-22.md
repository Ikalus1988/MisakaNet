## 125. 弹窗的焦点管理与可访问名的 i18n（2026-10-22）

§124.9 记的待办里有一条是这么写的：

> 弹窗**不移动/归还焦点**（抽屉的 `setDrawer` 有这个机制）；打开按钮没有 `aria-expanded`；
> `aria-label` 没有 `data-i18n-aria` 机制（中文模式读英文）。

这一条就是本卷。做的过程中**先量底再动手**，量出来的三件事都跟"照抄抽屉"这句话对不上——
照抄不够，得先知道抄的是什么。

### 125.1 弹窗的 DOM 不是 `<body>` 的直接子层（这是第一个坑）

实测 DOM 路径（Chromium）：

```
body > div#app.container > main#main-content > div#onboarding-modal.modal-overlay
```

`aria-modal="true"` 要求背景不可用。第一版按直觉写"把 `body` 的直接子层设成 inert"——
**这会把弹窗自己一起 inert 掉**：`.container` 是弹窗的**祖先**，container 一 inert，
`inert` 会沿着祖先链生效，弹窗也就收不到焦点。实测第一版的症状是：点了 `?`，弹窗开了，
焦点**不在弹窗里**。

改法：**从弹窗往上逐层**把兄弟节点设成 inert（每一层的兄弟里，跳过弹窗自身那一支）。
实测 inert 分布（弹窗打开时）：

| 元素 | inert | 说明 |
|---|---|---|
| `header` / `footer` | ✅ | container 的子层，弹窗的堂兄弟 |
| `.nav-toggle` / `.drawer-overlay` | ✅ | body 的子层 |
| `nav#drawer` | ✅ | **本来就是 inert**（`setDrawer` 的设计），不是本轮设的 |
| `main` / `.container` | ❌ | 弹窗的祖先，**不能** inert |
| `#onboarding-modal` | ❌ | 弹窗自己 |

### 125.2 焦点顺序反了，焦点会被拽回 `<body>`（第二个坑）

第一版是"先设 inert，再移焦点"。**顺序反了**：一个元素刚被设成 inert，浏览器就会把落在它
上面的焦点拿走，落到 `<body>` 上。于是实测症状是：焦点到了 `<body>`，弹窗里什么都没有。

正确顺序：**先把焦点移进弹窗，再把背景设成 inert**；关闭时**反过来**——先把背景解禁，
再把焦点还回去，否则焦点无处可落。

### 125.3 `inert` 挡不住 Tab 走出弹窗（第三个坑，量底才发现）

`inert` 把背景移出了 tab 顺序，**但 Tab 仍然会走出弹窗的末尾**——走到浏览器自己的 chrome，
此时 `document.activeElement` 变成 `<body>`。实测（改之前）：

```
Tab×4 → in, in, in, in   （弹窗里 4 个可聚焦元素：关闭键 + 3 个链接）
Tab   → BODY             ← 焦点离开弹窗
Tab   → in               （下一个 Tab 才回来）
```

`aria-modal="true"` 与 ARIA Authoring Practices 都要求"弹窗打开期间焦点不离开弹窗"，
所以补了一个环绕：最后一个元素把焦点交给第一个，第一个交给最后一个（Shift+Tab 反向同理）。
改后实测 12 次 Tab 与 6 次 Shift+Tab **全部停在弹窗内**。

### 125.4 做法：抄抽屉的机制，但不抄它的范围

`setDrawer` 是同一份文件里已有的、正确的样板：打开移入焦点、关闭归还焦点、Escape 同样处理。
本轮把它搬给弹窗，**没有引焦点陷阱库**（仓库不新增依赖）。

但**多抄了一样抽屉没有的东西**：抽屉关着时是 `left: -300px` 移出屏幕，
所以它需要 `inert` 把 17 个不可见的链接移出 tab 顺序；弹窗关着时是 `display:none`，
本来就不在 tab 顺序里——**弹窗需要的是"打开时把背景移出去"，抽屉需要的是"关着时把自己藏起来"**。
方向相反，所以没照抄 `drawer.inert = !open` 那一行。

**另一个必须抄对的细节**：只记录**原本就不 inert** 的元素。抽屉关着时本来就是 inert 的，
如果把"已经 inert 的"也记进账本，关闭弹窗时会把抽屉解禁——**抽屉那 17 个链接就回来了**。
实测：关闭弹窗后 `nav#drawer.inert === true`、`.nav-toggle.inert === false`（后者应恢复）。

### 125.5 i18n：`data-i18n` 够不到属性，这是机制问题不是文案问题

页面的翻译机制有三条：`data-i18n`（换 `textContent`）、`data-i18n-placeholder`（换属性）。
`data-i18n` 换的是 `textContent`，**够不到 `aria-label`**——于是关闭键的名字是一个写死的
英文串，中文模式下的读屏用户听到的是 "Close"。

本轮加了两个同款扩展（不是新机制，是 `data-i18n-placeholder` 的兄弟）：

| 属性 | 作用 | 用在哪 |
|---|---|---|
| `data-i18n-aria` | 换 `aria-label` | 关闭键、`?` 触发器 |
| `data-i18n-title` | 换 `title`（tooltip） | `?` 触发器 |

词表加了 `modalClose`（"Close" / "关闭"）。`?` 触发器直接复用已有的 `modalWhatTitle`。

**实测**（Chromium，真实切换语言）：

| | 英文 | 中文 |
|---|---|---|
| 关闭键 `aria-label` | `Close` | `关闭` |
| 触发器 `aria-label` | `What is MisakaNet?` | `什么是御坂网络？` |
| 触发器 `title` | `What is MisakaNet?` | `什么是御坂网络？` |

### 125.6 顺带修掉的：Cmd+K 从弹窗背后触发

背景 inert 之后，`#search-input` 也在 inert 里，于是 `input.focus()` **是个空操作**
（inert 元素不能被聚焦）。但 Cmd+K 的处理器照样把搜索框的边框闪了一下——
**看起来像有反应，焦点其实一步没动**。这是本轮改动引入的副作用，所以一并修掉：
弹窗打开时 Cmd+K 直接返回。

实测（先等定时器落定，排除干扰）：弹窗打开时边框 `currentcolor → currentcolor`（不闪）、
焦点留在弹窗内、搜索框没被聚焦；**关掉弹窗后 Cmd+K 照常聚焦搜索框并闪边框**（无回归）。

### 125.8 像素：0 差异，但门禁在容差 0 下会**偶发**红，原因与改动无关

基线 `b05cffb9` 的独立 worktree（`/tmp/px-base`）与本分支各采一遍（17 页 × 3 视口），
逐页比对：**容差 3 下全部页面 0 差异**（容差 3 是工具自带的 Chromium 抖动容差）。

容差 0 下有一页不为 0：`insights/reputation-leaderboard` 差 **20 像素 / 1,024,000（0.0020%）**，
分类 "recolour"，差异区域是 8×8 的小色块、通道只差 1 级（`[30,35,43]→[31,36,44]`）。

**第一版归因是错的，这里更正。** 当时写的是"那页 `fetch('/api/insights/reputation-leaderboard',
{ cache: 'no-store' })` 拿的是实时数据，所以像素天生不可复现"。**不成立**：采集时站点是由本地
静态服务器伺服，那个 URL 返回 **404**，`response.json()` 抛异常被 `catch` 掉，页面渲染的是
**固定的一句** "Could not load the leaderboard. Try again later."——内容是确定的，
`render(data)` 根本没跑到（`new Date(data.updatedAt)` 那行在 `render` 里）。

**实测出来的真因是 Chromium 的文字渲染抖动。** 同一份**基线代码**、同一页、连续采 4 遍：

| 对 | 差异像素 |
|---|---|
| run1 vs run2 | **20** |
| run2 vs run3 | **20** |
| run3 vs run4 | 0 |
| run1 vs run4 | 0 |

**同一份代码连着采两遍就能差 20 像素**，而且不是每次都差——所以它是**运行间**的抖动，不是随时间
变化的量。把差异区域裁出来看：两块图**肉眼完全一样**，差别在标题文字的抗锯齿子像素上
（通道值只差 1 级）。工具的 docstring 里其实已经写了这件事（"Chromium dithers gradients,
which moves a handful of pixels by ±2 between runs; `--tolerance 3` leaves that noise out of
the verdict"）——**但 `--tolerance` 的默认值是 0**，所以按默认参数跑，任何一页都可能偶发红。

### 125.9 还没做的 / 下一卷的入口

- **像素门禁在容差 0 下会偶发红**（§125.8）：根因是 Chromium 的文字抗锯齿在两次运行之间
  不保证逐位相同，**不是**数据、**不是**某几页特殊——任何有文字的页面都可能中招。实测幅度
  ~20 像素 / 1,024,000（0.002%），通道差 1 级。处置：把门禁的默认容差定成 3（工具已经支持，

### 126.2 #3645：issue 的诊断指错了地方，照着改会留病根

issue 说"payload 里没有可用的错误正文"。**症状是真的，但根因不是"少了字段"**——
如果照着 issue 的描述加字段，病根还在。实测下来是**五层**，每一层各丢一次：

1. **wrapper 丢的**：`rawSnippet` 取的是 `stderrBuffer.split('\n').filter(Boolean).slice(-4)`，
   也就是**最后四行**。而 Node 把错误名打在**第一行**
   （`Error: EACCES: permission denied, open '/root/x'`）——被切掉的正是那行。
   `message` 字段则被填成了 `exit code: 1, signal: none`。
2. **in-process 丢的（重复上报）**：`register.js` 先报 `uncaught_exception`（载荷**带**
   `errorName`/`message`/`stackSnippet`），随后 `process.exit(1)` 又报一次 `exit_code`
   （四个字段、没有 message），**把前一份覆盖了**。字段从来没缺过，是被**替换**了。
3. **handler 压根没跑**：`FATAL_HANDLER` 在 `index.js` 里**没有切分**就传给 `buildSpawnSpec`，
   而 wrapper 是先切分的。`sanitizeCommand` 于是拒绝了 `node /path/handler.js`，
   分发被**静默跳过**——带参数的 handler 从来没收到过崩溃。
4. **草稿层又丢一次**：Node 载荷用 `stackSnippet`/`message`，`scripts/tombstone_to_draft.py`
   读的是 `snippet`。
5. **草稿本来也升不成 lesson**：没有 `evidence_level`；`_infer_domain()` 兜底成 `"general"`，
   而它不在 `data/domains.json` 的规范词表里，于是 `scripts/lesson_gate.py` 拒收。

修完之后，同一个 EACCES 崩溃的实测：

| | 命中的 lesson | 分数 |
|---|---|---|
| 改前（用泛化的 exit-code 查询） | 一条**不相关**的权限 lesson | 0.82 |
| 改后（用真实错误正文查询） | **EACCES** 那条 | **0.905** |

**只加不改**：没有字段被改名或删除，退出码没变，载荷仍然作为最后一个 argv 传出去。

**一处"两个作者各写一份"的治法值得记**：`splitCommand` 原本是 `bin/fatal-guard.js` 里的
**私有函数**。修 in-process 路径需要它，若各写一份就是这个仓库点名的病类。所以把它**上移**到
`src/lib/spawn-command.js` 并导出——逐字搬移，不是重写——wrapper 与 in-process 共用同一份，
wrapper 里的本地副本删掉。`sanitizeCommand` **没有放松**（那是注入防线，有专门测试守着）。

### 126.3 #3644：issue 的前提被实测**推翻**，这比照着改有价值

issue 说"Glama connector 列表停在 2026-09-17，仓库侧已到 2.48.0"。逐条实测：

## 127. CI 抓到的真 bug：Windows 上 profile **根本没有锁**（2026-10-22）

#3646 的 PR 上，Windows 3.12 腿红了：

```
tests/test_issue_1775_severe.py::test_concurrent_profile_increments_all_survive FAILED
AssertionError: lost updates: expected 40 concurrent increments to survive, got 39
```

### 127.1 根因：`_profile_lock()` 在非 POSIX 上是**空操作**

```python
try:
    import fcntl
except ImportError:  # non-POSIX: best-effort, still atomic-rename on save
    yield
    return
```

`import fcntl` 写在**函数内部**，所以在 Windows 上必然抛 `ImportError`，
于是走 `yield; return`——**上下文管理器立刻放行，读-改-写完全没有保护**。
锁文件倒是照建不误，然后一个字节也没用上。

而这个函数自己的 docstring 早就写着它防不住什么：

> "`_save`'s atomic rename only prevents *torn* writes — it does nothing for *lost updates*.
> Two concurrent callers can both read `search_count: 0`, both compute `1`, and one increment vanishes."

**"原子 rename 只防 torn write，不防 lost update"——而 Windows 上正是后者。**
`increment_search`（~150 行）、`increment_lesson`（~171 行）和第三个调用点（~193 行）都吃这个亏。

### 127.2 为什么之前没天天红

因为**竞态窗口小**：Windows 上虽然**没有锁**，但"读-改-写"之间那一下不一定撞上。
40 个线程里丢 1 个，是概率问题。CI 机器忙的时候窗口就变大了。

本轮它红了，重跑又绿了——这正是"flaky"的样子。但**它不是 flaky，是缺一把锁**：
在 Windows 上这把锁从来就不存在。**重跑能过，不代表代码是对的。**

### 127.3 这一轮的处置

- #3646 的那个腿**重跑通过**，PR 已合（`ad7e1422`）。
- 根因修复单独成一条线（`/tmp/wt-locks`），**不塞进 #3646**：
  Windows 上用 `msvcrt.locking`（`fcntl.flock` 的对应物），保持"进程死了锁自动释放"这个性质
  （所以不能用 `O_CREAT|O_EXCL` 那种会留下死锁的锁文件方案），
  **拿不到锁就显式报错**，绝不静默地不加锁继续跑。
- **测试不许被改软**：`test_concurrent_profile_increments_all_survive` 在所有平台照跑，
  不许 skip、不许弱化断言、不许在 Windows 上标 xfail。去掉锁它必须变红。

### 127.4 教训

这一轮有**两处"我以为我知道"的错**，都是被证据推翻的，记下来：

1. **handoff 里"实时数据导致像素不可复现"是错的**（见 §125.8）：采集时那个 API 返回 404，
   页面渲染的是固定文案。实测 4 连采：20/20/0/0 像素差——是 **Chromium 文字抗锯齿的运行间抖动**。
   网页字体假设也被 `--proxy direct` 推翻了。
2. **"Windows CI flaky"这个标签把一个缺锁的真 bug 盖住了**。标签一旦贴上，
   大家就默认"重跑就好"，于是没人去问"为什么这里没有锁"。

**凡是"重跑能过"的红，都要问一句：重跑能过，是因为代码对，还是因为撞得巧。**
