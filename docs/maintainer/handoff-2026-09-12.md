## 2. 为什么 handoff-2026-09-11 §4.1 的三步修法被推翻

那份 handoff 的判断是："根因不是忘了更新，而是 SSOT 机制没覆盖 `index.html`"。
**现象是真的**（`docs/index.html` 3 处 435 + JSON-LD 310+ vs canonical 378），**归因只对了一半**。

真实根因：**占位符替换会消耗占位符**。

```python
if "{{LESSONS_COUNT}}" not in text:
    continue                                   # ← 第 2 轮起永远命中这里
text.replace("{{LESSONS_COUNT}}", str(count))  # ← 第 1 轮就把标记写没了
```

- 第 1 轮：`{{LESSONS_COUNT}}` → `358`，打印 `OK ... -> 358`，退出 0；
- 第 2 轮起：所有文件都不再含该标记 → `continue` → **什么都不做，也不报错**。

证据（可复核）：`ARCHITECTURE.md:35` 至今是 `358+`（标记在 2026-09-05 QW6 提交 `41e48a4a3`
里被物化，此后再没变过）；`README.md` 从未真正带过标记（`COUNT_MARKER_DOCS` 里列了它，文件里没有）。

**所以按原方案把 `docs/index.html` 加进 `COUNT_MARKER_DOCS`，只会制造第 3 个"第一次正确、之后再也不会更新"的受害者**——
而且是 meta description 这种最显眼的位置。原 §4.1 的第 ③ 步"同步更新 workflow 里的 diff 清单"更糟：
清单越长，静默 no-op 的观感越像成功（job 报"无需提交"）。

另一个顺带发现：**同一件事本来就有两套机制**。仓库里早就存在一个正则式、幂等的
`scripts/sync_lesson_count.py`（带 `--check`），但**没有任何 workflow、测试或文档调用它**——
一套自毁（占位符）、一套闲置（正则），于是同一个事实在三个地方有三个值。

## 6. 已踩过的坑（本轮新增，能省时间）

1. **占位符替换是一次性的**（见 §2 + lesson）。看到一个"把标记换成值"的同步器，先问"第 2 轮做什么"。
2. **同一文件的多行注册表写入会互相覆盖**：每行都用**扫描时**读到的文本做替换 → 后一行把前一行的
   写入覆盖掉。表现极隐蔽：工具打印 `docs/index.html: 3 site(s) → 378`，磁盘上文件仍是 `435`。
   正确做法：按文件累积文本、最后写一次。
3. **模式必须能匹配自己写出的文本**：`205+ verified ...` 用要求 `+` 的正则去校验、却写成不带 `+`
   的 `378 indexed ...` → 第一次成功后模式就再也匹配不上，工具会永远喊"句子被改写了"。
   测试里用"不动点"断言一次性挡住这一类。
4. `git push` 本轮**可直接用**（fetch/rebase/push 都成功；push 时出现过一条无害的
   `fatal: unable to get credential storage lock in 1000 ms: Permission denied`，推送仍然成功）。
   仍建议先 `git add`/`commit` 再 `fetch`+`rebase`（handoff-2026-09-11 §6.2）。
5. 本地 `pytest tests/` 仍有 3 失败 + 2 收集错误，**全部是环境漂移**、与本次改动无关：
   `ModuleNotFoundError: mcp.server.mcpserver`（`test_intake_kind`、`test_mcp_http_server`、
   `test_intake_spam_guard`）+ 需要公网的 `test_semantic_smoke`（huggingface 不可达）。
   其余 **1096 passed**。以 CI 为准。
6. **判断"某个 workflow 步骤到底跑没跑"，读 YAML 条件不算数**：用 API 看那次 run 的 steps 结论最直接——
   `GET /repos/{o}/{r}/actions/runs/{id}/jobs` 里每个 step 的 `conclusion` 是 `skipped` 还是 `success`。
   本轮就是靠它发现 release-please 的后三个步骤**从来没跑过**（YAML 里看不出来）。
   另外下载 run 日志（`/actions/runs/{id}/logs`，返回 zip）能看到 release-please 的原话
   （`There are untagged, merged release PRs outstanding - aborting`）——比猜快得多。
   踩坑：这两个 API 的响应在弱网下会 `IncompleteRead`，要重试；`?head_sha=` 过滤也会整页拉取，
   有时不如直接翻页。

**残余风险**：`SITES` 注册表是"手写的受管清单"，新增公开计数文案时如果不加行，新文案不在保护范围内
（`--check` 只保证**已注册**的不会漂）。缓解：新增 meta/文案时顺手加行；`docs/index.html` 这类文件
已按匹配数下限（`min_matches`）保护，删掉一个 meta 标签也会红。
