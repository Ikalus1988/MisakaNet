## 2. 为什么 handoff-2026-09-11 §4.1 的归因是错的（本轮最重要的一条）

那份 handoff 说 "SSOT 机制没覆盖 `index.html`"。**现象对，归因错一半**。真实根因是
**占位符替换会消耗占位符**：第 1 轮把 `{{LESSONS_COUNT}}` 写成数字并打印成功，
第 2 轮起 `if "{{LESSONS_COUNT}}" not in text: continue` 永远命中 → 什么都不做，也不报错。

证据：`ARCHITECTURE.md:35` 停在 2026-09-05 物化的 `358+`；`README.md` 从未真正带过标记；
仓库里同时存在一个**幂等但从未被任何 workflow/测试调用**的 `sync_lesson_count.py`。
按原方案把 `index.html` 加进 `COUNT_MARKER_DOCS`，只会制造第 3 个"第一次正确、之后永不更新"的受害者。

**修法原则（本轮）**：数值用"每轮重新匹配"，不用"替换标记"；匹配不到 = 硬失败。

## 6. 已踩过的坑（本轮新增，能省时间）

1. **占位符替换是一次性的**（§2 + lesson `ssot-marker-replacement-runs-once`）。看到"把标记换成值"
   的同步器，先问"第 2 轮做什么"。
2. **同一文件多行注册表写入会互相覆盖**：每行都用扫描时读到的文本替换 → 后一行覆盖前一行。
   表现：工具打印 `docs/index.html: 3 site(s) → 378`，磁盘上仍是 `435`。按文件累积、最后写一次。
3. **模式必须能匹配自己写出的文本**：用要求 `+` 的正则校验、却写成不带 `+` 的结果 → 第一次成功后
   永久喊"句子被改写了"。测试里用"不动点"断言一次挡住。
4. **`GITHUB_TOKEN` 永远推不了 `.github/workflows/**`**（`without workflows permission`）：
   别让 bot 去维护 workflow 文件里的值，改成运行时读。而且只有第一个值变化的那天才会炸，
   还会丢掉整次生成（lesson `github-token-cannot-push-workflow-files`）。
5. **未闭合的 `<!--` 会把整篇 markdown 正文注释掉**（GitHub 渲染成空白），并让"取第一行做摘要"
   的提取器把 `<!-- provenance:` 当成摘要发布到 meta/搜索结果。19 篇中招。不变式：
   `text.count("<!--") == text.count("-->")`（lesson `unclosed-html-comment-hides-markdown-body`）。
6. **判断"某个 workflow 步骤到底跑没跑"，读 YAML 条件不算数**：用
   `GET /actions/runs/{id}/jobs` 看每个 step 的 `conclusion`（`skipped` vs `success`）。本轮靠它发现
   release-please 的后三步**从来没跑过**；下载 run 日志（zip）能看到 release-please 原话。
   弱网下这些 API 会 `IncompleteRead`，要重试。
7. **改了 scheduled workflow 一定要 `workflow_dispatch` 跑一次**：本轮第一次真跑就抓到两个 bug
   （workflows 权限、push 竞态），否则要等到次日 cron 才知道。
8. `git push` 本轮大部分可用，但常被 bot 快照打成 non-fast-forward：稳妥顺序是
   `fetch` → `rebase` → `push`，失败就重试（本轮给每日 job 也加了 `concurrency` + job 内 rebase 重试）。
   偶发 `unable to get credential storage lock ... Permission denied` 无害；
   `GnuTLS recv error (-110)` 需要重试，或改用 `scripts/gh_push_via_api.py`。
9. **`issue-quality-gate` 的判据在 issue 正文，不在评论**：它按正文里的 `AC/验收标准` + `[ ]` 复选框
   打 `ready` 或 `needs-ac`。只发评论等于没补 AC；而且它**只加不删**标签，于是会出现 `needs-ac` 与
   `ready` 并存的怪状态（本轮已修 gate：满足条件时清掉过期那个）。
10. **HOL 的 `plugin-scanner` 判定已经读源码确认（不是猜）**：它是 PyPI 包
   `codex-plugin-scanner`（HOL 的 guarded-repository 用它，每 main push 重扫），判定函数是
   `_is_safe_relative_asset = is_safe_relative_path(plugin_dir, value, require_prefix=True,
   require_exists=True)` —— 于是 `interface` 资产必须**以 `./` 开头**，**且** `(plugin_dir / value)`
   真实存在。而它跑的 `PLUGIN_DIR=.`（**仓库根**，见 run 日志）。所以：
   外链 HTTPS 不行（`require_prefix` 直接拒），`.codex-plugin/assets/…` 这种写法也不行
   （从仓库根解析不到），**只有 `./.codex-plugin/assets/…` 同时满足两条**。
   `pip download codex-plugin-scanner` 就能读到这些判据——第三方扫描器报错时先读它的源码。

## 8. 事故复盘：`git add -A` 把本地残留提交进了公开仓库（2026-09-12）

**现象**（维护者先发现）：`29b098961` 一条提交里有 210 个文件、162,594 行新增，看起来像「上传了一堆 HTML」；
随后 GitHub 对 `.archify-tool/archify/package-lock.json` 开出 4 条**高优** Dependabot 告警
（fast-uri：错误 IPv6 规范化导致 SSRF、百分号编码 / 重复解码导致主机混淆）。

**根因**：会话开始时工作区里有**未跟踪的会话残留**——`.archify-tool/`（vendored 本地工具，8.2 MB，
含 6 个约 15k 行的 HTML 示例和它自己的 `package-lock.json`）、`reports/user_analysis_2026-09-07/`
（含 `raw_kv_dump.json` / `raw_email_dump.json`）、`scripts/mhs_watch*`、`docs/agents/mhs-watch.md`。
而我在后几次提交里用了裸 `git add -A`，把它们一起带了进去，且提交信息（gate the generated pages）
完全没提这些文件——等于**用一条文档提交走私了 162k 行本地垃圾**。

`.codexignore` 第 16–18 行一直把 `reports/`、`.archify-tool/`、`.audit-reports-*/` 标为本地物，
但 `.gitignore` 只覆盖了 `.audit-reports-*/`——**这个缺口正是 `git add -A` 得手的原因**。

**影响**：
1. 公开仓库多了 8.2 MB vendored 工具与 148 KB 分析 dump（含 30 个邮箱地址；快速模式扫描未发现 token/密钥类字符串）；
2. 依赖图里多出一个 manifest → Dependabot 对**本项目不发布、不构建、CI 不跑**的工具报高优漏洞；
3. 13 条 CodeQL shell-injection 同样来自这些 vendored 测试文件；我当时的 dismiss 理由对代码成立、
   但**对「它为什么在仓库里」是错的**，已在 §3.5 更正；
4. 维护者看到的「一堆 HTML」= 这些残留 + 我同一条提交带进去的
   `.archify-tool/misakanet-architecture.html`（15,028 行），**不是**页面生成器的产物。

**修复**（`c559d15e0`，已复核）：`git rm -r --cached` 全部撤回 + 补 `.gitignore` 规则。
main 上 `.archify-tool` / `reports` 已不存在；**Dependabot 开放告警 0 条、CodeQL 开放告警 0 条**。

**修复过程中的第二个错误（同一次复盘）**：`git rm --cached` 本身保留工作区文件，但随后的 rebase
把我的 revert 提交应用到仍跟踪这些路径的基线上，**应用删除 diff 时把工作区文件一起删了**——
即 8.2 MB 工具包与那批报告一度从磁盘上消失。已用 `git checkout 29b098961 -- <paths>` + `git reset`
**全部恢复**（回到"文件在本地、untracked、被 ignore"的原始状态，已逐一核对）。

**防复发**：`scripts/hygiene_check.sh` 增加第二道门（该脚本已挂 `.pre-commit-config.yaml`，**提交前**就会跑）：
用 `git ls-files` 断言这些本地专用路径**没有被跟踪**，命中就 exit 1 并给出 `git rm -r --cached` 的修法。
两个方向都实测过：故意 `git add -f reports/…` → 报错 exit 1；撤销后 → exit 0。
为什么放在 pre-commit 而不是 CI：**这次事故发生在提交的那一刻**，CI 只能事后发现。

**残留**：blob 仍在历史里（公开可访问）。彻底清除要改写历史（filter-repo + force-push），
会改 SHA 并影响所有 clone / PR / tag——属维护者决策，未擅自执行。若认为那 30 个邮箱需要清除，另行决定。

**教训（agent 视角）**：
- **不要在有未跟踪残留的工作区里用裸 `git add -A`**；提交前先 `git status --porcelain` 或明确列出路径。
  本次前几次提交我用了明确路径，后几次图省事用了 `-A`，事故就出在后者。
- 提交信息必须与实际文件集一致：一条 "docs+ci" 带 200 个无关文件，**发现成本被转嫁给了维护者**。
- 本地残留边界写在 `.codexignore` ≠ 写在 `.gitignore`；**两个都要写**，否则 `-A` 会替你决定。


## 9. DSH STORE 上架被 `blocked` 的根因与修复（2026-09-12，分支 `fix/dsh-store-bundle-patch`）

**现象**：维护者收到 `AI-Scarlett/DSH-Store#747`（自动通知，`author-action-required` + `candidate-rejected`），
报的是固定 commit `9e6439a61e54`（**2026-08-23**）上的 `SUBMISSION_VERSION_INVALID: package.json must
declare a semantic version`。

**两点更正**：
1. **那条理由是陈旧的**：我们的 `package.json` 从 **2026-09-07**（`dd0a5af0d`）起就有 `version`，而它审的是
   两周前的 commit——它们的"固定 commit"在提交/候选时被钉住，不会自动跟进。
2. **真正的当前状态更严重**：DSH-Store 仓库 `registry/candidates.json` 里（id `ikalus1988-misakanet`，
   `latestCommit` = `6d63642e4`）我们被判：

```
"status": "rejected",
"route": "blocked",
"statusReason": "SUBMISSION_PATCH_PROTECTED: Bundle Patch impersonates the protected @deepseek-ai namespace"
```

`blocked` 是**最严的档位**（比 candidate 还低，不进受保护安装通道）。根因在我们
`cordis.patch.yml` 的那一行：插入行直接实例化了官方组件（写的是 `@deepseek-ai/dsh-mcp-client`）。

**规则在源码里（不是猜）**：DSH-Store 的 `scripts/check-plugin-submission.mjs` →
`patchEntryIds()`：patch 全文（**含注释**）匹配"插入行声明受保护命名空间"的正则就直接抛
`SUBMISSION_PATCH_PROTECTED`；另一条规则是"patch 里出现 `@deepseek-ai/` 且带 `disabled: true`"。
**实测已收录插件**（随机抽 14 个）**没有一个**在 patch 里实例化 `@deepseek-ai/*`，它们都插入自己的组件
（`dsh-vision`、`@yejiming/dsh-gomoku`、`dsh-checkpoint-rewind`…）。

**修复**（分支上，等维护者合并）：
- `cordis.patch.yml` 只插入**我们自己的**包（插入行指向 `misakanet`），不再出现任何受保护组件名；
- MCP 接线搬进 `index.js`：`apply(ctx, config)` 运行时 `await import('@deepseek-ai/dsh-mcp-client')`
  并 `ctx.plugin(component, config)` 挂载（配置仍来自 patch 行，可覆盖默认值）；
- `package.json` 把官方客户端声明为**可选 peerDependency**（`peerDependenciesMeta.optional=true`）——
  这样 pnpm 会链接宿主那份，**不会重复安装受保护组件**（契约第 7 条），并补 `engines.node`；
- `tests/test_dsh_bundle.py`：原来那条断言**把违规写法锁死了**（`row["name"] == "@deepseek-ai/dsh-mcp-client"`），
  已改成断言我们自己的组件，并新增两条**复刻 DSH STORE 规则**的守卫测试。

**验证**：patch 对照其两条正则 = 干净；假 ctx 跑 `apply()` → 官方客户端（`name: mcp-client`）被挂载、
patch 行配置覆盖默认值；客户端缺失时默认静默降级、`failOnStartupError: true` 时抛错；`pytest` 7 例通过。

**注意（两个坑）**：
- 那个检查是**对整个 patch 文件文本做正则**，所以在注释里"引用"被禁的模式也会触发阻断——
  写规则时只描述、不要贴原样（`cordis.patch.yml` 头部已写明）。
- 本次改动影响了 **dsh.so L5 验证过的 bundle 契约**（2026-09-05 的 patch 就是为修 L5 引入的）：
  合并后**必须重跑 dsh.so 的 L5**，并等 DSH STORE 的 8 小时复检读取新的固定 commit。

### 10.1 检索质量：一个功能齐全、但**从未运行**的检索栈

外部演示（拿第三方仓库的真实失败去问 MisakaNet）暴露的：`misakanet_search("VISION_API_KEY env var not set")`
返回 `user-agent-identify-bots` 这类无关课程，而且**响应里没有 `no_match`**——永远不会说"我不知道"。往下挖了三层：

| 层 | 缺陷 | 修法 |
|---|---|---|
| 排序 | 只有排序、没有相关性下限，任何查询都返回"最不坏"的 N 条 | 相关性下限：≥1 个**有信息量**的词（df ≤ 30%）+ ≥min(2, 可配对) 个不同词；否则走既有的 `no_match` + intake 指引 |
| **匹配** | 线上走的是**朴素回退**，用 `text.includes("env")` 匹配 → 命中 "environment"，几乎"人人皆中"，下限形同虚设 | 两边统一 **token 匹配**（共享 `matchTokens`，CJK 感知）；FAQ 命中要求 ≥2 token 重叠 |
| **索引** | `GET /api/search-index` → `{"available": false}`：索引本该由 `scripts/build_worker_index.py` + `POST /api/search-index`（需 `X-Sync-Token`）推送，但**没有任何 workflow 调过这两个脚本**，KV 条目还有 **7 天 TTL**，仓库也没有 `SYNC_TOKEN` secret（脚本默认域名还写成 `misakanet.dev`，不是本项目的域名） | **worker 在自己的 cron 里建索引**（`refreshSearchIndex`，>20h 才重建，`{refreshed:false,reason:"fresh"}` 否则跳过）：不需要 secret、不需要外部 runner，也不会被 TTL 卡住；索引形状即 `searchLessonsBM25` 的契约，额外吃 `summary`/`preview`（worker 的课程载荷把正文放在 `preview`，这才让"只有正文提到"的失败可被检索到）。实测规模 **384 docs / 9,764 terms / 1.6 MB**（KV 上限 25 MiB） |

两次实测纠偏（都写进了代码注释，避免后人重踩）：
- 我第一版下限**引入了假阴性**（`kubectl crashloopbackoff` 不命中 k8s 课，因为 `kubectl` 在意料之外的课里出现过 → "至少 2 个词"的分母错了）→ 改成统计**可配对**的词（出现在 ≥2 篇里），修好；
- 还试过"短查询必须命中它最稀有的词"→ **实测净负收益**（`git push failed` 被误杀，垃圾命中没减少）→ 撤掉。

顺带修掉两条"有检查但没人跑"：`workers/d1-fts-search.test.mjs` 在 main 上一直红（不在 CI 名单里）→ 真因是无 D1 时 `?q=` 抛异常返回 502（已修成它本来就期望的提示）；**整个 worker 套件现在都进 CI**。
