### 3.5 组件健康：全量 3288 passed / 10 failed / 25 skipped，**9 个失败是同一个本机原因**

跑法（venv 口径，见 §4.1）：`pytest tests/ -q -p no:randomly`，13 分 11 秒。

| # | 失败 | 归因 |
|---|---|---|
| 9 | `test_agent_autostart` / `test_benchmark_fixtures` / `test_installer_portability` / `test_portable_environment_gates` ×6 / `test_voice_hooks` | **本机 CRLF**，见下 |
| 1 | `test_stdio_stdout_is_only_json::...cold_cache` | **真发现**，见 §3.6 |

**9 个 CRLF 失败是怎么定的**（A/B，不是推断）：本机权威检出在 `/mnt/c`（Windows 盘），
`git config core.autocrlf = true`，而 `.gitattributes` **一条 `text` / `eol` 规则都没有**
（它只有 `linguist-generated` 标记）。所以仓库存的是 LF、检出到工作树就变成 CRLF，
凡是执行 `.sh` 的测试全部炸：

```
scripts/misakanet_voice_hook.sh: line 14: $'\r': command not found
integrations/agent-autostart/bootstrap.sh: line 15: set: pipefail
```

**A/B 证明**：同一 HEAD（`4a8e5749`）、干净树，在 LF 文件系统的那份检出上跑同样的 12 个用例
→ **12 passed**。

```
$ cd /home/eric_jia/MisakaNet && pytest <那 10 个失败用例> -q
12 passed in 0.92s
```

**所以：不是仓库缺陷，CI 是绿的**（`.gitattributes` 不管换行是因为 CI 在 Linux 上检出）。
但它**确实是**一个贡献者可移植性缺口：Windows 上默认 `core.autocrlf=true` 的贡献者
跑不出全量绿，而"本地跑不绿"正是"门禁到底测到了什么"这件事失去信号的开始。
**最小修法**是给 `.gitattributes` 加 `*.sh text eol=lf` 一类规则 + 一条"每个带 shebang 的
受跟踪文件都必须有 eol 规则"的门禁。**本会话没有动 `.gitattributes`** —— 全仓
`* text=auto eol=lf` 会触发一次大范围 renormalize，那是维护者的决定，不是顺手该做的。

### 3.6 真发现：那条 stdout 纯度门禁，**只在没建过 SAG 索引的机器上才测到它要防的东西**

`tests/test_stdio_stdout_is_only_json.py::test_the_mcp_stdio_stream_stays_pure_json_on_a_cold_cache`
在 CI 上是绿的，在**两棵干净的本地树上都红**（不是 CRLF 造成的）。根因链：

1. `misakanet/server/handlers/search.py:411` — `if HAS_SAG and not explain:` 走 SAG-Lite 后端，
   **这一支根本不调用 `_load_docs_cached`**；
2. `misakanet/server/_config.py:19` — `HAS_SAG = SAG_DB.exists()`，而
   `SAG_DB = REPO_ROOT / "data" / "sag.db"`；
3. `data/sag.db` **被 gitignore**（`.gitignore:54`），是本地构建产物。

于是：**建过 SAG 索引的机器 → 走 SAG 分支 → L2 那条提示永不出现 → 门禁在自己 premise 上失败**；
**没建过的机器（含 CI）→ 走 BM25 分支 → `_load_docs_cached` 触发 → 提示出现 → 通过**。

验证：

```
$ MISAKANET_CACHE_DIR=$(mktemp -d) python -c "from misakanet.search.engine import _load_docs_cached, LESSONS; _load_docs_cached(LESSONS)"
  📦 L2缓存: 464 篇变动          # 直接调用会打印

$ MISAKANET_CACHE_DIR=$(mktemp -d) python scripts/mcp_server.py   # 走 tools/call → 无提示
MisakaNet MCP Server started / SAG-Lite: available / BM25: available
```

**为什么这条值得记**：这个门禁**失败得很响**（它自带"提示没出现 = 我没测到东西"的前置断言），
所以它没有骗人——但它暴露的是**覆盖率依赖一个可选后端不存在**。
10-04 那份 handoff §1.3 记的正是"L2 提示污染 stdio 流"这个 bug；
**在装了 SAG-Lite 的机器上，这个 bug 现在没有任何测试在守**。
又是一次"门禁的宽度正好等于那次事故"——只不过这次窄在**环境**上而不是代码上。

**建议修法**（未做，等决定）：让这条用例显式控制后端，而不是接受环境默认值。
最小做法是在 `_cold_cache_env` 里补一个让 `HAS_SAG` 为假的条件，
或直接给 `_load_docs_cached` 本身加一条 stdout 纯度断言，把覆盖从"端到端恰好走到"改成"就地"。

### 3.7 新盲区：`/api/versions` 的 `generated_at` 是新的，**内容却是旧的**

2.41.2 发布后立刻查线上（`generated_at = 2026-10-05T16:54:00Z`，比 tag 还晚 5 分钟）：

```
release           2.41.1     ← 实际 2.41.2
registry          2.41.1     ← 实际 2.41.2
npm               2.41.1     ← 实测 npm latest = 2.41.2
plugin_manifest   2.41.2     ← 唯一是对的
```

**四条线里三条是错的，而它们的 `generated_at` 看起来完全可信。** 原因：`plugin_manifest`
那一行是运行时从 main 现读的，另外三条是**打进 bundle 的部署时快照**——worker 还跑在
`82cee67f`，所以它如实报告了"我被构建时是 2.41.1"。

这是 §6.5 那个坑的**新变体**：
- 旧版：线上和 main 版本号相同 → 陈旧部署隐形；
- 新版：`/api/versions` 自报"我刚生成的" → **陈旧部署隐形，而且带一个看起来很权威的时间戳**。

`/api/health` 的 `commit_sha` 不会撒谎（§3.2 靠它抓到了 6 个提交的滞后），`/api/versions` 会。
**所以：判断部署新鲜度只看 `commit_sha`。** `/api/versions` 用来回答"这条版本线由哪些渠道组成"，
不要用它判断线上跑的是哪一版。
