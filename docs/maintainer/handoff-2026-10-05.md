## 2. 本会话最重要的一条：**"收据"这件事有三层，三层同时是坏的**

这三处不是三个独立故障，是同一个形状在三个高度上的表现。它们值得一起读，
因为**任何一层单独修好都不会让另外两层变好**。

### 2.1 第一层：收据本身不在读者所在的地方

10-04 那份 33 KB 的 handoff 写在 `/home/eric_jia/misakanet-handoff-2026-10-04.md`，
**从未进仓库**，抬头还明写"本地交接文档，不在仓库里"。
后果不是"风格不统一"：仓库里有一条门禁（`tests/test_handoff_citations_resolve.py`）
专门保证"代码引用的收据必须存在"，而**一份没人能读到的 handoff 就是不存在的收据**。
下一轮维护者（也就是我）花了几分钟才在 WSL home 里翻到它。

已收进 `docs/maintainer/handoff-2026-10-04.md`，抬头改成"原先在仓库外，10-05 收进来"。
两条相关门禁本地复跑均绿：`test_handoff_citations_resolve.py` +
`test_cited_lesson_paths_exist.py` 5 passed；`test_no_live_doc_pins_a_package_version.py` 7 passed
（`docs/maintainer/` 在其 `HISTORY` 豁免名单内，所以课文里的 `2.40.0` 不算违规）。

### 2.2 第二层：检查收据的那条门禁，自己带着一张假收据上线

`#2827`（main tip，`4a8e5749`，2026-10-04 18:06）加了上面那条门禁，并**当场修掉了 5 处
悬空引用中的 4 处**。第 5 处漏了：

```
E   AssertionError: code cites a handoff that was never committed, so the measurement
    it stands on cannot be checked by anyone:
E       .github/workflows/registry-drift-watch.yml cites docs/maintainer/handoff-2026-09-24.md,
        which does not exist
```

`handoff-2026-09-24.md` 从来不存在（序列是 09-16 → 09-30，中间没有 09-24），
`~1 request in 4` 这个比例在仓库里也查不到出处。#2827 已把同样形状的 4 处改成
"只留规则、不留数字"的口径 —— 唯独漏了这第 5 处，而它恰好是**唯一还没被改口径的那处**。

**修法**（#2848，单文件 +5/-4）：门禁自己的 message 给了两个选项——要么把 handoff 提交进来，
要么删掉数字、留下规则。第一个选项不可用（文件从没写过），所以走第二个：
`ATTEMPTS=3` 这条重试预算**本身**是站得住的工程决定，不需要收据；删掉比例和引用即可。
顺带把 `for the same measured reason` 改成 `for the same reason`——它指向的正是那个已不存在的测量。

**影响面**：这条门禁在**九个** test 作业上全红，release PR **#2825（2.41.2）因此 BLOCKED**。

### 2.3 第三层：**main 的 push 根本不跑测试矩阵**

这是本会话最该先记的一条，因为它决定了上面两条为什么"没被早点发现"。

```
$ gh run list --commit 4a8e5749 --limit 25     # 空
$ gh run list --limit 12                        # main 上只有 Update Badge Counts / Site build watch /
                                                # PR Quality Gate(skipped) / deploy-worker
```

`tests/` 矩阵只在 **PR** 上跑。推 main 时 `PR Quality Gate` 是 `skipped`，没有任何 `test (...)` 作业。
所以 **#2827 让 main 变红这件事在 main 上完全不可见**——它只在下一个 PR 上才显形。

这次是靠"2.41.2 发布 PR 恰好存在、恰好被挡住"才浮出来的。
**这不是门禁在工作，这是运气。** 仓库真正的盲区在这里：任何让 main 变红的门禁，
都要等到下一个 PR 才会被任何人看见；中间这段时间 main 上什么信号都没有。

`ruleset 23826057`（`main: the deterministic gates`）的必需检查只有 4 个：
`DCO / Signed-off-by`、`test (ubuntu-latest, 3.11)`、`gate`、`audit`。**其余全部可选**——
判断"能不能合"时别把可选腿当门禁。

### 5.3 待处置：code-scanning #325 / #326
`GITHUB_ACTIONS_UNTRUSTED_CHECKOUT` 指向 `deploy-freshness.yml:1`。这条规则会在
"workflow 有 `workflow_run` 触发器且调用了 checkout"时报警，但**它无法判断 checkout 的 ref 是什么**。
实际读下来这个工作流是安全的：它**没有** checkout 触发它的那个 run 的 `head_sha`
（`head_sha` 只出现在第 77 行的 `echo` 里），`workflow_run` 事件下默认 checkout 的是默认分支，
且 `permissions: contents: read`、不使用任何 secret。
**属于与 09-30 那批 `HARDCODED_SECRET` 同类的"规则看不见全貌"误报**，但处置（dismiss）是 owner 动作。
若要彻底消掉，更正的做法是把 ref 写死：`ref: ${{ github.event.repository.default_branch }}`——
这同时是**语义修正**：这个探针的职责是"生产 vs main"，而 `workflow_dispatch` 可以从任意分支触发，
从 PR 分支手动触发时它会去拿 PR 的 commit 当基准比，那是错的。
