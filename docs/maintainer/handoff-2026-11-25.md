## 1. 判断

### 1.1 闸门的三次否掉，每次否掉的都不是架构，而是**说明与行为不一致**

| 版本 | 审核意见 | 实质 |
|---|---|---|
| 1.5.15（拒） | 没取得用户确认就往 agent 注入 `user_confirmed=true`；卡不可用仍直发 | agent 替用户说话 |
| 1.5.17（拒） | `matched_lesson_id` 不在预览与票据绑定里 | 用户看过的内容 ≠ 发出去的内容 |
| 1.5.18（拒） | 规则里没有私网 IP；令牌/密钥只识别部分格式，而卡片宣称「已替换」 | 卡片在承诺它做不到的事 |

三次的解法都不是「改口径」，而是**把说明变成事实**：卡片与票据遍历 `INTAKE_ARGS`（不再手抄字段表）、
所有用户输入字段先过 `redact()` 再摆卡、补 `private_ip` 规则并**四处实现同步**（`workers/lib/redact-patterns.json`
是唯一真相、worker 两处内联、插件 `REDACT_RULES`、CLI 钩子的 Node+Python 双胞胎）。
`tests/test_redaction_sync.py` 与 `test_client_server_rule_agreement.py` 会拦漏。

**判据**：审核读的是「你承诺的事，代码做不做得到」。任何一句写在卡片/说明/手册里的保证，
都要能在代码里指到那一行；指不到就删掉这句话，别赌它不会被读。

### 1.2 卡片按钮自己发不出去，是宿主规则，不是 bug

卡片动作派生的 `spawnCallId` 是**卡位**（手册 §4.5），不是一次工具调用。宿主的 `cindy.fetch` 只给
**正在执行的那次工具调用**代发网络请求，所以点击之后插件自己发起的请求在真机上 **0 ms** 被网络闸拒——
用户以为提交了，仓库里什么都没建。市场审核又明确要求不要自主联网授权（`network`），
所以「点击 → 插件自己发」这条路在宿主规则下**封死**，不是再改几行能绕的。

**判据**：插件里凡是脱离在途调用的 `cindy.fetch`，在没有 `network` 授权时**必然是死代码**。
写之前先问「这次调用挂在哪」。

### 1.3 手机端能点卡片，但确认框只在桌面

真机探针（两张一次性卡片）量出来的三条事实，值得记住：

- 手机上**卡片会渲染、按钮点击会回传** `card-action`；
- **一次点击会投递两条事件**（必须按 callId 去重，否则会铸两张票）；
- 声明 `agent` 之后事件里才有 `userActionToken`，`cindy.agent.run` 返回 `{ok:true, disposition:'queued'}`，
  那一轮**确实会跑起来**；`mobilePageId` 时有时无，别依赖它。

`cindy.confirm` 则按来源呈现：不带移动来源时确认框落在**桌面**，只有从插件自己的移动端页面发起
（`mobilePageId`）才由手机原生弹。**所以「在手机聊天里弹个确认框」不成立**——这也是 1.5.19 那版
用「用户手打短码」的原因，而短码的代价是摩擦落在用户身上（复制 6 个字符 → 发一条消息 → 等一轮）。

### 1.4 最终形状：点击 → 一次性票据 → 一轮 agent

1. 第一次调用只摆卡（全字段、已脱敏），**不发任何请求**，回执 `awaiting_click: true`；
2. 用户点「确认提交」→ 宿主回传一次性 `userActionToken` → 插件铸票 + `cindy.agent.run` 换回一轮；
3. 那一轮的 agent 带 `click_ticket` 再调一次，外发发生在**它的在途调用**里，所以宿主会代发。

票据绑定**全部上报字段**、15 分钟、用一次即废（重放 → `TICKET_UNKNOWN`）；改字段 → `CONTENT_CHANGED`；
卡供不出来 → `CARD_UNAVAILABLE`；宿主没有 `agent` 能力 → `CLICK_GATE_UNAVAILABLE`。三者都**不发**。

### 1.5 「轮末替 agent 查语料」从来就没成功过

插件自己的 checkpoint 是最硬的读数：**9 个会话 `autoSearched` 全部推进，`hit` 与 `noHit` 全为空** ——
也就是每一次都走进了 `catch`。两天里它的唯一产物是 **17 条「语料查询没成功」** 的 toast。

原因是 §1.2 那条规则。1.5.21 改成分工：轮末只记失败 + 提醒，**下一轮由 agent 用自己的在途调用去查**；
「值不值得沉淀」也改由 agent 那次搜索的**零命中**判定（以前这个判据挂在一个永远失败的请求上）。

## 5. 坑（本卷实际踩到的）

1. **新增权限的安装必须由桌面侧会话发起**：手机远程的共享任务跑 `ghost_forge_install` 会直接
   `MUTATION_CANCELLED`（连权限卡都不渲染）。绕法只有两个——给用户 `.cindy` 让他自己在插件页导入，
   或等他人在桌面时再跑。
2. **社区提审也要求「账号任务」**：同一个会话挂到手机上会回
   `PERMISSION_DENIED: ... shared-task guests cannot borrow the Host account`。**别拿上次成功当这次也行**，
   权限跟着「会话挂在哪个端」变。
3. **`ghost_contribution_submit` 常返回 `stage:prepared`**，真正结果要接 `ghost_contribution_status`
   看 `stage:complete`；`UPLOAD_OBJECT_MISSING` 是宿主偶发（连撞两次、第三次同流程成功），不是包的问题。
   两次 prepare 的 sha256 会不同（打包非确定），正常。
4. **改 `integrations/agent-autostart/checkpoint_reminder.{mjs,py}` 必须重算 `bootstrap.sh` 的
   `CHECKSUMS`**（`python scripts/update_install_checksums.py --write`），否则 `test_bootstrap_checksums.py`
   在 CI 上先红。
5. **仓库 CI 的 macOS 作业经常 `The job was not acquired by Runner of type hosted` 然后 cancelled** ——
   基建问题，不是测试红；Ubuntu+Windows 全绿即可判断，必要时 `gh run rerun --failed`。
6. **同一工作仓两个会话并发**：本卷期间对方 `git reset --hard origin/main` 两次，把在途改动冲掉过。
   有未提交改动时先切到自己的分支，或干脆在旁边的 copy 里做（本卷后半段就是这么做的）。
