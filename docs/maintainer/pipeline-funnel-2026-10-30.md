# 语料入库的漏斗：哪些能自动进、哪些不能、以及卡在哪（2026-10-30）

> 一次对"仓库里 350+ 条语料"的体检。所有数字都是 2026-10-30 当天从 GitHub API 与
> `lessons/` 现算的，复现命令在 §8。结论先行：**自动链路不是"卡死"，是三处取数与观测缺陷让它
> 看起来卡死**；真正需要人回答的只有 5 条，其余是"等报料方的一手证据""等把已写好的课投进来"
> "应礼貌拒绝"三类。

## 3. 策略：谁答、成本、风险

现有三条路径都已实现，且各有实测：

| 路径 | 机制 | 实测 | 适用 |
|---|---|---|---|
| **语料已能回答** | `question_autopilot` 打回执 + 指到课程 | 上周 12 条里 2 条"已覆盖" | A 类之外的大多数"伪盲区" |
| **另一个 agent 撞过** | 按共享词聚成 cluster，开 **1 个 bounty 任务**（$0 / `zero-bounty`） | 10-29 digest：3 条 1 簇 | B 类里"别人也可能撞到"的 |
| **报料方自己答** | 回执写明"你有三样我们都没有：具体报错、试过什么、怎么验证" | B/C 类的唯一可行路径 | 平台特有、环境私有 |

**禁止的那条**：维护者凭空生成答案。`docs/maintainer/provenance-gate-2026-09-16.md` 记着四次
"24/24 全绿但引用了 404 仓库"的课程 PR；`answered` 标签会把文本送进 FAQ，当成"维护者答复"发给
agent。**答案必须来自观察过那次失败的人。**

按 `docs/maintainer/product-evaluation-lens.md` 的三问给这三条路径打分：

| 路径 | 谁操作 | 谁受益 | 有能力吗 |
|---|---|---|---|
| 我们答 A 类 | 维护者 | 提问者 + 产品 | ✅ 只有我们能改 |
| 报料方答 B/C 类 | 报料方 | 报料方（下次自己用）+ 后来者 | ✅ 他有环境；**但缺一步"把它写成课程"的推力** |
| bounty 集群 | 后来撞上的 agent | 它自己 + 发问者 | ⚠️ 依赖"真有人撞上"，$0 奖励只有名义 |

**结论**：A 类我们立刻答；B/C 类的动作不是"答"，是**把最后一步压到一次调用**
（`misakanet_write_lesson`，或对 B 类只要求补 `## Error` + 验证行）；D 类关掉并说明范围；
E 类补回执后关。

## 4. 自动化这条链，本周实际表现

### 4.1 调度层（近 7 天 workflow 运行）

| workflow | runs | 成功 | 失败 | 跳过 | 备注 |
|---|---:|---:|---:|---:|---|
| `intake-auto-review`（MCP triage） | 100 | 79 | 0 | 21 | 每条 intake 自动分类/打分 |
| `sync-question-answers` | 100 | — | **2** | 89 | 失败都在 "Backfill answered labels" 步 |
| `auto-merge-lessons` | 100 | 0 | 0 | 96 | 需 `auto-merge-lesson` 标签；本周没有带标签的课程 PR |
| `heartbeat` / `question-autopilot` / `intake-salvage-digest` / `stale` | 7 each | 7 | 0 | 0 | 日更 |
| `decision-queue-digest` | 7 | 7 | 0 | 0 | 周更 |
| `sync-d1` / `update-lessons` | 14 each | 14 | 0 | 0 | push + 定时 |
| `lesson-quality` | 28 | 28 | 0 | 0 | — |

**调度层故障率约 0–2%。** 但"跑成功"不等于"算对了"，见 4.2。

### 4.2 结果层的三个缺陷（都能量化）

1. **`question_autopilot` 只读一页。** `scripts/question_autopilot.py:151` 单次
   `issues?state=open&per_page=100`，**没有翻页**。现在开着 355 条 issue、54 条 question，它只看到
   **12 条（22%）**；最新 digest（#4063）因此写着"12 open question"，实际 54。
2. **digest 去重也依赖同一页**（同文件 :641）。于是每次"找不到旧 digest"就新建一条：
   现在有 **5 条同名开着**的 question digest（#2284/#2876/#3333/#3731/#4063），数字各自停在创建那天。
3. **覆盖率测量没有重试。** 生产端点会掐掉慢请求（#4072：全缓冲响应，首字节晚于约 3 s 就被链路
   切断）。今晚 dry-run 12 条里 **7 条**得到 `RemoteDisconnected` → 回执写给报料方的是
   "not measured yet"。同一缺陷也让 `sync-question-answers` 的 backfill 步两次失败（GraphQL 抖动，
   无重试），以及 `done_but_open` 全量跑 5 分钟没跑完。

### 4.3 结论

自动化的**判断逻辑**是对的（分类、打分、去重、回执、聚类、bounty 都实现了），**取数层**是薄的：
单页、无重试、把"读不到"和"没有"混在一起报。这解释了"看起来卡死"：卡的不是流程，是视野。

### 6.2 判断：**不新建站点页面**

按本仓的产品评估第一性原理（发展 + 减少摩擦；谁操作、谁受益、在什么场合）：

- **谁操作**：只有 owner 一个人。**谁受益**：同一个人。这不是"请求不获益者劳动"的问题，但它也
  不是社区的仪表盘。
- **在什么场合**：owner 读的是**通知**（GitHub 的 issue 评论），不是主动去开的页面。一个需要
  "记得去看"的页面，比已经躺在 inbox 里的每日评论**更差**——这正是 heartbeat 当年选择"一条评论、
  owner 什么都不用做"的理由。
- **现有五个面缺的不是"页面"，是六个标签答不出的数字**：转化率（按周/按类别）、issue→课程时延、
  各卡点的存量与最老年龄、auto-rejected 的 salvage 率、问题从"提出"到"答/课程"的时延、
  本仓 backlog 的净变化。

**因此**：把 §1–§5 的六个数字做成 heartbeat 的第 4 个面板（`pipeline`），由
`heartbeat_report.py` 现算、每天一条评论；不新增页面、不新增需要人点开的东西。什么时候再谈页面：
当面板 1（外部调用）**有数据**、且有人真的每天读它时。

### 6.3 能不能承接"流量来了"？

**现在不能**，两处证据：

1. **面板 1 是空的**：10-29 的 heartbeat 写着"没有 traffic-class 行""没有 client 行"——不是没人调，
   是计数没落库（或读错了 scope）。没有这一个数，任何流量判断都无从谈起。
2. **面板 3 的判读边界很清楚**：votes/retrievals 最近三天是 0/22、0/13、0/15；窗口内 44 票，
   且 `lesson_usage` 里"pip install timeout"一天 388 次是**我们自己的测试**。也就是说现在的
   "使用量"大部分是自己的回声。

先修 §4.2 的三个取数缺陷 + 面板 1 的写入/读取路径，再谈"流量判断"。顺序反了，页面只会把
"读不到"渲染成"没有"。
