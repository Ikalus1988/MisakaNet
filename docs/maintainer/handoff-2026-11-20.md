## 1. 判断

### 1.1 一条链上五个形状，前四个都是"绿着什么都不做"

`docs/maintainer/auto-merge-lessons.md` §1 的「再问一次」一节现在是它们的完整记录。按发现顺序：

| # | 形状 | 失败的表象 | 修法 |
|---|---|---|---|
| 1 | `SHELDON_PAT` 没有 `actions: write`，dispatch 一律 403 | 首次运行 0 候选，而"每个都失败才红" ⇒ `0 failed / 0 total` 是绿 | dispatch 改用 `${{ github.token }}`（`workflow_dispatch` 是 `GITHUB_TOKEN` 能抬起的两个事件之一）|
| 2 | `workflow_dispatch` 没有 `pull_request` 上下文，作业级标签守卫恒 false | run 结论 `skipped`、零个 step | 守卫加 `github.event_name == 'workflow_dispatch' ||` |
| 3 | `mergeStateStatus` 是**缓存字段**，任何合并进 main 都让所有 open PR 变 `UNKNOWN`；列表端点只读缓存 | 扫尾器报 `candidates: 0`，而 `GET /pulls/N` 仍是 `clean` | 候选集只按标签+非 draft 筛，再逐 PR 调单 PR 端点（触发计算）并重试 |
| 4 | `lessons/index.md` 额度写死 `+1`，生成器却给**每篇课**写一行 | 任何 ≥2 篇的批次被通道自己拒（`+2/-0 (allowed: +1/-0)`）| 额度改成"每篇新增课一行"，删行与超额仍拒 |
| 5 | `schedule */30` 在本仓送得极稀：14 小时 2 次 | 没有失败可看，只是"永远在等" | 加 `workflow_run` 触发（只列五个门），`schedule` 留作兜底 |

**判据（下次别重新推导）**：

- 自动环节的失败**不一定**是红的。先看结论词：`skipped`、`conclusion: action_required`、
  `candidates: 0`、`0 failed / 0 total` —— 这四个都能出现在一个"成功"的 run 里。
- 过滤器读的字段要问一句**"它会不会是空/延迟/缓存"**。`mergeStateStatus` 就是缓存，
  而它恰好是这条链最关键的过滤器（§1.2）。
- 规则要与产物的**体积**对齐：`+1` 行规则配"每篇课写一行"的生成器，等于把批次挡在门外（§1.3）。

### 1.2 API 里"可以晚点才有"的字段不能当过滤器

`mergeStateStatus` 在 `gh pr list` 里是**缓存值**；每次合并进默认分支都会让所有 open PR 的缓存失效，
GitHub 在这之后**懒计算**，而列表端点不触发计算。于是候选集恰好在"刚有人合并过"的时刻最不可靠 ——
而那时恰恰是队列最该被推进的时候。

修法不是加 sleep，而是**换端点**：单个 PR 的 `GET /pulls/{n}` 会触发计算，读到 `unknown` 再重试。
同一件事在 §2 的"标签"上不存在（标签永远现读）。判据：**读缓存的端点 + 你恰好很在乎的过滤条件 = 一个
只在特定时刻错、且错得合法的系统。**

### 1.3 "合并了"不等于"通道能用"，"通道跑了"也不等于"事情做了"

今天之前，这条链上的每一步都曾经跑过、绿过、有记录，但**从头到尾没成功过一次**。
到达 `mergedBy: app/github-actions` 那一刻之前，没有任何单一读数能证明它可用。

判据：给这类"多段流水"写验收时，**只认端到端的那个读数**（这里是"PR 的 `mergedBy` 是
`app/github-actions` 且我没有手动触发"），中间任何一段的绿都不算证据。

### 1.4 先把量度的对象分清楚，再谈“改不改”

同一个“ugly slug”问题里有两层，代价差一个数量级，而我第一遍把它们算在了一起：

| 层 | 数量 | 代价 |
|---|---|---|
| **id**（文件名主干）| 94 条以表单标题开头 | 它只是 `/lessons/<id>/` 的**重定向源**，命中就 301 到真页——几乎零代价 |
| **页面 slug**（公开 URL，黏性）| **38 条**（`problem` 21 / `症状` 11 / `symptom` 6），全部 >60 字符 | 换它要动黏性映射，而现在的 `_redirects` **只会生成 id→slug**，不生成旧 slug→新 slug ⇒ 换 slug 等于让旧地址 404 |

所以“存量 94 条很脏”是一个把成本算大了的结论。判据：**在报“存量债务”之前，先确认那个量对象是否就是会被访问的那一个**——
重定向源与目标页在监控里长得一样（都能 200/301 回来），但改它们的代价完全不同。

### 1.5 结论式的坑：把“客户端的行为”记成“服务的缺陷”

`#5245`（200 + 声明 3713 + 实际 605 字节）一直被当 worker bug，并因此污染同族 intake 的判断。
今天用探针把两条 Accept 路径都量了：**70 次采样零短正文**；差异只在延迟 ——
`application/json` 的首字节**等于**末字节（整条拼完才发），`text/event-stream` 有早字节。
即"缓冲式 JSON + 会掐链路的中间层"，不是 server 发短正文。

顺带修掉一个数字误读：604/605 不是服务端的常量，`/api/health` 的完整正文就是 **603 字节**。
判据：**一个数字只有在它等于某个真实产物的大小时才是线索**；否则它只是链路断在那一刻的残骸。

## 5. 坑（本卷实际踩到的）

1. **`POST /actions/runs/{id}/approve` 用 owner token 就够**（vol 41 §3 悬账 1 写的"需 admin 级"不成立），
   但只对 `status=action_required` 有效；已 `completed` 的再 approve 返回 201 而状态不变。
   同一条分支批过一次之后，后续 push 的 run 不再卡。
2. **环境部署批不了**：`github-pages` 的 `pending_deployments` 返回 `current_user_can_approve: false`，
   只能人去 Actions 点。这是 `#2416`（活体追踪单）存在的原因 —— **不要关它**，关了 watcher 会新建一条。
3. **改课之后少跑一个生成器就红**，而且是两条不同的红：`A lesson was added or changed without
   re-running the generators`（`data/lessons.json` 与 `docs/data/` 没跟上）与
   `test_lessons_index_plain_fields`（`lessons/index.md` 里的值与 frontmatter 不一致）。
   页面路径是**黏性**的：改 title 不改公开 URL，所以页目录名会留着旧标题的片段。
4. **frontmatter 的 `verify:` 必须是单行**（lesson quality gate 会查）；把"修正文 fence"的正则
   跑在整份文件上会连 frontmatter 一起改坏，改前必须按 `---` 切出 frontmatter。
5. **本机 pytest 的假红又多了两条**：`test_cli_waits_on_a_missing_label_and_exits_two`、
   `test_check_documented_gates.py::test_a_missing_token_is_an_explicit_error_not_a_pass` ——
   都是 `subprocess` 输出在这台机器的 GBK 控制台下解码失败变成 `None`。在 `origin/main` 上同样失败。
6. **`git worktree` 在 WSL 里不可用**：worktree 的 `.git` 文件写着 Windows 绝对路径
   （`gitdir: C:/…`），WSL 的 git 报 `fatal: not a git repository`，于是生成器走"扫盘回退"分支。
   本卷那次扫盘结果与 tracked 集合一致（disk == tracked，1105 篇），但**这条要自己验**，
   否则就是一个安静的假绿（vol 41 §5.2 同族）。
