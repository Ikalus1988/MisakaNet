## 1. 这一轮定下来的判断（是决定，别再重新论证）

1. **`v1` 是 rolling major tag**，随 action shell 变更前移；要冻结版本 pin 到 commit。
   配套的是 UA 从 `v1.0` 移到 `v1.1`——否则"新版到底到没到人"这个唯一该问的问题无法回答。
2. **Marketplace 给不出任何使用数据**（没有面板，对任何人都是）。仓库自己的那份在
   `lesson_usage.user_agent`，由心跳面板读；口径三条：run ≠ 人、读不到 ≠ 0、说清数的是什么表。
3. **`/api/helpful` 的计数不迁移**到 `counters` 表。迁移会同时把所有已发布计数清零——那是关于
   一个证据数字的迁移决策，不是 bug 修复。缺口写在代码注释里，等需要原子性的那天再单开一条。
4. **E4 不给票**：helpful 票在任何数量下都只是 E3 提示；E4 只来自 `search_signals` 里两个以上
   不同 client 的真实检索。这一轮确认代码已经是这样（报告里"匿名两次即 E4"是**旧**行为）。
5. **外部扫描器的告警可以 dismiss，但必须换一条能自己失败的检查**。理由写在告警的 comment 里并
   指向那个检查；不写理由的 dismissal 不允许（本卷 §4 第一条）。
6. **batch PR 不自动合并**是设计，不是缺陷：它带 `data/`，而 `Auto-Merge Lessons` 只合并全部路径
   都在 `lessons/` 下的 PR。想让飞轮真正闭环，缺的是"人点一下"这一步，不是更多自动化。

## 4. 可复用的判据（比结论更值钱，下轮直接用）

1. **外部扫描器读的是文本，注释也算。** 修完一个告警后，若注释里还写着那个 API 的名字，它不会关。
   规矩与 `test_scanner_secret_patterns.py` 一致：**描述模式，不要复述它**。本轮的 `#399`/`#400`
   就是因为"解释修复的句子"把告警又造了一遍。
2. **dismiss 的正当性来自替换，不来自理由。** 一条 dismissal 只有配上一个"能自己失败的检查"才算
   处理；否则它只是把噪声移出了视野。`#397` 的 dismissal 指向
   `tests/test_workflow_checkout_is_pinned.py`——它把真不变量（**没有任何特权 workflow checkout 被触发
   run 的 head ref**）钉在十一处。
3. **本地绿 ≠ 矩阵绿，差的那条腿往往是语法/依赖而不是逻辑。** 本轮两次：一次是 f-string 里带关键字
   实参（3.12+ 语法，CI 的 3.11 腿直接语法错误），一次是旧 wheel 影响 `serverInfo.version`。
   判据：改完用 `ast.parse(..., feature_version=(3,11))` 过一遍，别等 CI 告诉你。
4. **"同一 action 在两个 workflow 里钉不同 SHA"是审查看不出来的洞。** 它只能靠跨文件测试发现
   （本轮 deploy 的 `setup-node` 写成了 github-script 的 SHA，导致**部署本身**失败了一整天）。
   同类：两个测试各有一份 JS→JSON 读取器，修一处漏一处。
5. **派生文件要挑着生成。** batch 工作流带上 `feed.json`（含 `generated_at`）就是**必然冲突**；
   它归每日同步所有。判据：这个文件的 diff 里有没有时间戳——有，就别放进 PR 载体。
6. **给报料者的回执是铁律，且必须走脚本。** 手写回执会漏字段；`emit_intake_receipt.py` 读
   `provenance.issue`，是唯一能同时对得上课程与 issue 的那条路。
