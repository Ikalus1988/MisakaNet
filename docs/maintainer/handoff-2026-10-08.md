## 29. 规则的语料比它守护的集合窄：它报的不是「没有泄漏」，而是「我看过的地方没有泄漏」

#3011 报的是 5 处、3 个文件。把 FR3 的语料**真的**铺满已发布面之后，实测是 **77 处、26 个文件**：

根因不是「没人改」，是三条结构性原因让**任何一次 CI 都看不见它**：

| 事件 | 传什么 | 覆盖 |
|---|---|---|
| `pull_request` | `--base <base.sha>` | 只判**本 PR 碰过**的报告 |
| `push` → `main` | `--base <before>` | 只判**本次 push 碰过**的报告 |
| `workflow_dispatch` | （无参 = 全量严格） | 实测累计运行数 **0** |

复核证据：最近 100 次运行全是 `pull_request`(71) / `push`(29)，**结论全部 success**；该 workflow 是
84 个里**少数没有 `schedule:`** 的（31 个有）。


## 30. 我的第一版扫描是个坏门禁：117 条里 68 条是假阳性

第一版把 FR3 铺到 `docs/**` 后报了 **117 条**，逐条归类才发现 **68 条是语料自己的脱敏简写**：

| 假阳性 | 条数 |
|---|---|
| `C:\Users\YourUsername` | 30 |
| `/home/.git-credentials` | 26 |
| `/home/your_username` | 10 |
| `C:\Users\REPLACE_ME` | 1 |
| `/mnt/c/Users/...` | 1 |

**会对这些开火的门禁，和永不失败的门禁是同一种病**——本仓在 #2045 里写过这句的另一半。所以加了
`_is_redacted()`，识别三种形状：

1. 占位词（扩了 `yourusername` / `your_username` / `replace_me`）；
2. **点文件**：`/home/.git-credentials` 捕获到的是 `.git-credentials`，它是 home **下面**的文件，不是账号；
3. **无字母数字的捕获**：`/mnt/c/Users/...` 是省略号，用户名不会是 `...`。

两个方向都钉在 `tests/test_field_reports_published_surface.py`（16 个用例：7 个"不是泄漏" + 6 个"是
泄漏" + 3 个行为/漂移）。它还带一条**生成物清单漂移守卫**——它在这份改动里**当场抓到了我自己漏的
`docs/_lessons_count.txt`**：那条守卫不是装饰。

## 37. 让声明说出它支撑得起的话：§34 那个二分法漏了第三个选项

§34 对定时审计那 3 条 finding 的判断是「修法是补上缺失的证据，而那份证据我没有；编一个配置路径比留着

第三项当时没被考虑：**把声明降级到证据实际支撑得住的程度**。§34 的场景恰恰不是「证据存在于某处而我们没

实测边界比想象的窄，这点必须一起记：

|---|---|
| `2026-09-16-setup-verification-2lll5.md` 的 FR4 + FR7 | **能**。声明集中在局部，`_declined()` 的 ±3 窗口够得到 |

## 38. #2258：重排顺序是个陷阱，两种单阶段顺序都错

报料问的是「文档链向本次运行才写出的产物，该怎么校验」。复现出的错误与它报的逐字吻合
（`AssertionError: missing link targets ['./verification-results.json']`，与报料里的 `AssertionError: verification-results.json` 逐字吻合）。

直觉修法「把链接检查挪到最后」实测更糟：

```
link check result : FAIL ['./verification-results.json']
artifact on disk  : {'checks': {...}, 'all_passed': True}
-> run 是红的，但一个声称 all_passed=true 的报告已经发布
```

两种单阶段顺序在**相反的方向**上各错一种：先查是假失败，后查是假回执。都不是顺序问题 —— 报告的内容
依赖检查结果，而检查又依赖报告是否存在，没有单一顺序能逃出这个循环。

改成两段：先对「文件系统 ∪ 本次运行声明的产出」解析，再写产物，然后**只对文件系统**解析一次。
豁免必须在第二段失效，否则「声明了产出却没写出来」的运行会两段都过。已变异验证。

## 39. #2469：自带 ≠ 可解析；可解析 ≠ 存在

`apply_patch` 不在本机 PATH（实测 `command not found`），但它是 GNU `patch` 的薄封装，语义在后者。
`patch` 2.7.6 与 `git apply` 实测结论相反：

| | 第二个 hunk 失败时，第一个文件 |
|---|---|
| GNU `patch` | **已经被改了**，并留下 `.rej` / `.orig` |
| `git apply` | **原封不动**，不留任何残留（全有或全无）|

两个实测细节值得留着：`patch` 会报 `succeeded ... with fuzz 1`（丢掉匹配不上的上下文照样应用），
所以 dry-run 变绿不等于补丁落在你以为的位置；以及 `printf a>f` 写出的文件没有末尾换行，会让一个
本该匹配的 hunk 失败 —— 补丁在肉眼相同的行上失败时，先查行尾再怀疑工具。

## 40. #3001：`usage` 这个词把整个 FAQ 清零了

`EVIDENCE_INTENT_RE` 里有一个**裸 `usage`** 备选，而 `usage` 是 CLI 报错里的超高频词。查询被判成
evidence 意图 → `filterByKind(results, "evidence")` → 而 FAQ 条目（`matchAnsweredQuestions` 的返回）
没有 `evidence_level`、没有 `evidence_refs` → `isEvidenceResult` 恒 false → **每一条 FAQ 命中都被滤掉**。

用仓库自己的函数跑：

```
query="npm usage error"                  kind=evidence  faq_survives=0
query="how do I configure X"             kind=all       faq_survives=1
```

这同时解释了此前排除的三条假设为什么都不对（本地 BM25 对 `usage` 查询返回正常命中；停用词只影响打分，
不参与意图路由；`matchAnsweredQuestions` 确实产出了结果，是下游滤掉的）。

修法是把 `usage` 锚回它本来的意图：`usage\s*(?:count|of|number|次数|数)`。

**这条路由此前没有任何测试** —— 这就是它能静默清空 FAQ 而无人察觉的原因。新测试直接对仓库里那个正则
常量求值（把 literal 抽出来交给 node），因为把正则复制一份到测试里，它就会在别人改了 worker 之后继续
「通过」。

生产双向验证（部署 `a91baa5` success 之后，同一端点三次调用，只改查询词）：

| 查询 | 结果 |
|---|---|
| `…by exact ID`（基线） | 4 hits，含 3 条 `type=faq`：2463=100、2478=67、2858=33 |
| `…by exact ID usage` | **FAQ 全部存活**：2463=100、2478=57、2858=43 ← 修复前会是 0 |
| `…by exact ID usage count` | `no_match: True`、0 hits ← 原意图仍在 |
