### 2.1 #2766：「地板在测量生产服务不到的语料」——**不成立**

立项时的判断是：`search-dual-floor.test.mjs` 的语料含 28 篇 draft，而生产只服务 published，
所以地板量的是生产服务不到的东西，应当按 published 过滤后重校准。

**实测：生产的检索路径根本不过滤 `status`。** draft 课照常返回，只是在 compact/summary 命中上
多带一个 `status` 标记——因为「draft 该不该可检索」本身还是未决产品问题（#2270），
worker 的选择是**把事实暴露出来，而不是替产品做决定**（`lessonStatusMarker`，`register-proxy-sw.js:733`）。

直接打生产确认（不是只信仓库文档）：

```bash
curl -sS -X POST https://misakanet.org/mcp -H 'Content-Type: application/json' \
  -H 'MCP-Protocol-Version: 2025-06-18' -H 'Origin: https://misakanet.org' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"misakanet_search",
       "arguments":{"query":"FANUC Robot Alarm Code Reference Table","top":3}}}'
# → top-1 = fanuc-alarm-code-reference，带 "status":"draft"
```

所以「生产在服务什么」**就是整个文件**。按 published 过滤 = 量一个不存在的系统：

| 语料 | English hit1/hit3 | CJK hit1/hit3 |
|---|---:|---:|
| 整个文件（457） | 16/20 · 19/20 | **11/22 · 16/22** |
| 仅 published（427） | 16/20 · 19/20 | 10/22 · 15/22 |

**地板维持 11/15 不动。** hit3 高出 1 格但**刻意不抬**：那一格是 #2762 的 19 篇 lesson 挪动了排序，
不是检索变好了；把地板钉在某个语料规模上，等于把这道闸门交给无关的语料涨落。

真正该修的是底下的脆弱性：zh-18 整行的通过/失败挂在一篇没人承诺过的 draft 上，而它的 `note`
原本只是 lesson 标题。哪天这篇被删，最省事是把整行删掉——而 `ZH.total >= 20` **拦不住 22 变 21**，
中文覆盖会静默缩小，且所有测试照样全绿。现在守卫要求非 published 的 `expected` 必须在 `note` 里写明。

### 2.3 顺手挖出来的：**线上 worker 已冻结 3 天，没有任何机制报警**

用户报"前端 7 天网络活动图表不自动更新"。**不是前端 bug**——前端是对的，它先打实时接口、
失败才退回提交快照，而那个接口：

```
GET /api/activity/history?days=7  →  404 {"error":"Not found"}   # = register-proxy-sw.js:7736 的 /api/* 兜底
```

handler 早在 `88b360004`（#2692）就进了 main，完整且无条件，缺 store 返 503、内部异常返 502，
**不可能返 404**。所以只能是线上 bundle 没有这段代码。两条部署流水线状态不一致，正好凑成这个现象：

| | 部署方式 | 状态（冻结期间） |

| 前端 `docs/` | Workers Builds: misakanet-web | ✅ 成功 → **新前端** |

机制：`environment: release` 需人工审批，而 `concurrency: cancel-in-progress: true` 让**后一条 push
取消前一条还在等审批的 run**。最后一次成功部署是 2026-10-01T16:42，之后 6 次全 cancelled，
最后 newest 那条从 10-03 13:49 一直 waiting。**未上线的是 5 个提交 / 5 个已合并 PR**：

### 5.2 需要决定：**#2779 的检测盲区**（我建议做）
部署冻结是**靠人盯着**解掉的，系统自己不知道。`deploy-worker.yml` 的 post-deploy 校验比的是

## 6. 本轮新增的坑（能省时间）

### 6.1 模块级 memo 让"对比两个语料"静默退化成"量同一个语料两遍"
worker 在**模块作用域** memo 了 BM25 索引（`_bm25Index` / `_bm25IndexExpiry`）。
同一进程里量两个语料，第二个**静默复用第一个的索引**——于是"全量 vs 仅 published"的差值读出来是 **0**。
我因此连错三次才定位到（第一次还误以为是"多一个字段改变了排序"）。
**一个进程只量一个语料。** 已写进 `search-dual-floor.test.mjs` 的文件头。
附带：`ghapi` 那种共享 token 的并发循环还会被限流**降级**结果（不是报错，是安静地少召回）——
一度让我以为 published 过滤没有影响。

### 6.2 「重跑生成器」只适用于 lesson 文件冲突，**不适用于 workflow 步骤冲突**
两者解法相反，且同一个文件里就写着这个对比：lesson 文件撞车 → "哪边都不要，重跑生成器"；
workflow 步骤撞车 → "三个步骤都留"。**别把前者当默认解法套上去。**

### 6.3 我自己开的 PR 也会互相撞（同一条教训的第二次）
三个重新落地的 PR 都重生成 `data/lessons.json` + 页面 + ranking snapshot，
所以它们**彼此冲突**，必须串行合，且每合一个就要把下一个 rebase + 重跑生成器。
#2771 那次 rebase 还因为 `git rebase --continue` 卡住（index 里已无冲突项却仍拒绝继续），
最后是 abort 重做成单 commit 更干净。**批量开同源 PR 前先想好合并顺序。**

### 6.4 `tests/fixtures/ranking-snapshot.json` 是 lesson PR 的一部分
它 pin 了**排名路径和分数**，所以语料一变就红（#2762 带着它）。忘了重跑 → 交一个必然红的 PR。
而且它是"先决定改动是否可接受，再重跑"的那种快照，**必须核对再重跑**：
- 1 篇课：310 行里 0 处重排，纯分数漂移（max 0.0003）
- 5 篇课：**0 处 top-1 变动**，8 处重排全是 ≤0.001 的近似打平（0.4869/0.4860、0.4963/0.4959、
  三个 CI/DCO 课挤在 0.6118–0.6126），另 2 处是 rank-10 尾部新课进入

### 6.5 版本号相同的陈旧部署是**隐形**的
见 §2.3 / §5.2。任何"用版本号验证部署"的检查，对 `fix:`/`feat:` 提交都是瞎的——
而那正是日常的大多数。**下次看到"线上和 main 版本一致"不要当成部署是新的。**

### 6.6 已合并的东西会被后续提交**静默删掉**
#2485 的 `Check doc freshness` 步骤合入后，被 #2729 插入锚点注释时的一次
**替换**（而非插入）连带删掉，脚本留在 main 上闲置，`grep` 只在注释里命中它。
**加步骤要插在注释块之后，不要动注释块本身**；给"已合但可能已失效"的东西留一条门禁
