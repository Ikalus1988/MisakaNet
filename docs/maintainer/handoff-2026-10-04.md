### 1.3 MCP stdio 流被一行 print 污染（#2806，main 上最严重的一个）

`misakanet/search/engine.py::_load_docs_cached` 在重建 L2 缓存时 **裸 `print()` 到 stdout**。
它在**数据路径**上（每次检索都跑、与输出模式无关、MCP search handler 会走到），
而 `misakanet/server/protocol.py:199` 的 JSON-RPC 响应**正是逐行写 stdout**（stdio 传输）。

实测（清空 L2 缓存后跑 `scripts/mcp_server.py`，initialize + `misakanet_search`）：

```
line 1: {"jsonrpc":"2.0","id":1,...}   有效
line 2:   📦 L2缓存: 464 篇变动          ← 不是 JSON
line 3: {"jsonrpc":"2.0","id":2,...}   有效
```

**逐行解析 stdout 的客户端会在第 2 行失败**，而且恰好发生在**新装后第一次检索**。
热缓存时不可见 —— 那个 print 是 `if changed:`，所以运行中的服务器永远看不到自己。

`misakanet/profile.py` 同样的形状（6 处）打在 CLI 的 `--json` 上。
修法：人类提示一律走 **stderr**。同文件 560/603 行的 cross-encoder 警告**本来**就是
`file=sys.stderr`，那条 L2 提示是自己文件里的异类。

**附带解决了一个测试脆弱性**：`test_search_quota.py` 早就把"本地命令 `--json` 输出可解析"
当作契约，但它是**顺序依赖**的 —— 提示是一次性的，谁先跨过阈值谁触发，全新 profile
会在套件跑到一半时触发。我在**未修改的 main** 上复现了同样的失败，这才是它与任何改动无关的证据。
现在三种 profile 状态（`(newcomer,0)` / `(newcomer,2)` / `(active,18)`）下都通过 ——
**根因修复本身消除了这个顺序依赖**。

**这个仓库只有一处 stdout 帧传输**（`protocol.py:199-200`），HTTP MCP 是独立服务器不受影响，
所以暴露面是完整的。

## 6. 本轮新增的坑（能省时间）

### 6.1 模块级 memo 让"对比两个语料"静默退化成"量同一个语料两遍"
worker 在**模块作用域** memo 了 BM25 索引（`_bm25Index` / `_bm25IndexExpiry`）。
同一进程里量两个语料，第二个**静默复用第一个的索引**——于是"全量 vs 仅 published"的差值读出来是 **0**。
我因此连错三次才定位到（第一次还误以为是"多一个字段改变了排序"）。
**一个进程只量一个语料。** 已写进 `search-dual-floor.test.mjs` 的文件头。
附带：`ghapi` 那种共享 token 的并发循环还会被限流**降级**结果（不是报错，是安静地少召回）——
一度让我以为 published 过滤没有影响。

### 6.2 「重跑生成器」只适用于 lesson 文件冲突，**不适用于 workflow 步骤冲突**
两者解法相反，且同一个文件里就写着这个对比：lesson 文件撞车 → "哪边都不要，重跑生成器"；
workflow 步骤撞车 → "三个步骤都留"。**别把前者当默认解法套上去。**

#2771 那次 rebase 还因为 `git rebase --continue` 卡住（index 里已无冲突项却仍拒绝继续），
最后是 abort 重做成单 commit 更干净。**批量开同源 PR 前先想好合并顺序。**

### 6.4 `tests/fixtures/ranking-snapshot.json` 是 lesson PR 的一部分
它 pin 了**排名路径和分数**，所以语料一变就红（#2762 带着它）。忘了重跑 → 交一个必然红的 PR。
而且它是"先决定改动是否可接受，再重跑"的那种快照，**必须核对再重跑**：
- 1 篇课：310 行里 0 处重排，纯分数漂移（max 0.0003）

### 6.5 版本号相同的陈旧部署是**隐形**的
