### 2.3 变异工具自己也不可信——一次是它的错，一次是我的错

**工具报 MISMATCH，而那个 MISMATCH 是假的。** `read_text`/`write_text` 做 universal newline
转换，读到内存的 CRLF 变 `\n`、写回即 LF；于是被变异文件的行尾被改掉，而校验拿 LF 文本的
哈希去比 `shutil.copy2` 已按字节还原好的 CRLF 文件——**报了一个它自己造成又自己修掉的损坏**。
一个在没损坏时报损坏的工具比没有工具更糟：它训练你跳过那个本来能抓到真损坏的检查。
改成字节读写、按原有 EOL 写回、字节对字节校验之后，**我立刻引入第二个洞**：9 个变异里 3 个
报「变异没生效」，因为我把「每次从磁盘重读」写成了「每次从原文改」，后一条读到的是上一条
留下的文件。

## 4. 待办与决策

### 4.1 #2959 的三条 windows 腿：根因是绕开了 `posix_shell`，本轮已修并加了门禁

`test (windows-latest, 3.11/3.12/3.13)` 失败于 `test_workflow_hygiene.py` 的两个 tag-pin 用例，
**来自 #2959 第一个提交 9ef165cc**。对照 run `37592032941`（9ef165cc）失败的是同样两个用例，
所以不是加界改动引入的。

根因不是 CRLF（我先猜错了，见 §4.1.2）：`_run_pinning_check` 直接 `subprocess.run(["bash", ...])`，
而 `windows-latest` 上 PATH 里的 `bash` 是 `C:\Windows\System32\bash.exe`——**WSL 启动器**，
该镜像没装任何发行版。日志里的证据是断言失败时带着一段 UTF-16LE 横幅
（`W\x00i\x00n\x00d\x00o\x00w\x00s...`）：子进程打印的是这句话，**脚本根本没跑**。

仓库里 `scripts/posix_shell.py` 正是为这个失败建的（2026-09-21，当时「~20 个测试在每个 PR 上
变红」），15 个测试文件已经在用 `require_posix_shell()`。缺的不是 helper，是**没有任何东西要求
新测试用它**。修法：改用 helper + 脚本路径转正斜杠（反斜杠在 shell 里是转义符）。

**新门禁 `tests/test_shell_invocations_are_portable.py`**：禁止任何测试把字面量 shell 名交给
`subprocess`，除非它声明 POSIX-only。3/3 变异全红。

**CI 实测（run `37603815929`，2026-10-07）**：三条 windows 腿由红转绿——
`3.11 pass 7m34s`、`3.12 pass 7m47s`、`3.13 pass 5m50s`，macOS 三条同样全绿，
四条必需检查（DCO / `audit` 8m8s / `gate` / `test (ubuntu-latest, 3.11)` 3m53s）全绿。
**这是这个 PR 第一次整矩阵无红。**

#### 4.1.2 一条我写了、量了、然后被自己删掉的规则

门禁的第一版还有第二条：禁止用 `write_text` 写 `.sh` 而不 pin `newline="\n"`。理由是
`write_text` 在 Windows 上发 CRLF，而 bash 把 `\r` 当成 token 的一部分。我**确实量到了**
Linux bash 上 CRLF 脚本会失败：

```
crlf_probe.sh: line 1: set: -: invalid option
crlf_probe.sh: line 2: syntax error near unexpected token `$'do\r''
```

但这条规则在仓库里会命中 **9 处**，而这 9 处**在 `windows-latest` 上全是绿的**——
包括断言 `returncode == 0`、断言桩 `gh` 确实被调用的那些。**如果 CRLF 在 Git Bash 下是致命的，
那些腿应该是红的。** 它们不是。所以那条推论（从 Linux bash 外推到 Git Bash）不成立，
规则被我删掉了，而不是把措辞改软。

教训和 §2.3 是同一条：**「我测到了」不等于「我测的是这件事」。** 那次测的是 Linux bash，
写进规则的却是 Git Bash。9 处误报就是这条推论的价格。

`test_workflow_hygiene.py` 里仍然保留 `newline="\n"`，但注释已改成如实陈述：
它让字节与平台无关，**不是**在这里修掉了一个观测到的失败。

#### 4.1.3 变异验证在新门禁里抓到的洞

第一条变异（把字面量 `"bash"` 放回 `test_workflow_hygiene.py`）**没被抓到**。
原因是我把豁免写成「文件里 import 过 `posix_shell`」——而那个文件确实 import 了它，
**import 过 helper 和这处调用用了字面量是两回事**。豁免只保留给 POSIX-only。
改完 3/3 全红。这是本任务里第四次出现同一个形状，只是这次在我自己刚写的门禁上。

## 7. #2971：密钥扫描器报告「没发现密钥」的对象是它没打开过的文件

`scan_credential_patterns` 与 `check_env_var_handling` 都以 `except Exception: return hits` 结尾，
空列表与「读过了、里面没有」不可区分。临时树上的复现（修复前）：

```
readable   -> [{'file': 'leak.js', 'line': 1, 'type': 'GitHub personal access token'}]
chmod 000  -> []      ← token 还在盘上
directory  -> []
dangling   -> []
```

**后两种不是假想输入**：`Path.rglob("*.js")` 会吐出名为 `*.js` 的子目录和悬空符号链接，
两者都会经 `secret_scan_files()` 到达扫描器（这一点在测试里断言过，不是假设）。

修法：`_read_for_scan` 只把 `OSError` 翻译成 `UnreadableScanTarget`；
调用方把它计入 `errors`（退出码非零——**这里的红是可操作的，warning 不是**）；
并且成功那行改成 `elif not unreadable:`——**一次没有发生的扫描不该打印体检报告**。

3/3 变异全红（还原静默兜底 / 去掉成功行的条件 / 把未读记成 warning），脚本按字节还原。

### 7.1 为什么测试**没有**用 `chmod 000`

issue 的复现用的是 `chmod 000`，但这个探针有两种方式会什么都没测：
root 本来就能读；**本仓检出在 `/mnt/c`（DrvFs），Windows 文件系统直接忽略 POSIX 权限位**——
实测 `chmod 0o000` 之后扫描照样返回了那条命中。这样的测试会绿着通过而不证明任何事。
目录与悬空符号链接在任何 uid、任何文件系统上都读失败，覆盖同一个 handler。
`test_a_chmod_000_probe_is_not_used_because_it_cannot_fail_reliably` 把这个理由留在原地，
免得下一轮有人重新推一遍。

另有一个用例断言这道门**仍然可以是绿的**，所以新规则不能靠「永不通过」来满足。

## 38. #2258：重排顺序是个陷阱，两种单阶段顺序都错

报料问的是「文档链向本次运行才写出的产物，该怎么校验」。复现出的错误与它报的逐字吻合
（`AssertionError: missing link targets ['./verification-results.json']`，与报料里的 `AssertionError: verification-results.json` 逐字吻合）。

直觉修法「把链接检查挪到最后」实测更糟：

```
link check result : FAIL ['./verification-results.json']
artifact on disk  : {'checks': {...}, 'all_passed': True}
-> run 是红的，但一个声称 all_passed=true 的报告已经发布
```

两种单阶段顺序在**相反的方向**上各错一种：先查是假失败，后查是假回执。都不是顺序问题 —— 报告的内容
依赖检查结果，而检查又依赖报告是否存在，没有单一顺序能逃出这个循环。

改成两段：先对「文件系统 ∪ 本次运行声明的产出」解析，再写产物，然后**只对文件系统**解析一次。
豁免必须在第二段失效，否则「声明了产出却没写出来」的运行会两段都过。已变异验证。

## 39. #2469：自带 ≠ 可解析；可解析 ≠ 存在

`apply_patch` 不在本机 PATH（实测 `command not found`），但它是 GNU `patch` 的薄封装，语义在后者。
`patch` 2.7.6 与 `git apply` 实测结论相反：

| | 第二个 hunk 失败时，第一个文件 |
|---|---|
| GNU `patch` | **已经被改了**，并留下 `.rej` / `.orig` |
| `git apply` | **原封不动**，不留任何残留（全有或全无）|

两个实测细节值得留着：`patch` 会报 `succeeded ... with fuzz 1`（丢掉匹配不上的上下文照样应用），
所以 dry-run 变绿不等于补丁落在你以为的位置；以及 `printf a>f` 写出的文件没有末尾换行，会让一个
本该匹配的 hunk 失败 —— 补丁在肉眼相同的行上失败时，先查行尾再怀疑工具。

## 40. #3001：`usage` 这个词把整个 FAQ 清零了

`EVIDENCE_INTENT_RE` 里有一个**裸 `usage`** 备选，而 `usage` 是 CLI 报错里的超高频词。查询被判成
evidence 意图 → `filterByKind(results, "evidence")` → 而 FAQ 条目（`matchAnsweredQuestions` 的返回）
没有 `evidence_level`、没有 `evidence_refs` → `isEvidenceResult` 恒 false → **每一条 FAQ 命中都被滤掉**。

用仓库自己的函数跑：

```
query="npm usage error"                  kind=evidence  faq_survives=0
query="how do I configure X"             kind=all       faq_survives=1
```

这同时解释了此前排除的三条假设为什么都不对（本地 BM25 对 `usage` 查询返回正常命中；停用词只影响打分，
不参与意图路由；`matchAnsweredQuestions` 确实产出了结果，是下游滤掉的）。

修法是把 `usage` 锚回它本来的意图：`usage\s*(?:count|of|number|次数|数)`。

**这条路由此前没有任何测试** —— 这就是它能静默清空 FAQ 而无人察觉的原因。新测试直接对仓库里那个正则
常量求值（把 literal 抽出来交给 node），因为把正则复制一份到测试里，它就会在别人改了 worker 之后继续
「通过」。

生产双向验证（部署 `a91baa5` success 之后，同一端点三次调用，只改查询词）：

| 查询 | 结果 |
|---|---|
| `…by exact ID`（基线） | 4 hits，含 3 条 `type=faq`：2463=100、2478=67、2858=33 |
| `…by exact ID usage` | **FAQ 全部存活**：2463=100、2478=57、2858=43 ← 修复前会是 0 |
| `…by exact ID usage count` | `no_match: True`、0 hits ← 原意图仍在 |

## 51. #2759：一个在构造上就不可能失败的复现

上一轮我在这里记的是「根因已复现（dsh 传递依赖），修法未验证」。这句话的前半段是错的。

报料方给出的判据是：裸 `node -e` 里 `createRequire('<profile>/node_modules/misakanet/index.js').resolve('@deepseek-ai/dsh-mcp-client')` → `RESOLVE FAILED`。

但 dsh 的 launcher 文档写得很直白（`@deepseek-ai/dsh-app-boot/README.md`）：

> The launcher installs the runtime resolution on Node's internal ESM and CommonJS resolvers **before profile rows mount**.

> A profile link to an external directory admits its importers to **peer-aware ancestor lookup** … current `D/package.json` **peer names present in the runtime table use the runtime package**。

**那个探针跑在没有 launcher 的裸 Node 里，拦截层按构造就不存在。** 它唯一能证明的是「原生查找失败」，
而文档已经说了原生查找会失败。同一份文档还说「Runtime resolution creates no links」——所以磁盘上根本

路由条件只有一条（`lib/index.js:1479`）：

```js
if (ancestorSet.has(searchPath) && readPeerNames(directory).has(name)) {
```

`readPeerNames`（`:1224`）**只读 `peerDependencies` 的键**。本仓 `package.json:61` 已声明。

**容易踩的下一个坑：** `peerDependenciesMeta` 里的 `"optional": true` **不参与**路由判定 —— optional 管安装，
不管查找。解析读的是 `peerDependencies` 的名字。

报料方第 4 步「symlink 宿主那份不够」也已被文档解释：*"A nearer physical package precedes a later peer
declaration"* —— 实体 symlink 先赢查找，然后客户端卡在它自己的 9 个 `peerDependencies` 上。那是 workaround
的副作用，不是契约的反例。

**没有闭合的部分：** 我没有实跑一次 boot 观察到 `misakanet_search` 出现在工具列表里。所以 issue 保持 open，
我贴的是证据与边界，不是结论。

**但有一条比「给我 traceback」更直接的下一步，是我在第一条回复里漏掉的：** #3009（commit `2155185`，
