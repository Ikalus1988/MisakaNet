## 2. 本会话最重要的一条：**"不可能失败的检查"这个形状，我在这个任务里连犯三次**

三次都不是疏忽，是同一个判断习惯的产物：**把一个仓库级常量当成了对每个 job 都成立的界。**
每一次的修法都是"让常量变成实测值"，而第三次证明了前两次连改法都还没到位。

### 2.1 第一、二次：门禁的第一版有两条规则，两条都不成立

初稿要求：(a) 每个界都必须超过**全仓最慢的 job**（7.5 分钟）；(b) **没有界能超过 60 分钟**。

- (a) 错在**站不住**：它拿一个 `windows-latest` 测试腿的耗时去约束一个 20 秒就完的 job。
  而且它是"一个仓库级常量冒充一个 per-job 的事实"——这正是这个仓库反复在消灭的形状。
- (b) 错在**会 redden 一个有意设的界**：`benchmark-workers-ai.yml` 的 90。
  惩罚经过考虑的选择的规则，最终是被删掉的规则——`tests/test_automated_prs_skip_llm_review.py`
  记着三条这样被删掉的规则。

改法不是"把 60 调大"，而是**换成按 job 对账**：只有实测过的 job 才进表，
拿它**自己**的实测最长耗时去比它**自己**的界。见 §3.3。

### 2.2 第三次：变异验证抓出来的，是我自己写的一条不可能失败的检查

6 个变异里有 2 个活了下来。原因是 `test_the_added_bound_is_derived_from_a_measurement_rather_than_taste`
比较的是**两个常量**（`OBSERVED_MAX_JOB_MINUTES < ADDED_BOUND`，即 7.5 < 30）：

```python
assert OBSERVED_MAX_JOB_MINUTES < ADDED_BOUND
```

**工作流怎么改，这条断言都不可能变红。** 它 present、green、且不执行任何东西——
和我在同一份文件里刚删掉的那两条规则是同一个形状，换了个位置而已。

这条**保留**，但它的 docstring 自己说清楚了它是干什么的：它不是门禁，是**把 30 这个数的推导过程
钉在代码里**，好让"改 `ADDED_BOUND` 却没改实测值"成为一个可见的动作。真正读仓库的是 §3.3 那条。

### 2.3 第四次：**变异工具本身也不可信**，而且修了它之后我又引入了一个新洞

这一节值得单独记，因为它是我在这个任务里花时间最多、且最接近"白干"的一段。

**第一版工具报 MISMATCH，而那个 MISMATCH 是假的。** 它用 `read_text`/`write_text` 读写工作流，
而这两个函数做 universal newline 转换：读到内存的 CRLF 变成 `\n`，写回去就是 LF。
于是**每个被变异的文件都被留在了错误的行尾上**，而校验步骤拿这个 LF 文本的哈希
去比 `shutil.copy2` 已经按字节还原好的 CRLF 文件——**报了一个它自己造成的、并不存在的损坏**。

> 一个在没损坏时报损坏的工具，比没有工具更糟：它训练你跳过那个本来能抓到真损坏的检查。

修法：读写都走 bytes，`\n` 归一化后按文件原有 EOL 写回，校验比**字节对字节**。

**然后我立刻引入了第二个洞。** 改完之后 9 个变异里 3 个报"变异没生效"——因为我把
"每次从磁盘重读"换成了"每次从原文改"，写反了：后一条变异读到的是**上一条变异留下的文件**，
自然匹配不到要替换的那一行。

> 这两个洞是同一个：**验证工具的失败信息，被当成了被验证对象的结论。**
> "没生效"被读成"门禁没抓住"，而真实原因是工具自己坏了。
> 所以验证工具的错误信息必须能区分"规则没抓住"和"我没改成"——
> 脚本现在分开报：`mutation produced no change` 与 `[FAIL] <label>`。

## 5. 待办与决策

### 5.0 #2959 的三条 windows 腿是红的，**且早于本轮改动**

CI 上 `test (windows-latest, 3.11/3.12/3.13)` 三条腿失败，用例是
`tests/test_workflow_hygiene.py::test_a_tag_pin_is_still_reported` 与
`test_a_tag_pin_naming_a_sha_elsewhere_is_still_reported`——**都来自 #2959 的第一个提交
9ef165cc，不是本轮加界改动**。证据是对照 run：`9ef165cc` 的 ci-cross-platform run
`37592032941` 同样是 failure，且失败的是同样这两个用例。

根因（读代码，未修）：`test_workflow_hygiene.py` **全文没有任何平台守卫**——
`grep -n 'skipif|requires_posix_shell|platform'` 命中 0 次，而同仓库的
`test_lesson_notify_payload.py` 用的是 `from posix_shell import require_posix_shell`
加 `pytest.mark.skipif(sys.platform == "win32", ...)`。这两个用例会起 shell 跑 grep 循环，
在 Windows 上自然跑不通，且没有 skip。

**它不挡合并**：ruleset 23826057 的必需检查只有 `DCO`、`test (ubuntu-latest, 3.11)`、
`gate`、`audit`，本轮四项全绿，PR 状态 MERGEABLE。
**修法有取舍，本轮没做**：加 skip 会少掉 Windows 上对 pinning 规则的覆盖；
真修就得让那个 shell 循环在 Windows 上可用。属 owner 决定。
