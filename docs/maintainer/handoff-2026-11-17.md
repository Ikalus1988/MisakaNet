## 1. 本轮的判断（下次别重新推导）

### 1.1 合并 ≠ 上线 —— 而这道差在写这一卷时自己合上了，也只合了一半

`deploy-worker.yml` 走 `environment: release`，只有 owner 能批。写这卷时它挂着一个待批 run（`44029146695` /
`7081b9e87`，即 `#5161` 与 `#5162` 两条搜索修复），`/api/health` 还写着 `b82410a5`（`#5097`，11-16 10:01）。
那半天里，"两条 PR 说语料读已挪到 KV 并加了 8 秒预算"与"生产 p95 = **8834 ms**、corpus read **7581 ms**"
可以同时为真 —— 因为 PR 引用的 6337 / 6440 描述的不是正在跑的代码。

随后 owner 批了这次部署：`/api/health` 的 `commit_sha` 变成 `7081b9e87`。**但 AE 窗口里的 8834 ms 没变。**

**判据（两半）**：

1. 报"修好了"之前先读 `/api/health` 的 `commit_sha`，与 `origin/main` 比；不一致时所有性能读数都只描述**旧代码**。
2. 读完之后**按部署时间切窗口**。今天的 8834 ms 是部署前累积的 p95，部署后几分钟的流量不足以改写它 ——
   拿旧窗口的数当部署后的证据，与拿老代码当新代码是同一个错误的反面。`dist` 分支出新产物也不等于上线
   （那是站点产物，worker 另走审批）。

### 1.2 搜索的成本几乎全在一处，别的地方都是舍入

近 24 小时分阶段 p95（526 次搜索里 295 次带 phase）：

| 阶段 | p95 |
|---|---|
| corpus read (memo/KV/D1) | **7581 ms** |
| BM25 index (KV) | 1004 ms |
| semantic fallback | 774 ms |
| scoring | 0 ms |

所以"搜索慢"的下一步永远是 corpus read，"该动哪里"由这个比值定，不由直觉定 —— `#5161` 的方向正是
这个数给的。**仍未解释的是 ~1.4M D1 rows / 每次搜索**：`/api/lessons?q=` 是 **Enter** 触发而不是每次按键
（`#5162` 里已更正自己之前的说法），所以那个量级还得另找来源。这是下一轮第一个要测的东西，
也是唯一能说"KV 化之后还剩多少"的基线。

部署生效后再打同一个查询（`/api/lessons?q=pip`，8 次）：边缘缓存命中 **1.1 s**、未命中 TTFB **5.7 s**
（`Cache-Control: public, max-age=120, s-maxage=120`），而另外几次是 **连接层** 的失败 —— `000`（50 s 无响应）
与 `curl: (56) Failure when receiving data from the peer`，全程没有 HTTP 状态码。后者发生在 handler
**之前**，worker 侧的 8 秒预算管不到它；能管的只是"进了 handler 之后不许挂到边缘超时"。
所以"请求失败"这件事至少有两层，混在一起谈会把预算的效力和边缘的稳定性算成一件事。

### 1.3 squash 合并让 `git cherry` 说谎，判分支残留要看 PR

本地 **168** 条分支：**129** 条能对到已合并 PR，**0** 条有 open PR。用 `git cherry origin/main <b>`
分类会得到"57 条有 unique 提交"——抽查 3 条（`#3676` / `#4752` / `#4912`）全是 **squash 合并**过的。

**判据**：判一条本地分支是否残留，用 `gh pr list --state merged --head <branch>`，不要用 patch-id；
squash 之后 patch-id 必然不同，看起来像有活干。批量核对时注意 `gh pr list --limit` 有上限，
超出窗口的 PR 会显示成"没有 PR"（`feat/crash-search-first` 就是被这样误判的）。

### 1.4 发布的红是重复路径，不是发布失败

`misakanet-publish.yml` 同时被 `release` 事件与 `workflow_dispatch` 触发。11-15 / 11-16 / 11-17 三次发布，
每次都跑了两遍：dispatch 那遍红（`npm error code E409 ... Cannot publish over previously staged version`），
release 那遍绿，而 registry 最后是**对的**（3.19.0：PyPI 14:56:23Z、npm dist-tag `latest` 14:57:30Z）。

**判据**：判发布成功读 registry（`pypi.org/pypi/misakanet/json`、`registry.npmjs.org/misakanet` 的 dist-tags），
不要读 run 结论。那句 E409 的措辞（"previously staged"）会让人去 npm 后台找 staged publish，
而实际上版本已经上线了 —— 这次差点就去点了不该点的按钮。

### 1.5 GSC 这笔账卡在凭据，不卡在时间

vol 39 记的是"11-16 之后才有行"。今天复查：本机**既没有 `gcloud`，也没有 service-account json**，
`scripts/gsc_pull.py` 的三条取凭据路径一条都走不通。所以首拉要靠 owner 提供一份 service-account key
（并把它加为属性的用户），否则这笔账会一直显示成"在等时间"，而时间到了它也不会自己好。

### 1.6 数字必须带口径，否则每一卷都对不上

同一个问题，三种量法给出三个数（今天实测）：`question` 标签 **167** 条、标题含 `[Question]` **217** 条、
`needs-answer` **170** 条。vol 39 写的"59 条 open question"没记口径，因此无法与今天对比 ——
它可能一直是正确的，只是不可比。

**判据**：交接件里每个积压数字后面跟一句它怎么来的（label / title / search query）。数字会漂，
口径漂一次就再也对不上了。

## 5. 坑（本轮实际踩到的）

1. **`/tmp` 在 Git Bash 里写得进去，Windows 的 `python3` 读不出来**（`FileNotFoundError`）。
   脚本产物落在仓库相对路径或 `C:\tmp`，别用 `/tmp`。
2. **待批部署会让"合并了"看起来像"修好了"**。§1.1 那个 8834 ms 就是这么来的：
   一条 PR 的正文给的是合并前的基线，而生产跑的是更旧的代码。
3. **远端分支合并后被自动删除，本地同名分支还在**：`git status`、`git log` 都正常，
   只有 `git ls-remote` 才看得出远端已经没有了；此时再 `push` 就是**重建**一个没有 PR 的孤儿（§3 第 8 条）。
4. **一条红的发布 run 不等于发布失败**。§1.4 那个 E409 的文案会把人引向 npm 后台的
   "Staged publishes"，而去点那里是这次唯一差点弄错的动作 —— 先读 registry，再决定要不要动后台。
5. **`curl --max-time` 打生产会把两种失败混成一种**。`000` + 满超时可能是**边缘连接**没起来，
   不是 worker 超预算；分清楚靠的是 `-D -` 看有没有任何响应头，以及同一查询多打几次看分布。
6. **交接件不要写"做了什么"**。这一卷初稿里曾有一节复述 11-16 的 intake 改造链路，
   按 `handoff-rules.md` 第五条删掉，只留指针 —— 详情在 PR 页面和那两份专文里。
