## 113. D1：先付 $5，再谈优化（决策记录）

### 113.1 事实

CF 面板（2026-10-19 单日）：**Rows read 6.24M / 5M**，Rows written 7.09k / 100k，storage 66MB / 5GB。
官方价目（[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)，2026-04-21 版）：

| | Workers Free | Workers Paid（$5/月） |
|---|---|---|
| Rows read | **5M / 天** | 25B / 月含，超出 $0.001/M |
| Rows written | 100k / 天 | 50M / 月含，超出 $1.00/M |
| Storage | 5GB | 5GB 含，超出 $0.75/GB-mo |

按当前用量折算到月：读 **≈187M = 25B 的 0.75%**，写 **≈213k = 50M 的 0.4%**，存储 **66MB = 1.3%**。
→ **付费档 = $5/月，超量为 $0。**

### 113.2 结论：先买，再优化；两件事不冲突

**先买 `Workers Paid`（$5/月）**，因为额度打穿带来的不是"慢一点"，而是一整天的功能失效链：
注册 `storage_unavailable` → BM25 索引冻结（新课程搜不到）→ 首页/面板只剩今天 →
`Setup Package CI` 的 live 检查红 → PR 无法合并。这条链今天跑了两遍。

**同时继续优化**，因为付钱解决"额度"，不解决"每次搜索读 516 行"这个设计问题：
`misakanet_search` → `loadLessons` → `INTERNAL_LESSON_LIMIT=5000`（实际 516 行），
而 `getWithCache` 的缓存**本身是 D1 读**；9.4k 次/天 × 516 ≈ 4.85M，就是那 6.24M 的主项。

**不建议"只优化不付费"**：免费档的 KV 也是 1,000 次写/天，今天已经打穿过（`storage_unavailable`
发生在 token 写不下去时）——那不是优化 D1 能消掉的。付费档同时把这层也抬起来。

### 113.3 本轮已做的优化：isolate 内 memo（默认关闭，生产开启）

### 113.5 外部分析的核对（2026-10-19，逐条对过）

一份外部 D1 分析把根因归为"全表扫描，因为只有 1 条 CREATE INDEX"。核对结果：**那条前提是错的**，

| 外部说法 | 事实（文件:行） |
|---|---|
| 整个代码库只有 1 条 CREATE INDEX | **16 条**：`lessons(domain/status/updated/created)`、`counters(scope,period)`、`kv_store(expires)`、`lesson_usage(event/created_at)`、`questions`、`lesson_drafts` 等 |

2. **`INTERNAL_LESSON_LIMIT=5000` 意味着缓存未命中即全量读** → 已有 isolate memo（§113.3）压住乘法；

### 114.5 一个"会不会影响用户"的核对，抓到一处旧缺陷

被问到"这些改动会不会影响用户体验"时，逐条对过，结论如下：

| 改动 | 用户可见影响 |
|---|---|
| 语料 memo（30s） | **几乎无**。最坏是"刚合并的课程最多晚 30 秒被搜到"——而它前面那层缓存本身就是 300 秒，所以这是变**新**，不是变旧 |
| 计数批量（35→2 查询） | **无差异，只是更快**。但核对时发现一个**本来就存在**的缺陷（见下） |
| counters 冷却（60s） | 唯一可能让人**短暂看到更差数字**的改动：D1 出错后的 60 秒内面板可能读 KV/0（端点本身还有 300s 缓存兜着），换来的是不再每次加载都打 35 次注定失败的查询 |

**发现的旧缺陷**：`readTrafficCount` 在 D1 有行时**直接返回、忽略 KV**。而 `bumpCounter` 在 D1
upsert 失败时把增量写进 KV —— 所以一个"半天正常、半天 D1 写失败"的日子会被**低报**，而这恰好是
最需要被解释的那一天。`readFunnelDay` 的注释早就写明了这条规则（"a reader that returned on the first
successful D1 query would drop exactly the counts written during an outage"），但 traffic 那条没照做。

本轮一并修掉：traffic 改成 **D1 + KV**（与 funnel 同一条规则），批量路径也走同一条路。测试新增两条
（"批量保留 KV 增量"、"funnel 每天都加 KV 增量"）。数字方向是**略微变大**，因为补回了被吞掉的计数。

> 判据：这不是"优化"带来的副作用，而是"把优化的路径与原有路径逐条对齐"时被迫看见的旧账。对齐本身
> 是这次改动的**正确性门槛**——批量路径如果不复刻 KV 合并规则，就会在降级日给出更差的数字。

### 116.3 #3548 的根因是帧，不是负载

实测：`Accept` 带 `text/event-stream` 时服务端回 `event: message\ndata: {…}`，**与 JSON 只差 23 字节**，
`structuredContent` 与 `content[0].text` 逐字节相同。客户端在 `json.loads` 上死在 `event:` 的 `e`，异常被吞，于是打印
`intake_id=RAW`——而提交其实成功了。仓库自己有两处来源在教这个错写法（`docs/integrations/mcp-remote.md`、
`docs/journey/http-mcp/`），`intake_bot.py` 还把 `read()[:400]`（截断的 SSE 帧）当回执。

修法：`misakanet/mcp_reply.py` 一个解码器（JSON + SSE、多行 `data:`、keepalive 忽略），
`structuredContent` → 文本块 → `result` 三层回退，无法解码抛 `McpReplyUnreadable`（带状态码与片段）**而不是 `{}`**。
`remote.py` / `intake_bot.py` 已接上，文档片段改成要 JSON。

### 116.6 owner 的判据（已写进 `product-evaluation-lens.md`）

> 前端最重要的职责是**让人留在这里**；二维码是让人离开这里。

推论成一条可执行规则：**同一个 job 在本页能做完，出站入口就是漏损；做不了，它是桥，而且要说清桥的是什么。**
二维码只对"有摄像头的人"有意义（agent 直接 curl），所以它的正确位置在**站外**（README / 幻灯片 / 名片），
且目标页必须一只手能用——这就是为什么顺序是"搜索页响应式 → 站外二维码 → 首页只留链接"。
