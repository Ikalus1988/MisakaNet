### 94.3 今天最贵的一课：我验了工作区，没验提交

经过（留档，因为它的三次变体都值得记）：

1. 代理报告它把红夹具从 `origin/main` 改成固定提交，给了我提交号 `dafcf128`。
2. 我在它的 worktree 里 `grep` 文件、跑 pytest → 都过 → **我据此宣布"已修好"**。
3. 实际上**那个提交里 `PRE_FIX_SHA` 出现 0 次**，提交信息还是**原来那条**（改动从未 `git add`）。
   **推送与合并的都是旧字节。**
4. 后果：`main` 上那条红夹具测试红了 → `test (ubuntu-latest, 3.11)` 与 `audit` 都是必需检查 →
   **整条队列卡了一小时**（实测：`#3350` 的 `audit` 日志写着 "test suite has failing tests"）。

**根因**：`grep <文件>` 与 `pytest <文件>` 都能看见未提交的编辑，所以它们回答的是"这台机器上改了吗"，
不是"要发布的对象里有吗"。**证据是真的，对象是错的——这正是它读起来像"做完了"的原因。**

**三次变体（同一天，同一族）**：

| 变体 | 表现 |
|---|---|
| 参照会移动 | 红夹具钉 `origin/main` → 修复合入后夹具反转 |
| 派生比源旧 | 我在跑生成器**之后**又改了课程 frontmatter → `data/lessons.json` 描述的是旧源（被 `gate` 抓到） |
| 数字来自另一次运行 | 我在提交信息里写 "48 passed"，而那次实际是 9（第二次犯，已 amend） |

**由此确立的机械规则**（已写进课程 `lessons/contrib/verify-the-commit-not-the-worktree.md`，`#3353`）：

- 比较**对象**，不要比较目录：`git show HEAD:<path> | grep -c <marker>`、`git status --porcelain` 为空、
  以及在 **detached worktree**（那里看不到未提交编辑）里跑门禁。
- 复现步骤**不许指名会移动的 ref**；只能用不可变提交，取不到就**带理由 skip**，不静默通过。
- 数字只能从**刚跑完的那次输出**里抄。

## 95. 战略收口：定位可证伪了，方向差一个选择

### 95.1 定位（三层，混在一起就是今天所有"花瓶"争论的来源）

| 层 | 是什么 | 谁受益 | 判定 |
|---|---|---|---|

| **感知层** | 站点、面板、徽章、心跳 | **你**（看见 agent 真的在交互） | **成立但必须降级宣传**：它是可观测性，不是能力 |
| **资产层** | 你跨 agent 的失败记忆 | **你**（少踩坑） | **今天在它自己身上被证明**（见 94.2、94.3） |

**一句话定位**：**它不是"知识库产品"，而是 agent 通过 MCP 自动咨询的失败记忆协议；站点是它的镜子，
面板是可观测性，两者都不是产品。** 这一定位让"面板是不是花瓶"这个问题**被降级，而不是被辩护**。

### 95.2 方向：A 与 B，以及入场门

- **A｜私人记忆**（已证明）：成功 = 你自己的任务少重复踩坑。指标全是内部的，**不需要增长**。
- **B｜公开网络**（未证明且当前不可测）：需要增长与分发。

**决定**：**A 当产品，B 当期权**。**B 的入场门 = 心跳里出现"非本方、且做出检索+写入"的节点**；
没出现就不进路线图。这不是放弃 B，是把 B 从叙事挪进证据。

### 99.1 `/adopt` 跑成功了，产物永远凑不齐必需检查（已修，`#3368`）

机制是仓内已经写过三次的那条（`fix-dco.yml:156`、`build-feed.yml:139`、`auto-sync-prs.yml:73`）：
**`GITHUB_TOKEN` 推的分支、开的 PR，其 `pull_request` run 会被创建为 held，必须逐条人工批准。**

**恢复已开的收养（本轮已对 `#3366` 实测）**：13 条 held run 逐条
`gh api -X POST …/actions/runs/<id>/approve` → 全部转 `queued`（`#3366` 现在 22 项 queued）。
即"已开出去的收养不必重开 PR，批一次即可"。

### 99.2 §96.1 的前提错了一半：七个 bounty PR 不是"只缺签核"

§96.1 的依据是"每个 PR 红 13 项，全部 DCO fail"。**13 项是对的，"全部因为 DCO"不是。** 实测四类：

| 类别 | 证据 |
|---|---|
| `DCO / Signed-off-by` | §96 已覆盖 |
| `gate` | *"A lesson was added or changed without re-running the generators … the pull request did not carry them"*（`#3342` run `38917414955`） |

1. 邀请里除了 `--signoff`，还要写"跑这两个脚本并把产物一起提交"，否则邀请仍然生产**换个红叉**的 PR；

### 99.3 §98.2b 是分页陷阱：registry 其实是最新的（本条推翻，**无需修**）

§98.2b 说官方 MCP registry 条目仍旧（`2.12.2`）、措辞违规、发布路径没跟上。逐条实测后三条都不成立：

### 99.5 同一类还有一处，本轮只记录、不半修：`auto-draft.yml`

按 §99.1 那条机制**反查全仓**（任何 workflow 用 `GITHUB_TOKEN` 推分支或开 PR），除
`adopt-pr.yml` 只剩一处：`auto-draft.yml`（`workflow_dispatch` / `repository_dispatch`；
崩溃墓碑 → draft lesson → 自动开 PR）。

它**没有可指的受害 PR**（run 历史只有一条 `27970587912`，2026-06-22，之后未再触发），但结构上
**同时踩三个坑**，所以只修 token 会把它从"没有检查"变成"DCO 红"——正是 §99.2 记的那个错：

1. `Create Pull Request` 步骤 `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`，且 `actions/checkout` 未指定
   `token`、`persist-credentials` 默认 `true` → push 与 `gh pr create` 都是 bot 身份，run 被 held；
2. 提交信息是 `auto: draft lesson from crash tombstone [skip ci]` → run 还会被跳过；
3. 该提交没有 `Signed-off-by:` → DCO 是必需检查。

**本轮的动作**：新增 `tests/test_pr_opening_workflow_uses_the_pat.py`，按**操作**（任何
`gh pr create` 步骤）而不是按脚本发现对象；`auto-draft.yml` 以**写明理由的 `EXEMPT`** 留在名单外。
反例已实测：把 `adopt-pr.yml` 退回 `main` 版本，该测试立刻变红并点名
（`adopt-pr.yml:adopt:Open the adopted PR opens a pull request with ${{ secrets.GITHUB_TOKEN }} …`）。

> 要不要给 auto-draft 补签核、去掉 `[skip ci]`，是 **owner 的决定**：它改变那条流水线的语义与
> runner 成本，不是一处机械替换。**记录在这里，不做半修。**
