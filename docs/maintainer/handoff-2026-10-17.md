### 94.3 今天最贵的一课：我验了工作区，没验提交

经过（留档，因为它的三次变体都值得记）：

1. 代理报告它把红夹具从 `origin/main` 改成固定提交，给了我提交号 `dafcf128`。
2. 我在它的 worktree 里 `grep` 文件、跑 pytest → 都过 → **我据此宣布"已修好"**。
3. 实际上**那个提交里 `PRE_FIX_SHA` 出现 0 次**，提交信息还是**原来那条**（改动从未 `git add`）。
   **推送与合并的都是旧字节。**
4. 后果：`main` 上那条红夹具测试红了 → `test (ubuntu-latest, 3.11)` 与 `audit` 都是必需检查 →
   **整条队列卡了一小时**（实测：`#3350` 的 `audit` 日志写着 "test suite has failing tests"）。

**根因**：`grep <文件>` 与 `pytest <文件>` 都能看见未提交的编辑，所以它们回答的是"这台机器上改了吗"，
不是"要发布的对象里有吗"。**证据是真的，对象是错的——这正是它读起来像"做完了"的原因。**

**三次变体（同一天，同一族）**：

| 变体 | 表现 |
|---|---|
| 参照会移动 | 红夹具钉 `origin/main` → 修复合入后夹具反转 |
| 派生比源旧 | 我在跑生成器**之后**又改了课程 frontmatter → `data/lessons.json` 描述的是旧源（被 `gate` 抓到） |
| 数字来自另一次运行 | 我在提交信息里写 "48 passed"，而那次实际是 9（第二次犯，已 amend） |

**由此确立的机械规则**（已写进课程 `lessons/contrib/verify-the-commit-not-the-worktree.md`，`#3353`）：

- 比较**对象**，不要比较目录：`git show HEAD:<path> | grep -c <marker>`、`git status --porcelain` 为空、
  以及在 **detached worktree**（那里看不到未提交编辑）里跑门禁。
- 复现步骤**不许指名会移动的 ref**；只能用不可变提交，取不到就**带理由 skip**，不静默通过。
- 数字只能从**刚跑完的那次输出**里抄。

## 95. 战略收口：定位可证伪了，方向差一个选择

### 95.1 定位（三层，混在一起就是今天所有"花瓶"争论的来源）

| 层 | 是什么 | 谁受益 | 判定 |
|---|---|---|---|
| **能力层** | MCP 端点：agent 检索、无命中报料、报料变课程 | **agent**（下一轮表现） | **已成立**（当日 `mcp` 3884 次、课程 491、intake 管道自己在产课程 PR） |
| **感知层** | 站点、面板、徽章、心跳 | **你**（看见 agent 真的在交互） | **成立但必须降级宣传**：它是可观测性，不是能力 |
| **资产层** | 你跨 agent 的失败记忆 | **你**（少踩坑） | **今天在它自己身上被证明**（见 94.2、94.3） |

**一句话定位**：**它不是"知识库产品"，而是 agent 通过 MCP 自动咨询的失败记忆协议；站点是它的镜子，
面板是可观测性，两者都不是产品。** 这一定位让"面板是不是花瓶"这个问题**被降级，而不是被辩护**。

### 95.2 方向：A 与 B，以及入场门

- **A｜私人记忆**（已证明）：成功 = 你自己的任务少重复踩坑。指标全是内部的，**不需要增长**。
- **B｜公开网络**（未证明且当前不可测）：需要增长与分发。

**决定**：**A 当产品，B 当期权**。**B 的入场门 = 心跳里出现"非本方、且做出检索+写入"的节点**；
没出现就不进路线图。这不是放弃 B，是把 B 从叙事挪进证据。

### 95.3 增长要拆成三种

## 101. CodeQL 的三代告警：抑制注释在**这个仓库对本查询无效**，最后按误报关闭

> 起因：owner 贴出 Code scanning 的三条 high（#339/#340/#341，`py/clear-text-logging-sensitive-data`，
> `scripts/arm_auto_merge_lesson_prs.py:287/290/293`）。看起来是"#3361 加过抑制注释却没生效"，实际比这深两层。

### 101.1 三代告警与三次尝试

| 代 | 何时 | 当时代码 |
|---|---|---|
| #336–#338 | 10-16 | 直接打印 `entry['reason']` |
| #339–#341 | 10-17 上午 | 加了 `# codeql[py/clear-text-logging-sensitive-data]` 注释（**无效**） |
| #342–#344 | 10-17 下午 | `_redact` 改成按形状清洗、**完全不读 token**（**仍红**） |

三次尝试的结果是决定性的：

1. **行首 `# codeql[...]` 注释不抑制**——#339–#341 正是开在带注释的行上；
2. **`_redact` 不读 token 也照样红**——说明 taint 不在 redactor；
3. **裸打印（连 `_redact` 都不调用，#3445）仍然红**——所以分析器的"敏感数据源"在这台打印机**上游**
   （`entry['reason']` 由 `gh` 输出经 `candidate_skip_reason` / `decide` 拼出）。

③ 是关键的隔离实验。**做它之前我已经按"taint 来自 `_redact`"下了结论并合了 #3442**，结论被 ③ 证伪。

### 101.2 处理：按误报关闭，理由逐条落库

打印的是 PR 号、判定和一句由 `head_repo`/作者关联/判定器解释拼成的话——**没有任何凭据**。
所以对 **三批共 9 条**执行：

```
PATCH /repos/:owner/:repo/code-scanning/alerts/{n}
  state=dismissed, dismissed_reason="false positive", dismissed_comment=<280 字符以内>
```

> **API 限制（实测）**：`dismissed_comment` **最多 280 字符**，超了是 `422 Only 280 characters are allowed`。
> 我第一版写了 580 字符、第二版 293 字符，都被拒。压到 277 字符才过。

关闭后：`state=open` 的 CodeQL 告警 **0**。

### 101.3 顺手修掉的错误注释

#3442 在代码里留下「removing the taint works where silencing it did not」——已被 ②③ 证伪。
#3448 改成实际记录（抑制无效 / redactor 无关 / 已按误报关闭）。**一句解释了错误原因的注释比没有注释更糟**，

### 101.4 一条可复用的判据

遇到 CodeQL 告警，**先做"去掉可疑来源还报不报"的隔离实验**，再决定改代码还是关告警：

```bash
# 隔离实验的最小形态：把被怀疑的来源摘掉，只留打印
#  - 去掉 redactor 后仍报  → 源在上游（本例：gh 输出）
#  - 去掉后不报            → redactor/变换本身就是源
```

顺带：`# codeql[...]` 行首注释在本仓库**对本查询不生效**，别再把它当解法（它是本轮第一次尝试，白花了半小时）。
