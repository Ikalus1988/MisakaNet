### 122.4 门禁：紫色从"七个 hex 的名单"改成按色相判定，还挖出了门禁自己的一个洞

原来判据 12b 靠一份手写的 hex 名单（`#a371f7` ×6、`#7c3aed` ×1）。**那份名单漏了
`#bc8cff` 和 `#d2a8ff`**——报告说"0 处"的时候，页面上还有三个紫。按色相重数，
基线上的紫是 **18 处 / 5 个页面**，不是名单里的 7 处：

| 色值 | 处数 | 页面 |
|---|---|---|
| `#a371f7` | 6 | search、start |
| `rgba(163,113,247,·)` | 5 | search、start |
| `#d2a8ff` | 3 | journey、search |
| `rgba(210,168,255,·)` | 2 | journey |
| `#7c3aed` | 1 | index |
| `#bc8cff` | 1 | pr-genius |

现在的判据：

- **主色带**：色相 195°–290°、饱和度 ≥ 0.45、明度 ≥ 0.5。三个条件都要：页面里全是
  蓝相的近灰（`#8b949e`、`#c9d1d9`、`#30363d`）和深色面（`#0f172a`、`#1f3a5f`），
  只看色相会把它们全扫进来，报出一个浏览器里根本不存在的站点。
- **紫色带**（250°–290°）：**自己的**饱和度地板 **0.30**，比主色带低。为什么低：
  `#d2a8ff` 的饱和度是 0.34，用主色带的地板它就从门禁眼皮底下走过去了——而它就在
  当初"名单漏掉"的两个色值里。淡紫还是紫。地板取 0.30 是量出来的：全站 588 个页面
  （14 个手写页 + 571 个产物页）里没有一种颜色落在 250°–290° 且饱和度 ≥ 0.30。
- 白名单 **5 条**，每条带理由（理由是数据，不是注释）：证据徽章的 E3 蓝（契约规定）、
  journey 终端模拟的 audit 行（模拟的是工具自己的输出，七种行类型）、搜索页结果徽章的
  setup 色（六级分类色阶），外加**首页英雄区的两层环境辉光**——那是 owner 明确说过
  不动的辉光，实测最紫的一个像素是 `rgb(16,18,40)`，是暗海军蓝的雾，不是第二主色。
- 新增判据 15（页脚壳）与 16（页脚壳由共享 token 块拥有——块里删掉这条规则，
  `sync_design_tokens.py --check` 仍然是绿的，因为页面和块仍然"一致"，只是一致在什么都没有）。

**门禁自己的洞（本批查出来的第五个 bug）**：`colour_hsv()` 用 `fullmatch` 去匹配
`rgba?\(...)` 的**三段前缀**，所以**每一个带 alpha 的 `rgba()` 都不解析**——包括
`rgba(88,166,255,0.12)` 和 `rgba(163,113,247,0.14)`。门禁看不见的颜色，就是门禁管不住
的颜色：基线上 14 个手写页里 **250 处**带 alpha 的颜色对判据 1 和判据 12b 完全隐形，
其中 **25 处**是真正的违规（16 处旧 GitHub 蓝、7 处紫、2 处分类色阶）被静悄悄地放过，
而判据 12b 报的是"0 处"。

修法是拆出 `colour_rgb()` 统一解析，`alpha` 可选；顺带把白名单的键从**字面量**改成
**颜色身份**（`(rel, (r, g, b))`）——`#3b82f6` 和 `rgba(59,130,246,0.14)` 是同一个颜色，
按字面量记的白名单会放过 hex、静悄悄地禁掉 rgba，E3 徽章自己的底色就是这么被报出来的。

修完之后门禁在基线树上报 **143 处**：18 处紫、89 处第二主色、36 处底色/页脚。
（改之前是 138 处：紫色带的地板降低之后，`#d2a8ff` 那 5 处也浮出来了。）

`tests/test_site_design_convergence.py` 25 → **46 条**。

### 122.7 §122 写完到合并之间踩到的四个坑（都已经在 main 上复现过）

这四条**没有一条是这批代码的错**，但每一条都会让下一轮以为是自己弄坏了东西。
全部在合入后的 main 上当场复现过，写在这里是因为它们**会重复发生**。

#### 1. 本机 `no_proxy` 写的是 `127.*`，而 curl 不认通配 —— 症状是「测试变红」和「全量跑不动」

本机的 `no_proxy` / `NO_PROXY` 是：

```
192.168.*,172.31.*,...,10.*,127.*,*.local,localhost,*360buyimg.com,...
```

里面有 `127.*` 和 `localhost`，**没有字面的 `127.0.0.1`**。curl 的 no_proxy 只做精确和
后缀匹配，**不认 `*` 通配**，于是 `http://127.0.0.1:PORT` 的请求被交给 `http_proxy`
指的 Windows 侧代理（`127.0.0.1:7890`），代理当然够不着本机的 stub。

两个后果：

- `tests/test_http_utils.py` 的 **3 条测试在 main 上就是红的**
  （`test_get_proxy_handler_no_proxy`、`test_get_proxy_opener_no_proxy`、
  `test_case_insensitive_env_vars`）。清掉代理变量后同一个文件 8 条全过。
- 凡是往本地 stub 发 HTTP 的测试都会**卡到超时**：`tests/test_lesson_notify_payload.py`
  的 4 条 payload 测试从「**4.95 秒**全过」变成「15 分钟跑不完」。

还有一个更贵的连带后果：**全量测试从 17 分钟变成跑不完**。第一轮全量跑了 40 分钟、
停在 47%，被 `timeout 2400` 杀掉，Python 在收信号时正好卡在一次 `yaml.safe_load` 上，
core dump 了一段——**看着像 libyaml 崩溃，其实是超时杀的**。加上
`no_proxy=127.0.0.1,localhost` 之后，同样 4380 条 **17 分 17 秒**跑完
（4348 passed / 4 failed / 29 skipped）。

> **在本机跑本仓库的测试，一律先设 `no_proxy=127.0.0.1,localhost`**（`NO_PROXY` 同）。
> 这是**本机环境**的性质，不是仓库的性质——CI 上没有这个代理。

#### 2. `test_agent_autostart_parity.py::test_first_turn_announcement_is_byte_identical` 是一颗时间炸弹

它比 python 钩子和 node 钩子的首轮公告，要求**逐字节相同**。但 node 安装器
（`packages/misakanet-setup/bin/misakanet-setup.mjs`）的公告里带一句
「本机安装的是 X.Y.Z，距上次确认已超过 14 天」——**这句话由本机的版本戳时间决定**。
本机那个戳早就过期，于是 node 侧多一句、python 侧没有，两边不等 → **必红**。

它在 main 上就是红的，报错信息里能直接看到那句多出来的公告。与这批改动无关。

#### 3. `pr-agent`（Codium pr-agent，LLM 代码评审）会间歇性红，而且它不是必需检查

main 上 26 pass / 0 fail / 5 skipping 里，那唯一一条非绿是它：
`APITimeoutError - Request timed out. timeout value=120.0, time taken=362.54 seconds`，
重试之后被 workflow 的 `timeout-minutes: 15` 取消。

- 它**不是必需检查**：PR 在 08:09:31 就合并了，那个 job 08:14:04 才被取消。
- **不是这批的问题**：#3591（17 文件）、#3592（18 文件）的 pr-agent 日志里是同一组错误
  （`APITimeoutError` + 401/403），所以这是外部 LLM 供应商的抖动，**与 diff 规模不严格相关**。
- 合并的正规路径是仓库自己的 `pr-checks.yml`：门禁通过后执行
  `gh pr merge "$PR_NUM" --squash --auto` 授权 GitHub 合并（前提是 PR body 里没有未勾选的
  `[ ]`）。**别把 pr-agent 当成门禁。**

#### 4. `/tmp/baseline-tree` 那个 worktree 还在

它是用来证明「那 4 条失败是既有的」：`git worktree add /tmp/baseline-tree 5ba76cc3`，
然后在基线树上跑同样的测试，**同样 4 条、同样报错**。按仓库「不删目录」的规矩没删它，
`git worktree list` 可以看到。

#### 方法论：判断「失败是不是我造成的」，别靠推理，开一个基线 worktree 跑一遍

这一轮我差点把那 3 条环境导致的红当成自己的回归。推理链是「我没碰这些文件 → 不是我」——
这在大多数时候对，但**不是证据**。开一个 worktree、在基线上跑同样的命令、看是不是同样的红，
才是证据：

```bash
git worktree add /tmp/baseline-tree 5ba76cc3
cd /tmp/baseline-tree && <同样的 pytest 命令>
```

这一步把「我以为」变成「我看过」，而且只花几秒。**「我没碰它」是推理，「基线上它也红」是证据。**

> **量的时候踩的一个坑**：`wrangler d1 insights` 的**每形状调用次数有抖动**（24 小时窗口里五个
> 形状是 650 / 695 / 631 / 649 / 569 次；两小时窗口里是 43 / 47 / 24 / 32 / 35）。
> 所以**只有行读总量和每次均值是可信信号**，调用次数只能用来判断量级。别拿它做等式。
>
> **后来又踩了一层**（见 §123.7b）：这个工具**会漏掉整个形状**——一条明明在跑的查询在窗口里
> 整个消失，而同批的别的形状还在。**窗口总量也因此是缩放后的估计值，不是真账。**
> 真正精确的只有 `wrangler d1 execute` 逐条返回的 `rows_read`。

### 123.2 三处根因

**① 查了用不上的。** `knowledge_gaps` 是维护者专属字段（别人原样发来的失败查询），
匿名 payload **永远不包含它**——但那条 `event='no_match'` 的 GROUP BY 一直无条件执行、
执行完丢掉，每次重算白花 3,008 行。生产里 `MCP_TOKEN` 根本没配，维护者分支**不可达**，
所以这 3,008 行**每一行都花在了没人收到的答案上**。

**② 算得太勤。** 27 次/小时正好是 120 秒 TTL 的槽位数（30/小时）——这条路由**以缓存允许的
最勤频率**在重算。而它的答案窗口是**七天**：十分钟的 TTL 最多藏起 10,080 分钟里的 0.1%，
而没有任何消费者需要它更新鲜（面板是七天滚动视图，heartbeat 一天读一次）。

**③ 扫全表的。** `search_signals` 在生产上**一个索引都没有**（`sqlite_master` 只返回表本身），
E4 的 `COUNT(DISTINCT client_hint)` 每次调用扫全表 5,976 行——**其中只有 17 行带非空
`client_hint`**（4 个不同 hint），另外 5,959 行根本不可能进这个计数。5,842 行/次 × 349 次
= **2,039,019 行/24 小时**，为一台"有用内容 17 行"的表付的钱。

### 123.3 两个被证伪的直觉（本地实验，SQLite 真引擎）

这一轮最值钱的不是改了什么，是**先证伪了两个看起来当然的改法**：

| 直觉 | 实测 | 结论 |
|---|---|---|
| 给 `lesson_usage` 加覆盖索引，五个 GROUP BY 就走 index-only scan 了 | `GROUP BY day` 那条**本来就走覆盖索引**（`idx_usage_created`），却照样读 1,805 行 | **D1 的行读把索引条目也算进去**，覆盖索引不减少行读，只是少一次表取 |
| 给 `search_signals` 加普通 `client_hint` 索引就行 | SQLite **3.45**（系统 Python）计划仍是 `SCAN search_signals`；**3.50+**（venv）才会用 | 普通索引是 **planner 相关**的；**D1 的 SQLite 版本读不到**（`sqlite_version()` 被拒：`not authorized to use function`），所以要选**两个版本都成立**的形状 |

最后定下的形状是**部分 + 覆盖**：

```sql
CREATE INDEX IF NOT EXISTS idx_search_signals_hint_top
  ON search_signals(client_hint, top_id)
 WHERE client_hint IS NOT NULL AND client_hint <> ''
```

部分索引的前提是"查询的 WHERE 蕴含索引的 WHERE"——这里两者**正好是同一个谓词**，
所以查询**一个字都没改**（`top_id LIKE '%/<id>.md'` 前导通配，本来就服务不了，
这个索引要解决的是**扫描本身**）。覆盖 `top_id` 则让表根本不用碰。

> D1 用哪个 SQLite 版本**没查出来**（`sqlite_version()` 无权调用）。所以选形状的标准是
> **在 3.45 和 3.50+ 上都被选中**，而不是"在某个版本上更快"。

### 123.7b 部署后的整点行读：让"流量"当控制变量

> **这一节返工过一次。** 第一版写的是"部署后 1 小时 21,007 行 = 降了 2.95 倍"。
> 那个数**站不住**：同一天、同一个工具、同样的 1 小时窗口，账号合计行读在
> **21,007 / 69,366 / 475,053** 之间跳——**流量波动比改动本身大**，
> 所以"窗口总量"不能当验收数。
> 下面是返工后的版本：**用调用次数做流量对照**，让流量自己当控制变量。

部署完成的准确时刻是 **2026-10-21T11:12:58Z**（deployment `7224225699` 的
`updated_at`）。于是 `wrangler d1 insights --time-period Nh` 的窗口可以按它切成
"整段在部署前"和"整段在部署后"两类。四次取数连着跑（窗口边界随取数时刻平移几分钟），
相减得到逐小时：

| 1 小时窗口 | 账号合计行读 | 调用数 | 每次调用平均行读 |
|---|---|---|---|
| 08:39–09:39Z（整段部署前） | 366,374 | 1,754 | 209 |
| 09:39–10:39Z（整段部署前） | **610,717** | 2,817 | **217** |
| 10:39–11:39Z（**跨部署**：26 分钟前 + 26 分钟后） | 454,046 | 2,767 | 164 |
| 11:39–12:39Z（**整段部署后**） | **113,470** | 2,869 | **40** |

拿 **09:39–10:39Z** 和 **11:39–12:39Z** 比，这两段的**流量几乎一样**
（2,817 次 vs 2,869 次调用，差 **1.8%**），行读却是 **610,717 → 113,470**：

- **绝对量降了 5.4 倍**；
- **每次调用的平均行读从 217 降到 40**（同样 5.4 倍）——**这个比值对流量不敏感，
  是这一轮真正可复现的数**。

> 同一段（11:39–12:39Z）单独跑一次 1 小时窗口得到的是 **113,335 行 / 2,765 次**
> （12:39:10Z 那次），和上面相减得到的 113,470 / 2,869 **差 0.1%**——
> 这就是 `insights` 那个 0.1% 量级的采样噪声，两个数都对。

> **顺手记一个 24 小时计数器的行为**（今天实测到的）：
> 12:47Z 它是 25,948,796，13:06Z 变成 **20,522,282**——**19 分钟掉了 5.4M（-21%）**。
> 原因**不是用量下降**，是**滚动窗口把修复前的那几个小时甩出去了**
> （#3590 那条前缀 LIKE 在 10-20 16:58Z 之前，每小时贡献 **300 万–530 万行**：
> 代码注释里那次实测是 259 次 / 17,800,700 行 / 六小时 ≈ 300 万行/小时，
> 24 小时窗口里量到的是 370 万–530 万）。
> 掉完之后它就稳了：13:07Z → 13:12Z 涨了 **8,903 行 = 约 1,780 行/分钟 ≈ 10.7 万行/小时**，
> **和干净一小时窗口实测的 113,335 行/小时 对得上（差 6%）**——
> 两条互不相干的测量落到同一个数上，**这是这一轮最硬的一个交叉验证**。
> **教训：24 小时计数器是"昨天 + 今天"的混合体；它掉下来的那一刻不是好消息，是历史在走。**

> **为什么不能只报"窗口总量"**：总量同时被"流量"和"每次代价"两个因子推动。
> 这一轮两个因子朝**相反**方向动（每次代价降了，流量涨了），
> 于是比值会被流量放大或缩小，落在 2.95×–5.4× 之间全看取哪一小时。
> **不受流量影响的量是"每次调用的平均行读"**，这才是验收依据。

下面这张表是上一版量出来的 **11:15–12:15 那段干净窗口**，
形状级明细仍然有效，但它只说明"逐条形状降了多少"，不说明"整个账号降了多少"：

| 形状 | 部署后（1 小时） |
|---|---|
| E4 `COUNT(DISTINCT client_hint)` | 22 次 × **17 行** = 374 行（改前 14 次 × 5,992） |
| `CREATE INDEX IF NOT EXISTS idx_search_signals_hint_top`（worker 自己的 DDL） | **46 次 × 0 行 = 0** |
| `counters` gap 清理那条读 | 18 次 × **500 行**（改前 2,410） |
| `analytics get_lesson` | 26 次 × 722 |

**"46 次 × 0 行"这一行是这一轮最该被记下来的一条**：我担心的不是"索引建得慢"，是
"**每个冷启动都要重跑一次建索引 DDL，每次 6,011 行**"——那会把这一轮省下的钱又花回去。
实测：索引存在之后，那条语句是**纯 no-op，0 行**（D1 上手动跑两次也是 0 行 / 0.18ms）。
6,011 行只发生在**真正建索引**的那一刻（一次是我手动建的，一次是 worker 重建的）。
**这条担心是假的，但它得被测出来才算数。**

> **口径必须一起说清楚**：`wrangler d1 insights` 的**形状采样不可靠**——同一条语句会在窗口里
> 凭空消失（干净窗口里 `analytics search` 和 `GROUP BY day` 两个形状就没出现，而同一批的
> `get_lesson` 出现了 26 次），它的**调用次数和总量都是缩放后的估计值**（它报 56 次建索引，
> 真实只有 2 次）。所以：
> - **可信**：逐条 `wrangler d1 execute` 的 `rows_read`（精确），以及每次均值；
> - **只能当量级看**：窗口总量和调用次数。
>
> **"只能当量级看"要再说精确一点（实测）**：`insights` 的 **`avgRowsRead` 是准的**，
> 被缩放的是**调用次数**，于是 `totalRowsRead` 跟着虚高。五个形状交叉验证
> （左边 `insights`，右边 `wrangler d1 execute` 逐条）：
>
> | 形状 | `insights` 的 avg | 权威逐条 | 差 |
> |---|---|---|---|
> | analytics search | 5,283 | **5,287** | 0.08% |
> | analytics day | 2,030 | **2,102** | 3.4% |
> | analytics get_lesson | 722 | **722** | 0% |
> | E4 distinct clients | 17 | **17** | 0% |
> | `kv_store` 范围列表 | 6 | **6** | 0% |
>
> 而 24 小时窗口的**总量**比 `d1 info` 的计数器高 **18%**
> （30,652,142 vs 25,948,796）——**那 18% 全部来自被缩放的调用次数**。
> **所以用法是：拿 `avgRowsRead` 比大小，别拿 `totalRowsRead` 当账。**
>
> **还有第三类污染源：我自己的诊断查询。** `wrangler d1 execute` 跑的
> `SELECT ... FROM kv_store`（**没有 WHERE**）就是**全表扫**，它会以**字面量 SQL** 的形态
> 出现在 insights 窗口里，**行读和 app 的查询一模一样大**，而且分不出谁是谁。
> 实测：12:57Z 的 1 小时窗口报 **379,682 行**，而 12:39Z 测的同一段是 **113,335 行**——
> 多出来的 266,347 行里，绝大部分是**我自己在 12:41Z–12:49Z 跑的那几条 `kv_store`
> 全表扫**（每次 70,346 行）。
> **所以窗口之间对不上时，先看自己是不是刚量过。**
> **同一条也适用于 `d1 info` 的计数器**——它统计的是**所有**行读，包括我自己量东西的那些：
> 13:12Z→13:17Z 那 5 分钟它涨了 30,513 行，其中绝大部分就是我刚跑的那几条 `lesson_usage`
> 聚合（5,287 + 2,102 + 722 + 4,477 + 7,355 ≈ 20,000 行）。
> **13:07Z→13:12Z 那 5 分钟的 +8,903 行是干净的**（那段只有一次 `d1 info` 元数据调用），
> **它才是那个数。**
> 本文引用的 1 小时窗口是 **12:39:10Z 测的**（11:39–12:39Z），**早于**今天那批重诊断，
> 那段是干净的。
>
> **还有第四类污染源：`insights` 的 1 小时窗口本身就会塌。**
> 12:39:10Z 测 1 小时窗口拿到 **34 个形状**；13:05Z 再测同一个窗口长度，
> **只回来 1 个形状**（`INSERT INTO counters … RETURNING count`，2 次调用），
> 而且 13:0xZ 前后连测 6h / 12h / 18h / 24h 都正常。
> **所以"某个形状没出现"这句话本身不可信**——它可能只是没被采样到。
> **这正是 §123.7d 那个错的第二层原因**：判断一条形状还在不在，
> **不能只靠"它没出现"，得靠"更长的窗口 + 源码"两边一起对**。
>
> **"2.95 倍"这个数撤回**（上一版写的）。它和上面那个 5.4 倍**并不矛盾**：
> 两个数都是同一个工具、同一个窗口长度下测的，但**窗口总量被流量推着走**，
> 取哪一小时就得到哪个数——**所以它是这批里最不该被当成验收依据的一个数**。
> **能站住的是这两个**：
> - 逐条精确值：E4 5,992 → 17、gap 2,410 → 500、每次重算 10,920 → 5,977
>   （`no_match` 那 3,008 行没了），重算频率按 TTL 从 27 次/小时降到 6 次/小时；
> - 每次调用的平均行读：**217 → 40**（在流量对照下 5.4 倍）。
>
> **"下一次该怎么量"也记在这里**：先问"这次窗口的流量和上一次可比吗"，
> 再比总量；不可比就换**每次均值**，或者像本文这样**把流量当控制变量**。
> **这一轮真正的教训是：拿一个会被流量推动的量当验收数，等于把噪声写进了结论。**

### 123.7c 那 +60MB 是谁的：不是错题，不是笔记，也不是索引

看板上库从 **156MB 涨到 214MB**，猜的是"最近往库里塞了不少新东西

| < 1KB | 70,195 | 7,594,300（7.2 MiB） |
| 1KB–10KB | 1 | 1,033 |

**150 行（占 0.21%）装着 164,204,172 字节 = 全库的 74.3%。**
这些是**语料缓存块**：每块 1–2MB 的语料被整体写进 `kv_store`，
`ON CONFLICT(key) DO UPDATE SET value = ?` 每次重写都是**整块替换**——
旧页不会立刻还给 freelist，文件就一路涨。**这是写入放大，不是"塞新东西"。**

> **而且这件事是活的、现在就在涨**：同一个文件 **12:42Z 的 218,730,496 字节
> → 12:49Z 的 221,110,272 字节，七分钟 +2.4MB**；同一段时间里 `kv_store` 的
> `value` 载荷从 169,649,910 涨到 171,799,505（+2.1MB）。
> **这就是"库在变大"的实时证据**——不是错觉，是 `kv_store` 在写。

> **这一轮唯一的容量支出是 +13.4MB**：`CREATE INDEX` 触发整文件重写，
> 185,860,096 → 199,651,328。**那 13.4MB 是一次性代价，索引建完就不再涨**；
> 剩下的 60MB 是缓存块重写的历史累积，**和本轮无关**。
> 顺带记一把尺子：`wrangler d1 execute` 每次都回一个 `size_after`，
> 那是**当前文件的精确字节数**（12:49Z 时是 221,110,272），比 `wrangler d1 info` 里
> 四舍五入的 "219 MB" 好用。

### 123.7d 24 小时窗口的第一名，是一个**已经修好的**历史问题（这一节自我推翻过一次）

先摆事实：24 小时窗口按行读排下来，第一名是这一条

```sql
SELECT key FROM kv_store WHERE key LIKE ?1 ESCAPE '\'
  AND (expires_at IS NULL OR expires_at > datetime('now')) LIMIT ?2
```

**14,483,754 – 20,403,608 行 / 210 – 296 次 = 每次 68,931 行**
（表一共 70,293 行，所以它每次扫了整张表）。
（次数和总量是采样估计，两次取数给出 210 / 296 和 14.5M / 20.4M——**形状本身是稳的**。）

**第一版结论（错的）："这是一个新发现，下一轮给它加个 `COLLATE NOCASE` 索引"。**

**它不是新发现。** 三条独立证据把它钉死是**历史的**：

1. **源码里早有修法，而且注释里记的就是今天这个测量。**
   `workers/register-proxy-sw.js:3469-3473` 写着：
   *"measured 2026-10-20 on production D1, `WHERE key LIKE 'prefix%' ESCAPE '\'` has no usable
   plan and reads **every row of `kv_store`** — 68,892 rows for one prefix listing …
   `wrangler d1 insights` for the six hours to 14:20Z counted 259 such calls and 17,800,700
   rows read: 87% of the account's entire row-read spend, for a listing whose answer is six
   keys."*
   —— **和今天量到的 68,931 / 210–296 次 / 14.5M–20.4M 是同一个东西。**
   同一段注释还记着修法：*"The range (`key >= lo AND key < hi`) uses the primary-key index
   instead: the same call reads 6 rows."*
2. **#3590 在 2026-10-20T16:58:22Z 就把它换掉了**（squash 提交 `1225e9e6`，
   *"fix(worker): the prefix list must not read the whole table"*）。
3. **窗口边界对得上**：24 小时窗口（从 10-20 **13:05Z** 起）**有**这条 LIKE；
   18 小时窗口（从 10-20 **19:05Z** 起，**在修复之后**）**一次都没有**。
   两个窗口只差 **3.9 小时**，差的正好是修复前那一段。

现在的形态是范围谓词，**每次 6 行**：

| 窗口 | 范围形态 `key >= ?1 AND key < ?2` |
|---|---|
| 6 小时 | 225 次 × **6 行** = 1,350 行 |
| 12 小时 | 466 次 × **6 行** = 2,796 行 |
| 24 小时 | 599 次 × **6 行** = 3,594 行 |

**所以那 14.5M–20.4M 行是昨天的新闻，会在 2026-10-21T16:58Z 之前完全滚出 24 小时窗口。**
**`COLLATE NOCASE` 索引会是一条"给已经不存在的查询准备的索引"——不做。**

（顺带把"精确查找"这件事也说清楚：真正的精确查找
`SELECT value FROM kv_store WHERE key = ?1` 在 1 小时窗口里
**758 次调用共 612 行，每次 0.8 行**——它一点都不贵，也从来不是大户。
**贵的是当时那条前缀 LIKE，而它已经没了。**）

> **这一节真正的收获不是那个形状，是那个错。**
> 我是**只看 24 小时窗口**就把它当成了"今天的第一名"，少做了两件事：
> **(a) 拿更短的窗口确认它现在还在不在**；
> **(b) 去源码里 grep 这条 SQL，看它现在还在不在主路径上**。
> 两件各花一分钟，**而它们各自足以推翻结论**。
>
> **规则写下来**：**24 小时窗口排出来的"第一名"，在下结论之前必须过这两关——
> 更短的窗口（6h / 12h）里它还在吗？源码里这条 SQL 现在还在跑吗？**
> **窗口越长，历史混得越多**；**源码是最便宜、最准的判据**：
> 那条 LIKE 至今还留在文件里，但它只是 `prefixRange()` 返回 `null` 时的兜底分支
> （只有"前缀全是最大码位"才会走到），**早就不在主路径上了**。

> **生产上 `kv_store` 的全部索引**（`sqlite_master` 实查，2026-10-21T13:0xZ）：
> - `sqlite_autoindex_kv_store_1` —— `key TEXT PRIMARY KEY` 隐含的**唯一**索引，
>   **BINARY collation**，所以 `key LIKE ?1` 用不上它（当年的全表 SCAN 就是这么来的）；
> - `idx_kv_store_expires` —— `workers/d1/schema.sql:171` 建的；
> - `kv_store_expires_at` —— **worker 运行时自建的，和上面那条列完全相同**
>   （1 小时窗口里它以 no-op 形式跑了 179 次）。**这是一对重复索引**，
>   本轮没动它（删索引要单独验一次"删了之后 worker 会不会立刻重建"），
>   但它该被记下来。
>
> **注意第一条索引现在只服务范围谓词了**（`key >= ?1 AND key < ?2` 正好吃主键索引），
> **LIKE 已经不在主路径上**——所以"给它加个 NOCASE 索引"这条路是**多余的**。
