Problem

自动化脚本给 GitHub PR/issue 发评论时，正文常含用户可见的命令片段（git log、$HOME）和 脚本输出。用双引号拼接正文：

gh issue comment 42 --body "see \`git log\` and $SECRET"

shell 会在执行前展开 $SECRET 并执行反引号里的命令——正文被发出去时，密钥已经躺在公开评论里。 更隐蔽的是：cat <<EOF（不带引号的 heredoc）同样会展开，只有 cat <<'EOF' 是字面量。

实测三臂对照（2026-11-02，SECRET=do-not-leak-12345）：

[1] double-quoted string — expands:
key is do-not-leak-12345
[2] unquoted heredoc (<<EOF) — expands:
key is do-not-leak-12345
[3] quoted heredoc (<<'EOF') — literal:
key is $SECRET

Root Cause

POSIX shell 的词法：双引号内 $ 和反引号仍然求值；heredoc 的分隔符不加引号时按双引号规则 处理正文，加引号（<<'EOF'）才关闭一切展开。这是 shell 的设计，不是 bug——把它当成"多行字符串 字面量"是调用方的误解。

Solution

评论/PR 正文一律走带引号的 heredoc：

gh pr create --repo owner/repo --title "..." --body-file - <<'EOF'
Fixes #42

Run `git log --oneline` and compare with $HOME — both stay literal here.
EOF

配套三条：

  1. 禁止把原始命令输出直接拼进正文（防 env dump）：输出先过 grep -v -i 'token\|secret\|key' 之类的 脱敏过滤，或只粘贴结论行；
  2. 反例写法（双引号 + 反引号）在 code review 里见到就拦：--body "...\cmd\..." 是泄露形态；
  3. 同一规则适用于所有发往外网的文本：commit message、issue、飞书消息——凡 shell 拼接，先问 "这段会不会被展开/执行"。

Verification

SECRET=do-not-leak-12345 bash -c 'cat <<'"'"'EOF'"'"'
key is $SECRET
EOF'

预期：输出字面量 key is $SECRET；把 <<'EOF' 换成 <<EOF 重跑，预期输出 key is do-not-leak-12345 （展开 = 泄露）。三臂完整版见 /tmp/heredoc_demo.sh 的写法（同款脚本可自查）。
