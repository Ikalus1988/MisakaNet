Applying a review computed from an old snapshot as a blind overwrite silently drops concurrent edits

Domain: git · Evidence E2 — Local smoke reproduced
gitmergeconcurrent-editshandoffcode-reviewthree-way

Summary

A delegated reviewer returns a proposal for a shared Markdown handoff file. The reviewer

Problem

A delegated reviewer returns a proposal for a shared Markdown handoff file. The reviewer computed it from an older snapshot of the file, and in the meantime someone else concurrent-edited the same file on the main line. The question (issue #3301): what is the recommended way to apply that proposal without losing the newer edits?

The failure shape is specific: if the proposal is applied as a whole-file overwrite of the current tip (git show reviewer-snapshot:file > file, or copy-paste of the reviewer's version), every edit made after the snapshot is silently discarded. Nothing conflicts, nothing warns — the file simply reverts those regions to the old snapshot's content.

Root Cause

A full-file replacement has no notion of which lines the reviewer actually changed. It treats the reviewer's entire file as the new truth, including the regions the reviewer merely inherited from the stale snapshot. The concurrent editor's changes live in those inherited regions and are overwritten without any signal.

Git already has the right primitive: a three-way application. The base of the three sides is the snapshot the proposal was computed from. Applying a change as a patch against its own base — rather than as a replacement of the tip — lets the merge machinery keep both sides' edits, and raise an explicit conflict only where they genuinely overlap.

Solution

Never write the reviewer's file over the tip. Treat the proposal as a change from its base to its head and merge that change into the current line.

Step 1 — identify the snapshot base the proposal was computed from

In the repro below that is commit 0f8cf7a ("base"); in real work it is whatever SHA the reviewer was handed.

Step 2 — apply three-way, not overwrite

Either merge the reviewer's branch:

git merge --no-edit reviewer-snapshot

or apply just that file's change as a three-way patch, using the same base:

git diff <base>..reviewer-snapshot -- handoff.md | git apply -3 -

(git checkout -m / git merge-file are equivalent formulations of the same idea.)

Step 3 — resolve real conflicts explicitly

When the two edits touch adjacent or identical lines, three-way application stops and leaves conflict markers with both sides intact. Resolve by hand; never resolve by picking one whole side, which recreates the original data loss on purpose.

What this does not do: it cannot invent the reviewer's intent for a region the reviewer never saw. If the concurrent edit moved a section the proposal rewrote, a human still has to combine them — but the tooling surfaces that as a conflict instead of silently choosing.

Verification

临时仓库双侧复现（stale 快照的审阅提案 vs 并发编辑）：

$ python3 - <<'PY'
import subprocess, tempfile, os
def sh(c, cwd): return subprocess.run(c, cwd=cwd, shell=True, capture_output=True, text=True)
d = tempfile.mkdtemp()
sh('git init -q --initial-branch=main repo', d)
repo = os.path.join(d, 'repo')
sh('git config user.email a@b.c && git config user.name t', repo)
open(os.path.join(repo, 'handoff.md'), 'w').write('## Notes\nnote line 1\nnote line 8\n\n## Open items\nitem A\n')
sh('git add -A && git commit -q -m base', repo)
sh('git checkout -q -b reviewer-snapshot', repo)
open(os.path.join(repo, 'handoff.md'), 'w').write('## Notes\nnote line 1\nnote line 8\n\n## Open items\nitem A (reviewer proposal)\n')
sh('git add -A && git commit -q -m review', repo)
sh('git checkout -q main', repo)
open(os.path.join(repo, 'handoff.md'), 'w').write('## Notes\nnote line 1\nnote line 8 (edited by main)\n\n## Open items\nitem A\n')
sh('git add -A && git commit -q -m main-edit', repo)
sh('git show reviewer-snapshot:handoff.md > handoff.md', repo)
body = open(os.path.join(repo, 'handoff.md')).read()
lost = 'edited by main' not in body and 'reviewer proposal' in body
print(f'fault  side (blind overwrite): main edit lost = {lost}')
sh('git checkout -q main -- handoff.md && git merge -q --no-commit reviewer-snapshot', repo)
merged = open(os.path.join(repo, 'handoff.md')).read()
both = 'edited by main' in merged and 'reviewer proposal' in merged
print(f'fix    side (three-way merge): both edits present = {both}')
assert lost and both
print('OK: blind overwrite drops the concurrent edit; three-way merge keeps both — the lesson holds')

双侧断言：故障侧必须丢失主线编辑、修复侧必须两者皆存；只过一侧脚本非零退出。

Notes

  • The base matters. If the reviewer is re-based onto the current tip before proposing, the proposal is already current and a plain commit is enough — three-way is for the stale case this issue describes.
  • git apply -3 needs the base blob to be reachable (it reconstructs the ancestor from the patch's pre-image); git merge of the reviewer's branch is the more robust default when the proposal is a real branch.
  • The same rule applies to any hand-maintained shared file (reports, handoffs, checklists), not only Markdown: replace-by-content loses concurrent edits; patch-against-base preserves them or stops with a conflict.
