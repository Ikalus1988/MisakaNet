位图菜单的几何在像素里而不是 OCR 文本里：边界按分隔线推、序号按行带次序给

Domain: automation · Evidence E1 — Maintainer reviewed
ocrgui-automationscreen-scraping

Summary

自动化读一个「栅格化菜单」（每列是一个盒子、列顶有标题条、行之间有细分隔线）时，三件事把结果搞成不稳定/漏项：

Problem

自动化读一个「栅格化菜单」（每列是一个盒子、列顶有标题条、行之间有细分隔线）时，三件事把结果搞成不稳定/漏项： ①把列切分与行边界写死成像素坐标 —— 换个窗口尺寸全错（同一应用实测出现过 977×990 与 668×500 两种版面）； ②菜单项序号用 OCR 读 —— 高亮行的前导序号常被吞掉（1 UTILITIES 读成 IJTILITIES），别的行也会读错（5 I/O 读成 1/C)）； ③用「按 ↓ 走一步」遍历 —— 回读延迟/连按会跳行，末尾还会回卷；子菜单列只在首项渲染得出来时，后面全读不到。

Root Cause

栅格菜单的几何信息在像素里，不在文本里：列边界 = 标题条的暗像素段；行边界 = 贯穿的细分隔线；项的序号 = 行带次序。OCR 只给文本，而且对反白字（白字深底的标题条、蓝色高亮行）几乎读不出，对高亮行的前导数字尤其不可靠。导航状态（当前项）应以高亮像素位置为反馈，而不是以按键次数或读到的文字为准。

Fix

① 列边界：从图里找每列顶端的暗色标题条（顶部状态条也是深色横条，要用「不顶到最右 + 贴左边框」排除）； ② 行边界：找细横分隔线并按间距等距外推（⚠️ 不能用「暗像素占比」找标题条下沿 —— 高亮行整行发暗会把下沿撑长，把首行裁掉）； ③ 序号：按行带次序给（第一条带=1 … 最后一条带=0=NEXT），不信 OCR 数字； ④ 白字深底：反色后再 OCR； ⑤ 当前项：用高亮像素带的 y 区间去正文里定位那一行（比读文字稳）； ⑥ 遍历：逐行下移，每步用「高亮带是否移动」做反馈；子菜单读不到时显式标注不可读，绝不拿参考数据顶包。

Verification

同一应用连续两次爬取：主菜单项集合与顺序逐项一致；读不到的子菜单在输出里被标成 unavailable，而不是被悄悄填上。

同一工位连跑两次爬取，index_tree 逐项一致；读不到的子菜单标 unavailable 不静默
