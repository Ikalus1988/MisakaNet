# The hit@1 misses, row by row (2026-10-30)

The handoff left one item open: *"bench 的 7 条 hit@1 miss 逐条看"*. This is that pass. It separates
two things the number hides — a query the **ranking** gets wrong, and a query whose **expectation**
was written before the corpus had a better answer — and it ships the one code fix the pass found.

## The measurement

Two benches, and they are different corpora (never compare their floors):

| bench | corpus | before | after |
|---|---|---|---|
| `node --test workers/search-dual-floor.test.mjs` (the gate) | `data/lessons.json`, 657 rows | EN 16/20 · 20/20, ZH 12/22 · 16/22 | EN **18/20 · 20/20**, ZH **14/22 · 20/22** |
| `python3 scripts/bench_production_recall.py` (live) | D1, 657 rows `rich` | EN 15/19 · 19/19 (1 transport error), ZH 15/22 · 17/22 | re-measure after deploy |

The production run before the change reported 6 misses and 6 hit@1 misses; the rows below are all 12,
grouped by verdict rather than by which list they appeared in.

## Verdict 1 — the expectation was written before a better answer existed (5 rows, fixed here)

"The corpus answers this query" is the property under test, and `expected` is supposed to list **every**
acceptable lesson. Five rows named only the answer that existed when they were written, so a *better*
lesson (or an equally good one) ranked first and the row read as a miss.

| row | query | ranked first | why that is a correct answer |
|---|---|---|---|
| `en-inline-docker-exit-code-137` | `docker exit code 137` | `docker-build-exit-137-multistage-oom` | the title is literally "Docker multi-stage build OOM-killed with exit code 137" — the expected k8s guide does not mention 137 at all |
| `zh-13` | `容器内存不足被杀死` | `docker-build-exit-137-multistage-oom` | "container killed for lack of memory" is the same failure mode; the k8s pod-OOM guide is one deployment shape of it |
| `zh-03` | `pip install 卡住不动` | `pip-install-timeout-ssl` | "pip install hangs" — the general timeout lesson is the direct answer; `lesson-08` (WSL HTTPS_PROXY) is one cause |
| `en-dco-001` | `DCO signoff` | `dco-signoff-force-push-pitfall` | four DCO lessons exist; the calibration probe (`workers/relevance-floor-calibration.test.mjs`) already accepts three of them for this failure |
| `en-dco-002` | `git commit --signoff missing DCO` | `dco-signoff-force-push-pitfall` | same, for the command-shaped phrasing |

`data/search-floor-queries.jsonl`, `data/regression_queries.json` (the two English rows' source of
truth) and `scripts/eval_query_aliases.py` (the two CJK rows' source of truth) were updated together.

**The floor does not move for these.** The CJK top-3 floor moved 15 → 18, which is the level the *code*
change below reached under the old expectations (16 → 18). The two extra rows these corrections add
(→ 20/22) are headroom, not a promise: a floor is a claim about what search does, not about how many
answers a fixture accepts.

## Verdict 2 — the ranking was wrong, and the cause was a term-space mixup (fixed here)

**`公司代理导致 SSL 证书校验失败`** ranked `gpt-sovits-hubert-16khz` first — a lesson about HuBERT
feature extraction that happens to contain the letters "SSL".

The ordering score was built from the terms the *user* typed, with alias expansions only breaking ties
(#1780/#2079). That rule was measured on Latin queries. On a CJK query the tokenizer drops the Chinese,
so the typed set is the Latin fragment — here, the single term `ssl`:

```
gpt-sovits-hubert-16khz     userScore 5.69   full 5.69    coverage 0.25
corporate-proxy-curl-timeout userScore 3.95  full 13.70   coverage 1.00
```

For a CJK query the alias table is not a guess at what the user meant — it is how the query is read. So
the order there is now decided by the expanded terms (`orderingTerms` in `searchLessonsBM25`), and the
row moved from **absent** to rank 3 (`python-smtplib…` still wins; see verdict 3). Same fix, same run:
`Node.js 连接被重置` went from absent to rank 2.

**What it nearly broke, and the guard that caught it.** The floor's own counters used to be incremented
inside `if (decidesOrder)`. Making the ordering set wider therefore fed the alias expansions back into
the *relevance floor* — the exact regression #2358 rewrote the floor to stop: `chrome-relay-browser-
automation` was admitted to `wsl2 landlock 文件系统沙箱` again, and the bench's "#2358 confident-wrong
answer is gone" test went red in the same run. The counters now follow `floorTerms` explicitly, with
the two sets named separately in the code. **A variable that decides two things is a variable that
cannot be changed safely** — that is the transferable part.

## Verdict 3 — still wrong, with the cause measured (not fixed here)

| row | query | expected | what wins | cause |
|---|---|---|---|---|
| `en-encoding-001` | `encoding bug Python` | `python-gbk-encoding-error` (rank 3) | `python-venv-tiktoken-module-not-found` | "encoding" is the *subject* of the tiktoken lesson and one word of a GBK error; the gbk lesson has the higher full score (12.46 vs 6.29) but a lower typed-word score, so the ordering rule keeps it third |
| — | `WSL NTFS SQLite` | `wsl-ntfs-sqlite-update-100x-slower` (rank 2) | `permission-denied-fix` | one shared token (`permission`) at rank 1 |
| — | `定时任务不执行` | `cron-job-not-running` (rank 3) | `lesson-9-redis-postgresql-replacement` | the alias 定时任务→cron matches many lessons; the expected one is third |
| — | `中文乱码怎么解决` / `乱码` | gbk / aider / wsl-pip (rank 2–3) | `python-venv-tiktoken-module-not-found` | same "encoding" effect as row 1 |
| `zh-11` | `飞书机器人收不到消息` | `feishu-gateway-group-policy-silently-drops-messages` (rank 4) | `feishu-setup-complete-cc-connect` | **fusion normalisation** — see below |
| `zh-20` | `浏览器自动化被拦截` | `browser-automation-csp-bypass` (absent) | `chrome-relay-browser-automation` | the same shape: the winner contains 拦截 *and* matches both channels |

**The fusion one is structural, and it is the next piece of work.** `fuseRankings` weights each hit by
`covered` — the share of *that channel's* query terms the document matched. The two channels have very
different denominators: after alias replacement a CJK query has ~2 English terms but ~9 CJK bigrams. A
lesson matching both English terms (2/2 = 1.0) therefore outranks the Chinese lesson that is the answer
(3/9 = 0.33) even though the latter matched more of the *query*. Measured: adding a candidate alias
机器人→bot moved the expected lesson from absent to rank 4 — the English channel then matched it — and
`feishu-setup-complete-cc-connect` still won on a perfect 1.0 coverage. The fix is a normalised or
calibrated share per channel, and it needs the 20-question set plus the English arm to judge it — that is
a session of its own, not a patch to slip in behind a floor change.

## What this pass did not do

- No new alias entries. The table is hand-reviewed with per-entry evidence (`tests/test_query_aliases.py`
  re-checks every citation), and 机器人→bot was only measured as a candidate above.
- No tokenizer stemming ("blocks" ≠ "block" is why `浏览器自动化被拦截` misses today). A light plural
  strip changes every Latin ranking and needs its own before/after; it is the most promising single
  change for the English rows.
- No production re-measurement: the ranking change ships with the worker, so
  `scripts/bench_production_recall.py` should be run once the deploy lands.
