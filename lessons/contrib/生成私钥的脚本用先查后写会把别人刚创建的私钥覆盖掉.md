## Problem

【生成私钥的脚本用「先查后写」，会把别人刚创建的私钥覆盖掉】

写了一个给插件包打发布者签名的 Node 工具（零依赖，`node:crypto` 的 ed25519）。里面有��个生成私钥的函数：

```js
function generateKey(keyPath) {
  if (fs.existsSync(keyPath)) throw new Error(`私钥已存在，不覆盖：${keyPath}`);
  const { privateKey } = crypto.generateKeyPairSync('ed25519');
  const pem = privateKey.export({ type: 'pkcs8', format: 'pem' });
  fs.mkdirSync(path.dirname(keyPath), { recursive: true });
  fs.writeFileSync(keyPath, pem, { mode: 0o600 });
  return { privateKey, ... };
}
```

看着像「绝不覆盖已有私钥」，实际不是：**检查与写入之间是一个窗口**。期间若有人（或另一个进程）创建了同一个路径，这个脚本就会把那把私钥**覆盖掉**——而「绝不覆盖已有私钥」恰恰是这个函数唯一不能破的承诺。仓库的 CodeQL 把它报成 `js/file-system-race`（高危），位置正是那次 `writeFileSync`。

同一类还有两处：签名前「检查密钥不存在 → 生成」那一段（同样先查后写），以及读信任表时「`existsSync` 存在才 `readFileSync`」（窗口里文件换了，读到的就不是你检查过的那份）。

## Root Cause

把**保护**放在了写动作**之前的一次检查**上。凡是「检查 → 使用」两步，中间都存在 TOCTOU 窗口；正确做法是把不变量编码进那一步操作本身，让它**原子地**拒绝：

- 创建要独占：写入用 `flag: 'wx'`（create-exclusive），路径已存在时由内核让写失败，而不是靠脚本先问一句；
- 读要一致：直接读，文件不存在就当没有，而不是先检查再读。

「检查」不是保护，「操作本身的原子语义」才是。

## Fix

```js
function generateKey(keyPath) {
  const { privateKey } = crypto.generateKeyPairSync('ed25519');
  const pem = privateKey.export({ type: 'pkcs8', format: 'pem' });
  fs.mkdirSync(path.dirname(keyPath), { recursive: true });
  try {
    fs.writeFileSync(keyPath, pem, { mode: 0o600, flag: 'wx' });   // 原子独占
  } catch (error) {
    if (error && error.code === 'EEXIST') {
      const err = new Error(`私钥已存在，不覆盖：${keyPath}`);
      err.code = 'KEY_EXISTS';
      throw err;
    }
    throw error;
  }
  ...
}
```

调用方不再「先查后写」：直接调 `generateKey`，撞上 `KEY_EXISTS` 就**用那把已有的密钥**，不覆盖；其余错误照旧抛出。读信任表同理：直接 `readFileSync`，`ENOENT` 当作「没有信任表」，其余错误抛出。

## Verification

1. `node --check` 通过；
2. 实测：第一次 keygen 成功创建；**第二次报「私钥已存在，不覆盖」且原文件内容未被改动**（这是这条修复的核心判据）；
3. 用已有密钥走一遍完整签名流程：`keyCreated: false`、签名产物与 `verify` 均通过（说明「密钥已存在」不再被当成错误）；
4. 仓库 CodeQL（security-extended）重跑后 `js/file-system-race` 告警消失。

（注：工具与路径已脱敏；机制是这条教训的重点，具体工具名通常不是。）
