## Problem

桌面应用（多副本共存、共享同一配置目录）新增跨版本判定字段（如「本机见过的最高版本」）后：
新版本写入的字段，只要任何一个旧版本副本运行一次就从状态文件消失——判定依据被旧副本自己
擦掉，依附它的功能（旧副本事件标记）永远不生效。复现实验三步：新版本跑一次字段在 → 旧版本
跑一次字段消失 → 新版本再跑又写回。

## Root Cause

旧版本的反序列化结构只认识当年那几个字段；它每次运行都「读整个状态 → 改自己的字段 → 整文件
写回」，serde 对未知字段默认丢弃 → 新版本新增的任何字段都会被旧副本的写回抹掉。前向兼容坑：
加字段时没人会想到已发出、改不了的旧二进制会当橡皮擦。同坑会命中以后新增的任何状态字段。

## Fix

双层：
1. 未知字段保底（结构性，root cause）：状态结构加 `#[serde(flatten)] extra: Map<String, Value>`
（serde）或等价机制——读入时收集不认识的字段、写回时原样带回；新版本之间互不伤害（救不了
已发出的旧二进制，但影响面随旧副本退场收敛）。
2. 关键数据独立文件（免疫层）：跨版本判定必须依赖的数据（如最高版本记录）双写到旧版本根本
不认识的独立文件（如 telemetry-maxver.json）——旧副本不会碰它。判定读 max(独立文件, state
字段) 并把值救回 state 字段（给只认 state 的中间版本读），写回双写。

## Verification

- 回归一：state JSON 带未知字段（含嵌套）→ 本版本 load/save 往返后未知字段原样还在；
- 回归二：模拟旧副本写回（只含它认识的字段的 JSON 覆盖 state 文件）→ 判定仍从独立文件取到
最高版本、判出旧副本、并把 state 字段救回；
- 回归三：只有 state 字段、无独立文件（存量数据迁移）→ 判定正确、独立文件被补齐。
判据：单测全绿（新增 3 条回归用例，含「旧副本抹除后仍判出 stale」——照多副本复现步骤写）。
