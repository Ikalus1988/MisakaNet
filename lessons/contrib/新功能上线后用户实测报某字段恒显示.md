## Problem

新功能上线后，用户实测报「某字段恒显示 N/A」。翻代码一看，解析函数写得没问题，单测也绿（用的是手工构造的输入）。但在真实备份里，那个数据源文件**明明存在**——80 份 `summary.dg` 就在压缩包里。

于是形成一个很难查的假象：**功能没报错、解析没报错、单测全绿，就是不出值**。

## Root Cause

数据从磁盘/压缩包到解析函数之间还隔着一层**收集层的扩展名白名单**。那张白名单是**按需求逐个往里加**的：

```
初版    : .ls .tp .xml
某需求  : +.sv      （另一个功能要用）
新需求  : 需要 .dg  ← 忘了加
```

新功能的解析函数只管「给我文件内容」，它**不知道文件根本没被收进来**。于是 `null` 一路传到 UI 变成 N/A，中间没有任何一层报错。

同类症状还会出现在：某个检查项恒「跳过 / 不适用」、某列恒空、某个统计恒为 0——**凡是「静默无数据」都可能是收集层掐掉的**，不一定是数据真没有。

## Fix

1. **扩展名单一声明**：抽成单一常量/谓词（如 `isAnalyzeFile(name)`），所有收集入口共用，
   禁止各处硬编码 `.endsWith('.ls') || ...`（那是分叉的温床）
2. **改这张表前先问「谁要它」**：每加一个分析维度，同步加扩展名；表里每一项都要能说出「哪个功能依赖它」
3. **加回归锁**：测试断言关键扩展名**不许从表里删掉**——比单测解析函数本身更能防这类回归

## Verification

1. **拿用户报障的原始输入复现**（不是自造样本）：修复前恒 N/A、修复后出值
2. 数一数：组内文件数应「修复后 = 修复前 + 新扩展名的文件数」——数量对上说明是收集层，不是解析层
3. 回归锁：从白名单里删掉该扩展名 → 测试必须红

诊断口诀：**「界面 N/A 但源文件存在」→ 先查收集白名单，再查解析函数。**
单测绿只证明「拿到文件后能算对」，不证明「文件能拿到」。
