## Problem

排查一个"物理化结构上视频不出画面"的 bug 时，我在反编译树里找到一个形状非常契合的函数（两处"摄像机 ↔ 屏幕"的距离比较，正是"世界坐标当 plot 坐标用"那类错误），准备直接改。动手前先查调用方：**整棵反编译树里没有任何调用方** —— 它是死代码。

如果直接改，结果会是"修完还是坏"，还白烧一次游戏内验证（这个项目每轮验证都要用户重启客户端、实测、回传日志）。

## Root Cause

从**代码形状**推因果（"这段比较看起来就会导致这个症状"），没有先验证**可达性**。静态阅读很容易把死代码、未走分支、只在别的平台/版本里才用的路径当成活跃路径。

更隐蔽的一层："没有调用方"这个结论本身也有前提 —— **必须先核实反编译树是完整的**，否则漏掉的类会让结论反转。

## Fix

动手前用三种低成本手段**证活**：① grep 调用点（注意方法引用、lambda、反射、字符串派发）；② 查日志/断点有没有这条路线留下的输出；③ 加一条**一次性证据行**，在真实运行里观测一次，确认它真被走到。

并且先核对"完整性"本身：本例核对了 jar 里 724 个顶层类与反编译树 710 个 `.java` 的对应关系，确认只有我们自己注入的类不在其中，才敢下"死代码"结论。

## Verification

完整性核对通过 → 结论"死代码"，放弃该修法。此后所有修复都要求先有"这条路径被执行"的证据，且修复判据放在日志上（例：音频修复的判据是日志出现 `音源位置投影生效：plot 坐标 … → 世界坐标 …`，而不是"听起来有声了"）。

先核对反编译树完整性（724 顶层类 vs 710 .java），才允许下"无调用方=死代码"结论；修复判据必须落在日志证据行上
