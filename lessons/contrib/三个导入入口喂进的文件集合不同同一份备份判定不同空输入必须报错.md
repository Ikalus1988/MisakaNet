## Problem

一个检查工具有三个导入入口（单台上传、批量文件导入、批量文件夹导入），同一份备份从三个入口进来看到的检测结果不一致：同一个目录，单台报「1 台 / 43 项 / 3 失败 / 3 个问题」，批量文件夹导入报「43 台 / 每台 24 项 / 0 失败 / 0 问题」。

## Root Cause

批量文件夹导入是架构迁移留下的半截链路：它只把文件**路径**存进任务（{robotName, zipPath}），从不读文件内容。真正按 zipPath 读内容的是旧架构里的一个子进程；迁到新架构后渲染层只认 {robotName, files}，于是拿到空数组。

更危险的是：分析函数对空输入**不报错，而是返回「24 项检查全部通过、0 失败、funcType=默认值」**。空分析看起来像全绿。另外扫描层的扩展名表漏了一种格式，导致 36.2% 的备份目录扫出 0 个条目。

## Fix

1. 空输入必须失败：分析入口收到空集合时抛错（错误信息带被分析对象名），不允许返回「全过」。加单测锁死这条。
2. 修一类入口问题时，枚举所有入口做同一份输入的对拍（本次写了全量横扫脚本，对 3300 个真实目录比对三条链路的判定）。
3. 架构迁移（Electron→Tauri、单体→多端）后，grep 旧链路的「路径型任务」字段，确认新链路是否还在读它。

## Verification

全量横扫 3300 个真实机器人目录：三条链路的判定（检查数/通过/失败/应用类型/问题集合/信号数）全部一致，0 不符。空输入单测：空数组/undefined/null 均抛错且错误信息含对象名；有一个文件就照常分析（不误伤）。发版门禁全绿 + 桌面 exe 真机双入口对拍通过率一致。
