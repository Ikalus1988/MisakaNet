## Problem

一个多阶段硬件审查工具把「未验证」聚合成五类报告（阻断 / 缺数据 / 默认值 / 不会验 / 未接线）。用户看到「三、机器用了默认值：_无。_」就认为没有默认值。

真相是有 7 条：指向精度按 1.0°、最大跟踪角速度按 45°/s、检测距离按 3000mm、最小目标尺寸按 150mm、链路带宽按 8Mbps、端到端延迟按 300ms、电源电流按 2000mA —— 全部是代码里的默认值，不是设计里的数。

同类形态在同一项目里还出现两次：
- 阶梯的 V5/V6 恒为 not_run，报告只说「通过」不提这两层没跑；
- 链路表为空（links_list=[]）时检查函数返回 ok=True —— 空表被当成「检查通过」而不是「没检查」。

## Root Cause

聚合层去 budget.json 里找 coverify 字段，而 coverify 的判定结果只出现在 snapshot 的一次性返回值里，从不落盘。那个字段从来不存在，于是这一段永远读到 None，第三类永远为空。

三层机制叠加：
1. 数据源缺失不报错：读不存在的字段返回 None，被当成「没有条目」而不是「读不到来源」。
2. 空结果无凭据：报告只输出条目列表，不输出「查了什么、凭据在哪」，读者无法区分「查过，没有」与「没查」。
3. 上游产物无落盘：判定结果只存在于返回值里，下游拿不到，也不会为此报错。

危险之处：空表看起来像「这一类没有问题」，比误报更隐蔽 —— 误报会被人质疑，空表不会。

## Fix

1. 每类输出 checked(查了几项) + sources(凭据指纹)，产物缺失标 missing，渲染时显式写「该类没有被检查过」而不是省略整节。
2. 空结果分三态：not_ready / unknown / pass，空表不能返回 ok=True。
3. 判定结果必须落盘，聚合层只读产物、不重算（报告要对着某一版产物，用内容哈希做指纹而不是 mtime）。
4. 回归双侧断言：有来源时必须报出条目；没有来源时不能虚构且 sources 标 missing。

## Verification

双侧断言（均有实测）：
1. 有来源：counts.assumed == 7，七条默认值各自出现在报告第三类表格里，sources["coverify.json"] != "missing"。
2. 无来源：删掉 coverify.json 后 counts.assumed == 0（不虚构），且 sources["coverify.json"] == "missing"。
3. 退化验证：把聚合函数改回「去 budget.json 找 coverify 字段」，第 1 条立刻 FAIL（实测报「0 条」）；改回来后恢复 PASS。
