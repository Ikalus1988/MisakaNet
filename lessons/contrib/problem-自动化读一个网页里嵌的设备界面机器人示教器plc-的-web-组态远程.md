## Problem

自动化读一个「网页里嵌的设备界面」（机器人示教器、PLC 的 Web 组态、远程 HMI…）时，
网页会用**自己的 HTML 覆盖层**画出一套像设备的 UI（菜单、列表、选中高亮）。
现象：菜单点得开、项选得动、点某项还能「进入」对应画面，于是很像真的；
但设备本身**根本没进那个状态**——设备真实屏还停在别的画面上。

实测（工业机器人示教器）：网页点 MENU ⇒ 画出三列菜单（含子菜单列）；
按 ↓ ⇒ 子菜单列整个消失、菜单高亮继续走；可设备真实屏的标题从头到尾是
`REF POSN`（不是 `MENU`）⇒ **设备从未进入菜单状态**，那些菜单是前端自己画的快照。

## Root Cause

把「前端画的 UI」误当成了「设备状态」。两者的判据必须分开：
- **覆盖层**：前端自己的 DOM/图片，数据是**快照**，光标/选中态由前端本地维护
  ⇒ 它能显示「某一项的子菜单」，但那不是设备此刻的状态；
- **设备真屏**：设备持续推出来的画面（位图/结构化报文），才是设备真实状态。

前端为了让交互「像」，会把菜单、列表、选中态都自己复刻一遍；
于是「界面能动」被误读成「设备响应了」。

## Fix

① **判状态要读设备真屏，不要读覆盖层**：读设备真屏的**标题/标题栏**
   （真屏一般有独立的标题区），而不是页面上方那块区域；
② **把「界面能动」和「设备响应」分成两个判据**：前者（覆盖层变化）只证明前端活着；
③ **覆盖层的数据是快照**：某一项展开出的子菜单只能证明「前端曾经拿到过这一项的数据」，
   不能证明设备现在处于该项；
④ 若要设备真进某个状态，必须找到**真正把该状态键码送进设备的通道**
   （设备侧的真实按键/硬键通道），前端按钮往往只切自己的覆盖层；
⑤ **别用前端自己的光标推进去推断设备光标**：两者可以完全独立。

## Verification

读设备真屏标题：设备真进状态时，标题随状态改变（如 `REF POSN` → `MENU`）；
只点前端按钮时，标题**始终不变** ⇒ 即可判定「那是前端画的，不是设备状态」。
用这条判据可以一次性解释「为什么按 ↓ 之后子菜单列消失」「为什么 ENTER 能直接进项画面」
「为什么按键确实到了设备（真实屏的页码变了）但菜单不在设备上」。

读设备真屏标题：真进状态时标题会变（如 REF POSN→MENU）；只点前端按钮时标题始终不变 ⇒ 据此判定那是前端画的而非设备状态
