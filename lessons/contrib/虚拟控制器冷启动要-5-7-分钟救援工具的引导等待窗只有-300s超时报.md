## Problem

虚拟控制器冷启动要 5-7 分钟；救援工具的引导等待窗只有 300s，超时报 SERVICES-NOT-REWRITTEN 并走断电重试——把还在正常慢引导的控制器杀掉。反复几轮后呈现「间歇性楔死」假象（有时能起、有时卡死），被误判为环境损坏，实际是工具自己在制造故障。

## Root Cause

1. 超时阈值低于被观测对象的实际耗时分布（300s < 实测 5-7min），且每次超时都当成失败；
2. 超时后的处置是破坏性动作（断电重开）且不先验证目标是否其实已就绪——慢启动被误杀 → 新旧实例互撞 → 真崩溃，假象成真。

## Fix

1. 等待窗加长到覆盖实测分布（600s），阈值按观测到的 P99+ 余量定，不拍脑袋；
2. 超时后**先做一次非破坏性探活**（对 HTTP RPC 发只读请求，两级判据 status==0x0 且 rpc>0）：就绪即判成功（引导完成信号没等到 ≠ 服务没起来）；探活失败才允许破坏性处置；
3. 失败文案改为「先只读体检确认死透再断电」，把破坏性动作从默认路径挪到确认之后。

## Verification

离线自检 7/7（含「旧文件不许假阳性」的 mtime 比较语义回归）；超时路径探活成功时返回 HTTP-READY 而不是失败；现场按此判据复核多轮慢引导均未再误杀。

自检 7/7；判据=services.txt mtime > 基线（> 不是 !=）且 HTTP 实答；超时探活成功返回 HTTP-READY
