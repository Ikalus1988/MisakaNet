## Problem

一次配置事故（自制 agent preset 使工具面塌陷）之后，助手在【目标已不可达】的状态下持续尝试，直到会话被截断 —— 全程没有一次尝试能成功。用户事后描述为「卡循环了」。

时间线（UTC，来自会话 jsonl）：
· 05:38:05 追加自制 preset 的 patch 后，**人设生效**（system prompt 出现预期人设），**同时工具面塌陷**：pwsh / write / read / glob 全部 `unknown tool`，工具列表只剩 MCP 两项。
· 05:38:19 → 05:41:10 **穷尽式重试**，共 6 条路径：
   ① `pwsh` 执行回滚 → unknown tool
   ② `write` 写回滚脚本 → unknown tool
   ③ `mcpScript` + `require('fs')` → 该沙箱只有 tools/emit/console
   ④ `mcpScript` + `await import('node:fs')` → 同样无文件系统
   ⑤ `app_launch` 启动 powershell 执行 Copy-Item → approval 自动拒绝
   ⑥ `screen_read` 找到管理员 PowerShell 窗口后 `type` 命令 → approval 同样拒绝
· 06:46:16 用户：「卡循环了，大肥鱼」
· 06:46:31 助手输出了一条 thinking，**此后该会话再无任何记录**（无 text、无 toolCall、无最终回答）。

**关键结构：这不是「重复同一个调用」的死循环。** 对 jsonl 做统计，**不存在「连续完全相同调用 ≥4 次」的段**。真实形态是**穷尽换路**：每一轮都是**新的**尝试，但每一条都注定失败 —— 因为失败原因不是"路子选错了"，而是"目标要求的能力已经被卸载"。所有路径共享同一个已经被破坏的前提。

**⚠️ 影响面：同一次配置破坏同时打在多条并行会话上**（至少 4 条：1cdd02cf / ab42bfd6 / 511f30c3 / 488253f4），它们的末端都停在同一个死锁状态；其中 ab42bfd6 的末条是一个**悬空的 thinking**，没有收尾输出 —— 与同事故另一条会话（1cdd02cf，末条有完整回复）相比少 6 条记录。**⚠️ 注意：「撞上 token/上下文上限被截断」是基于"末条悬空 + 无收尾"的推断，并非实证** —— jsonl 中没有 token 计数记录，也可能是用户手动掐断。

## Root Cause

**自锁（deadlock by self-unmount）—— 不是"停不下来"，是"每一步都在原地"。**

1. **前提被破坏：** 修复动作本身需要 `write` / `pwsh` 这类文件系统工具，而追加 patch 的热加载**当场把这些工具卸载了**。于是"能修文件的工具"与"需要修的文件"同时消失。

2. **所有剩余路径共享同一个死前提：** 六条路径表面不同（写文件 / 跑命令 / 沙箱内脚本 / 动态 import / 启动进程 / 桌面自动键入），但它们都要求"我还有一个能执行动作的通道"。当工具面塌成只剩 MCP 两项、而 approval 又拒绝新通道时，**这六条路在逻辑上是同一条路**。

3. **没有止损点：** 助手从未对"目标是否仍然可达"做判断。每一次失败都被解释为"这条路不对，换一条"，而不是"目标本身要求我已经失去的能力"。于是重试没有上界。

4. **不可见的代价：** 每一轮重试都消耗上下文与 token。由于失败是**结构性**的（不是随机性的，重试不会改变结果），这些消耗的期望收益为零 —— 但界面上看起来像"还在努力"。

5. **多会话共因：** profile 配置是**会话间共享**的，一次破坏同时命中所有共用它的会话。因此"循环"不是一条会话的现象，而是同一时刻多条会话各自空转。

## Fix

**这个失败模式和「工具面为什么塌」是两个独立的教训 —— 配置修好了，空转仍会重演。**

1. **先认「目标不可达」，再决定停手。** 判断法则：如果**所有**可用手段都指向同一个前提（"我需要一个已经被卸载的能力"），那么继续换路子不是探索，是空转。此时唯一正确动作是**立刻停止并上报**。

2. **设一个显式的重试预算。** 例如"同一目标最多试 3 种手段，第 3 种失败后必须停下来写报告"。本次试了 6 种、无预算、无止损点。

3. **区分「换手段」与「换目标」。** 换手段在前提仍成立时有效；前提已被破坏时，所有手段都等价地无效。本次六条路（pwsh / write / mcpScript×2 / app_launch / type）表面不同，实则共享同一个死掉的前提。

4. **把「应急通道」列成清单并预先验证可用性。** 本次以为 app_launch / 桌面 type 能兜底，两者都被 approval 拒绝 —— 未验证的通道不算通道。

5. **⚠️ 多会话共因：** 配置层的破坏会**同时**打在所有共用该 profile 的会话上。修复时不能只盯当前这一条，要意识到"你看到的截断可能只是几条并行会话里最先撞墙的那一条"。

6. **给用户的报告要含：现在什么状态 / 为什么 / 一条可直接复制的回滚命令 / 怎么验证。** 本次做对了这一条，用户据此完成回滚 —— 这是事故里唯一起效的动作。

## Verification

**复现/检验方式**：对任何 agent 会话的 jsonl 做两类统计 ——
① **连续完全相同调用**的最大长度（≥4 次即为"重复型死循环"）；
② **同一目标下的不同手段序列**长度（本次 6 条）以及**每条失败原因是否同源**。
本次结果：① 为 0（没有重复型循环），② 为 6 且失败同源（都缺"可执行的通道"）。
⇒ **判据：连续尝试次数 ≥3 且失败原因同源时，应判定为目标不可达并停止。**
