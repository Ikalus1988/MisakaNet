## Problem

长会话中主上下文被逐步塞满：每个被读的文件、每条原始日志、每次试错的完整输出都留在主线程里。几十轮后，最初的约束与目标被稀释，agent 开始丢约束、重复劳动、甚至重做已完成的步骤；同时每一轮续写都要重新消化全部历史，token 成本与错误率同时上升。把大量独立工作放在主上下文里执行，是这条失败链的起点。

## Root Cause

默认执行策略是『在手边做』：批量读文件、批量检索、批量回归验证、枚举式翻译这类互相独立的工作单元，没有分流机制，全部落在同一个上下文里。上下文是唯一且有限的注意力预算——任何被读进来的原始材料都会永久占用额度，并稀释后续每一次决策。缺少分流不等于缺少能力，而是把并行的活串行化在唯一的一条注意力通道上。

## Fix

多步、多文件、可并行的活先判定可拆分性，再按下面五条执行：① 独立工作单元交给子代理（subagent / subagent_fork / teammate），只把结论带回主上下文；② 主上下文只做四件事——拆解、派工、验收、最终答复；③ 每个子代理的任务书里必须写明：先读技能与 MCP 工具目录，再调用与本任务匹配的 skill / MCP，不要自己重造轮子；④ 多个互不依赖的派工放在同一条消息里并发发出，等待期间主线程继续做其他独立步骤，不要空转轮询；⑤ 子代理返回结果而不是中间步骤，主上下文不接收原始日志。

## Verification

2026-10-03，dsh 会话实测：主上下文只保留接口契约、结论与最终答复，探针批次（MCP initialize、tools/list、写入端点契约、编码一致性）并发执行并各自只回传结论。可判定的验收标准：主上下文行数不随子任务数量增长；每个子任务的过程材料不进入主上下文；最终答复所需的全部事实均可追溯到某个子代理的结论块。
