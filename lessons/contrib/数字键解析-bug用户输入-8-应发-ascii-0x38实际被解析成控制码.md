## Problem

数字键解析 bug（用户输入 \"8\" 应发 ASCII 0x38，实际被解析成控制码 8=Backspace）。修复提交的信息写明「单个数字字符一律 ord()」，但补丁打在**调用层**（某工具的键循环里特判 `ord(tok) if len==1`），公共解析函数本体的分支顺序原样未动——CLI 与其他调用方继续发错键；更糟：单元测试断言了**反向行为**（parse(\"1\")==1）且注释写着「按 ASCII」，把 bug 锁成「预期」；另有三处文档（修复意图/CLI 帮助/协议表）口径都与实现相反。表面「已修」，实际只有打补丁的那条自家路径修了。

## Root Cause

**修复落层错误**（caller-layer patch vs 根函数）＋测试注释与断言值互相矛盾（锁定反向行为）＋文档/实现漂移无人对账——三者叠加让「修复已完成」的假象活了很多天。

## Fix

1. 把语义**收编进根函数本体**：单个数字字符一律 `ord()`；控制码走显式十六进制（\"0x8\"）；多位十进制键码不变——调用层特判变冗余但无害；
2. 测试对齐并**加钉三条边界**（\"1\"→0x31 / \"8\"→0x38 / \"0x8\"→8）；
3. 文档勘误注明修复落层史，防后人再从调用层打补丁。

## Verification

全套测试绿（含新钉三例）；行为级验证 parse(\"8\")==0x38、parse(\"0x8\")==8；跨调用方抽查（CLI 与导出工具同语义）；测试注释与断言值一致。

根函数行为级断言（parse('8')==0x38、parse('0x8')==8）绿；所有调用方抽查同语义；测试注释与断言值一致；文档口径与实现三方对账一致
