## Problem

一台工业仿真机（ROBOGUIDE 虚拟控制器）出现「连接反复重建 / 协议栈刷屏 / 客户端永远登录不上」的**网络/协议症状**，
排查了半天才发现：**没有任何网络问题**——是自研的看门狗（自愈器）自己造成的。

看门狗的「假活」判据是「进程在 + 3 秒 CPU 增量 ≤0.1 + 内存一字不动 ⇒ 判定为已死 ⇒ 干净断电 + 重开」。
而它监控的进程列表里包含一个**常驻空闲的辅助宿主进程**（无窗口、COM 本地宿主、没人调用时天然零 CPU、内存恒定）
⇒ **每个稳定周期必然撞上阈值** ⇒ 每 45~51 秒重启一次整机。

⇒ 症状链条完全被误导：重启 ⇒ 会话被打断 ⇒ 下一次启动时残留失效连接被再次投递 ⇒ 协议栈刷屏
（「connection already closed」几百行）⇒ 看起来像「协议栈有 bug / 端口绑定失败 / 安全软件拦回环」；
真正的主机进程**一次都没坏过**，客户端登录不上也只是「每次都被重启打断」的**结果**。

## Root Cause

**健康信号的归因错了**：把「某个辅助进程的空闲」当成了「整个系统死了」。
⇒ 更糟的是**自愈器用自己的误判驱动自愈**，于是：
   ①误判被放大成**重启循环**（越重启越像坏了）；
   ②它制造出的症状（连接重建/协议栈刷屏/客户端掉线）**正是后来所有人去追的那个症状**
   ⇒ 排查方向被整体带偏（去查协议、端口、加密软件、模板），而真因是自家工具。
（与语料 `event-count-is-not-a-health-signal` 同族：拿错健康信号驱动自动修复 ⇒ 去杀健康的服务；
本条补的是**「信号取自辅助进程」+「自愈放大误判并自造症状」+「调试期必须能关自愈」**这三点。）

## Fix

① **健康信号必须取自「承载工作」的那个进程**，辅助/空闲宿主进程不参与存活判定（哪怕它在监控列表里）；
② **自愈的判据与观测的判据要能分开**：排障期间必须能「只观测、不自愈」，
   否则自愈器会持续污染现场（并把自己的噪声写进同一份日志，互相覆盖）；
③ **自愈必须幂等且有上限**：同一段「存活时长」内不得重复触发（防止误判 ⇒ 循环）；
④ **识别「循环」的特征**：进程 PID 每几十秒换一任、日志文件大小反复回退（被重写）、连接在每次启动后的固定行号重新刷屏
   ⇒ 这是「有人在我头上反复重启」的指纹，不是网络问题；
⑤ **发现症状时先查「谁在重启我」**：看进程代际（PID 更替）+ 自愈工具日志，再谈协议。

## Verification

修判据后连续观察 >15 分钟：**进程 PID 不再更替**、日志不再回退、协议栈刷屏消失、客户端登录成功（TPIF-137 出现）
⇒ 证明症状链的每一环都来自自愈器，而非网络/协议/安全软件。
同时按 §「先查谁在重启我」的指纹法，在另一次现场同样命中。
