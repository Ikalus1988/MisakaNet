## Problem

自动化监控 GUI 向导类长任务时，用「目标进程的窗口还在」当「构建进行中」判据——结果把**「已完成、坐在完成对话框上待命」误判成「还在干活」**，盯着进度空等 40 分钟；期间还对着成品目录的「空/未出现」反复起疑，甚至对早已完成的任务做多余的救援点击。监控脚本的超时退出还带 0 退出码（假成功），把误判固化成「构建失败」的错误结论。

## Root Cause

「窗口存在」只证明**进程活着**，不证明**工作在进行**：GUI 构建类任务完成后的常见形态就是停在完成/确认对话框（零 CPU、产物已落盘）。单一存活判据把「完成待命」与「进行中」「卡死」三态混为一谈；配套的超时 return 0 又让上游无法区分。

## Fix

长任务监控用**三重硬判据**区分三态：
1. **CPU 采样**（3 秒窗口 delta）：进行中=持续 >0；完成待命/卡死≈0；
2. **产物时间戳**：输出文件全部集中在起跑后一小段=干完了；持续零散新增=进行中；目录空=真没开工；
3. **完成信号**：任务自身日志的收尾行（如干净 SHUTDOWN/成功摘要）是金判据。
监控超时必须**非零退出**并附三态证据；救援动作（补点按钮等）先核对目标窗口的当前画面/子控件状态，别对着历史截图的坐标开火。

## Verification

实际误判案例事后一击定态：CPU delta=0.0 + 全部产物时间戳集中在 1 分钟内 + 任务日志以「Saving Complete → SHUTDOWN」收尾 = 判定「40 分钟前已完成」；据此跳过重建、直接消费成品，全流程恢复。三判据均可脚本化（进程时间 API + 目录 mtime + 日志关键字）。
