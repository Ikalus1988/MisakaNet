## Problem

用设备自带的「网页/远程客户端」自动化时，发现一个诡异现象：**每做一次操作，设备端的状态就被清空**。
现象链：点一下菜单 ⇒ 菜单能开；但一按方向键，展开的子菜单就消失、状态回到原处；
设备日志显示每次交互后设备任务重新初始化（`… ready at …`）。

实测（工业机器人示教器）：网页客户端每次发键都会
`连接 → 送键 → 握手事件顺序错 → 断开 → 设备任务重新 ready`
⇒ **设备任务被反复重启** ⇒ 任何「先进入某状态、再在里面翻页」的操作都不可能成立
⇒ 只能读到「刚进入状态那一瞬间的快照」。

## Root Cause

**交互通道是「一次一连」的短连接**：每发一个键都新建连接 ⇒ 设备把这次交互当成
「新的客户端会话」⇒ 设备端任务/会话状态重新初始化 ⇒ 之前建立的状态（菜单展开、编辑上下文、
多步向导）全部归零。

⇒ 「状态化 UI 不可遍历」看起来像 UI 的问题，实际上是**通道语义**的问题：
**每次动作都在重置设备会话**。

## Fix

① **先确认通道语义**：看设备日志/抓包，确认「一次操作 = 一次新连接 + 设备任务重启」；
   只要成立，「翻页/遍历/多步操作」就必然不稳定，**不要再从 UI 逻辑上找原因**；
② **换一条不会重建会话的通道**：设备通常还有别的入口
   （本例：控制器自带的 **TP 终端口**，连上是一条**长连接**，
   登录后屏以**文本**整屏下发 ⇒ 不抢焦点、不需要 OCR、状态能保持）；
③ **把「读屏」与「发键」分开判断**：读屏通道可用 ≠ 发键通道可用 ——
   本例里读屏（文本）先通，发键编码还没解 ⇒ 结论要分开写，别混成「这条路走通了」；
④ **先解「最小动作」**：找到能让设备**可见地**变化的那一个键（而不是盲试一堆编码），
   用它当探针来反推其余编码；
⑤ **穷举编码时要有判据**：光等「屏幕文本变化」不够 —— 设备常常只下发**变化区域**，
   文本不变但光标/位置变了 ⇒ 判据要包含原始字节流的变化。

## Verification

对照日志：交互前后设备任务是否重新 ready；同一条长连接上连续发多个动作后，
设备状态是否保持（菜单展开项仍在）。只要「一次操作 = 一次 ready」，就判定为短连接通道，
应当改走长连接通道而不是继续调 UI 自动化。

看设备日志：一次操作是否伴随任务重启；长连接上连续多动作后设备状态是否保持（菜单展开项仍在）
